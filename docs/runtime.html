Runtime Folder

Fully self-contained portable runtime created and managed by bootstrap/setup.py. It holds a private Python interpreter, a private PHP (CGI + CLI), the SQLite CLI tools, a cache of the downloaded archives, and — optionally — a native llama-server binary. Nothing here touches the host system's PATH, registry, or site-packages. The whole folder is safe to delete; running the bootstrap recreates it from scratch.

Overview docs

runtime/ — what this folder is
doc

Overview

The runtime/ folder is the single point of contact between the project and the outside world's binaries. It is created on first run by bootstrap/setup.py and contains everything the backend needs to run — Python, PHP, SQLite — without relying on whatever happens to be installed system-wide.

Because of this isolation, every install behaves identically. Windows, macOS, and Linux all end up with the same Python version, the same PHP build, and the same SQLite CLI. The host system's PATH, PYTHONPATH, registry, and site-packages are never touched.

The folder is disposable. Deleting runtime/ entirely and running python bootstrap/setup.py again rebuilds everything from scratch. No state lives here that cannot be regenerated.

What lives here

SubfolderContentsSize (typical)
_downloads/ Cached archives of every downloaded component ~90 MB
python/ Portable CPython 3.12.11 interpreter + stdlib + installed pip deps ~120 MB + deps
php/ PHP 8.4 CLI (php.exe) + CGI (php-cgi.exe) + php.ini ~40 MB
sqlite/ SQLite CLI tools (sqlite3, sqldiff, sqlite3_analyzer) ~3 MB
llama-server/ Optional native llama-server binary (user-supplied) ~10–50 MB
runtime.env Manifest — absolute paths to every installed binary < 1 KB

What does not live here

These sit at the project root, next to runtime/:

PathPurpose
models/GGUF model weight files
logs/Rotating daily log files
php_app/The PHP notes app source + its SQLite database
sessions.dbChat sessions and graph run history
web/Frontend HTML / CSS / JS
.envUser configuration (AGENT_* variables)

Who manages it

Exactly one thing: bootstrap/setup.py. Nothing else writes to this folder. The backend reads from it (via the manifest), and the launcher scripts (start.sh / start.bat) source the manifest to find the binaries. But the folder's contents are entirely the bootstrap's responsibility.

The only exception is llama-server/, which the bootstrap never writes to. That folder exists for users who want to drop in a native llama.cpp binary; the backend detects it automatically at startup.

Order of operations

main() runs six stages in a fixed order. A failure in one stage does not abort the others unless a later stage depends on it — for example, pip cannot install into a Python that was never unpacked.

  1. Python — install_python
  2. PHP — install_php (Windows and Unix paths differ)
  3. SQLite — install_sqlite
  4. Python deps — install_python_deps (only if Python installed)
  5. Vendor files — download_vendor (LiteGraph, optional)
  6. Manifest — write_runtime_env (only if Python installed)
Why the manifest is written last. The manifest describes what was actually installed. If the script crashes halfway through, there is no manifest — and the launcher scripts detect its absence and report "run bootstrap first" instead of failing with a missing-binary error.

_downloads/ folder

runtime/_downloads — archive cache
cache

_downloads/

A cache of every archive the bootstrap has downloaded. Its only purpose is to avoid re-downloading a 30 MB PHP ZIP when you re-run the bootstrap to fix a different component.

What lives here

File patternSourceSize
python-<version>-<triple>.tar.gz astral-sh/python-build-standalone ~27 MB
php-<version>-Win32-<vs>-x64.zip (Windows) windows.php.net ~31 MB
php-<version>-cli-<os>-<arch>.tar.gz (Unix) dl.static-php.dev ~11 MB
sqlite-tools-<platform>-<version>.zip sqlite.org ~2.5 MB

Cache behaviour

download() checks whether the target file exists and is larger than the expected minimum size before opening a network connection. If both are true, the cached copy is used. 

def download(url, dest, *, force=False, expected_min_size=0, label="file"):
    if dest.exists() and not force:
        size = dest.stat().st_size
        if size >= expected_min_size:
            Log.ok(f"{label} already cached ({_human_bytes(size)})")
            return dest
        Log.warn(f"{label} cached but small - re-downloading")
    ...

During download, a .part file is written and atomically renamed when complete. An interrupted download therefore leaves a .part file, not a corrupted cache entry — the next run sees no cached file and re-downloads cleanly.

Sizes and the minimum-size check

Each download specifies a minimum expected size. A response smaller than that is almost always an HTML error page from a captive portal or proxy, not the real binary:

ArchiveMinimum size enforced
Python tarball10,000,000 bytes
PHP Unix tarball3,000,000 bytes
PHP Windows ZIP20,000,000 bytes
SQLite CLI ZIP500,000 bytes

If the downloaded file is below the threshold, it is deleted and the download fails with a clear message. This catches the class of problem where a corporate proxy returns a 200 with an HTML login page and the bootstrap would otherwise try to extract a ZIP containing an HTML login page.

Safe to delete. This folder holds nothing unique. Deleting it frees roughly 90 MB and the next bootstrap run re-downloads everything.

Cache corruption

If a download completed but the extracted binary is broken, the cached archive is the suspect. Delete the folder and force a fresh download:

Windows:

> rmdir /s /q runtime\_downloads
> python bootstrap\setup.py --force

Unix:

$ rm -rf runtime/_downloads
$ python bootstrap/setup.py --force

Why cache at all?

  • Re-runs are fast. Fixing a broken php.ini usually means re-running the PHP installer only. With the cache warm, that is a local extract rather than a 30 MB download.
  • Offline reinstalls work. If you already have the archives, the bootstrap can install from the cache without network access.
  • Deterministic. The pinned versions make the cached archive a known-good copy. Re-running with the same cache produces byte-identical binaries.

python/ folder

python/

A completely self-contained CPython 3.12.11 interpreter. Every Python dependency the backend needs — FastAPI, uvicorn, openai, mcp, httpx, loguru, and the rest of requirements.txt — is installed into this interpreter's site-packages, not the host's.

Source of the binary

Downloaded from astral-sh/python-build-standalone (tag 20250712). The specific archive is:

Where <triple> is one of:

The install_only_stripped suffix means the archive contains the interpreter and stdlib only — no build system, no debug symbols. It is roughly 27 MB.

Installation process

  1. Download the tarball into _downloads/.
  2. Extract it into a temporary directory.
  3. Move the single top-level folder into runtime/python/.
  4. Verify by running python --version.
  5. If verification fails, remove the folder and return failure.

Pip dependencies

Once the interpreter is in place, install_python_deps runs: 

runtime/python/python.exe -m pip install -r requirements.txt

Every dependency lands in this interpreter's Lib/site-packages/. Because the interpreter is completely isolated, pip never sees (and never installs to) the host's Python.

Why a private interpreter?

  • Version lock. The project requires Python 3.12.x. If the host has 3.10 or 3.13, the difference can break a dependency. The private interpreter is always the pinned version.
  • No conflicts. Installing FastAPI into the host's site-packages can break other projects that need a different FastAPI version. The private interpreter avoids that entirely.
  • Portable. The whole folder can be copied to another machine that has never had Python installed.
  • Reproducible. Same version, same sources, same result on every machine.
The MCP subprocess uses this interpreter. AGENT_MCP_SERVER_COMMAND defaults to sys.executable, which is this interpreter when the backend is launched via start.sh / start.bat. The MCP server therefore shares the same venv and installed packages as the backend.

Rebuilding from scratch

To reinstall Python and every pip dependency: 

python bootstrap/setup.py --force --skip-php --skip-sqlite --skip-vendor

This re-downloads the Python tarball (unless cached), replaces the interpreter folder, and re-runs pip install -r requirements.txt. Use it when a package is corrupted or the interpreter itself misbehaves.

php/ folder

runtime/php — portable PHP (CGI + CLI)
interpreter

php/

A portable PHP installation containing both SAPIs — the CLI (php.exe) and the CGI binary (php-cgi.exe). The CGI binary is the one the backend actually uses; the CLI is kept for debugging.

What lives here

PathPurpose
php.exeCLI SAPI — for running PHP scripts from a terminal
php-cgi.exeCGI SAPI — the one the backend uses
php.iniWritten by the bootstrap; enables the required extensions
php8ts.dllThe PHP engine (thread-safe build on Windows)
ext/Extension DLLs (php_pdo_sqlite.dll, etc.)
libcrypto-3-x64.dllOpenSSL runtime (Windows)

Two SAPIs, one install

PHP ships as several "SAPI" (Server API) front ends that share a common engine. The two that matter here:

  • CLI — designed for command-line scripts. php script.php runs the script and exits.
  • CGI — speaks the CGI/1.1 protocol. Reads the request from environment variables and stdin, writes the response (headers + body) to stdout. This is what a web server would normally launch.

The backend is not a web server in the PHP sense, but it can set up the CGI environment variables and pipe the request body to php-cgi.exe — which is exactly what backend/php_server.py does.

Why not just use the CLI? The CLI reads scripts from disk. The CGI binary reads the request from stdin and environment. They are not interchangeable for serving web requests. The notes app is written against the CGI environment ($_SERVER, $_GET, $_POST) and cannot run on the CLI SAPI.

Windows vs Unix sources

PlatformSourceWhy
Unix (Linux / macOS) dl.static-php.dev (static-php-cli) Single statically-linked tarball, no dependencies
Windows windows.php.net (official) Only distribution that ships php-cgi.exe

The static-php-cli Windows builds only contain the CLI SAPI. The official PHP for Windows ZIP is larger (~31 MB vs ~6 MB) but contains both SAPIs and every extension DLL the notes app needs.

Fallback chains

Version candidates are tried in order. On a typical install the first candidate succeeds: 

PHP_WINDOWS_VERSION_CANDIDATES = [
    "8.4.15", "8.4.14",
    "8.3.33", "8.3.32", "8.3.31", "8.3.30",
    "8.2.30", "8.2.29",
]

For each version, the installer also tries two VS variants (vs17 then vs16) and two folder names (releases then releases/archives). That is up to 32 URL combinations before giving up.

The php.ini trap

The official Windows PHP ZIP does not include a working php.ini. It ships two samples (php.ini-development and php.ini-production), neither of which is loaded automatically. Without a real php.ini, PHP starts with every extension disabled — including pdo_sqlite — and the notes app fails with "could not find driver".

The bootstrap writes a minimal php.ini into runtime/php/ after extraction: 

extension_dir = "ext"

extension=pdo_sqlite
extension=sqlite3
extension=mbstring
extension=openssl

display_errors = On
error_reporting = E_ALL

date.timezone = UTC

Required extensions

ExtensionRequired by
pdo_sqliteThe PDO connection in db.php
sqlite3Companion to pdo_sqlite; some helper functions use it directly
mbstringmb_strlen() and mb_substr() in index.php
opensslPassword hashing helpers and any future HTTPS calls

If pdo_sqlite is missing from -m, the php.ini was not loaded. Check that runtime/php/php.ini exists and contains the four extension= lines.

Quick fix for a broken php.ini

python bootstrap/setup.py --force --skip-python --skip-sqlite --skip-deps --skip-vendor

Re-extracts the PHP ZIP and writes a fresh php.ini. Takes about 30 seconds and does not touch anything else.

Version scheme

3460000 is SQLite's version number in their own encoding — the digits are 3 46 00 00, meaning version 3.46.0. The pattern is M mm pp ss (major, minor, patch, sub-patch) with each field two digits except the major.

llama-server/ folder

runtime/llama-server — optional native binary
optional

llama-server/

This folder is not created or managed by bootstrap/setup.py. It is an optional drop-in location for a native llama-server binary from the upstream llama.cpp project.

Why it exists

The Python llama-cpp-python wheels are compiled with AVX-512 instructions. On CPUs without AVX-512 support (Intel 9th gen and older, most 10th and 11th gen desktop SKUs), the first GGML kernel that runs raises STATUS_ILLEGAL_INSTRUCTION (0xC000001D) and the process dies.

The native llama.cpp binaries are compiled with the baseline instruction set (or AVX2, depending on which ZIP you download) and run on any modern x64 CPU. Dropping one into this folder is the fix.

What lives here

FilePurpose
llama-server.exe / llama-serverThe main server binary
llama.dll / libllama.soThe core library
ggml.dllGGML tensor library
ggml-cpu.dllCPU kernel implementations
ggml-cuda.dll (optional)CUDA GPU offload kernels

How to install a native binary

  1. Go to github.com/ggml-org/llama.cpp/releases.
  2. Pick the release matching your CPU:
    • llama-...-bin-win-cpu-x64.zip — CPU-only build (most compatible)
    • llama-...-bin-win-cuda-x64.zip — CUDA GPU build
  3. Extract the ZIP so that llama-server.exe lands directly in runtime/llama-server/.
  4. Restart the backend. It will prefer the native binary over the Python module automatically.

Binary discovery order

The backend's find_llama_server() checks in this order:

  1. AGENT_LLAMA_CPP_BINARY if set and pointing at an existing file
  2. runtime/llama-server/llama-server.exe (this folder)
  3. llama-server on the system PATH

If none is found, the backend falls back to the Python module python -m llama_cpp.server.

Verifying

> runtime\llama-server\llama-server.exe --version
version: 3xxx (xxxxxxxx)
built with MSVC ...

> runtime\llama-server\llama-server.exe --help
usage: llama-server [options]
...

Once the binary is in place, the backend log will show: 

INFO | Spawning llama-server (native, model size 2.00 GB,
       port 8080, alias 'local')
INFO | llama-server ready at http://127.0.0.1:8080
       (model=..., backend=native, alias=local)

The backend=native field confirms the native binary was used rather than the Python module.

Deleting this folder is safe. If the native binary is not present, the backend simply falls back to the Python llama_cpp.server module. The only consequence is the potential AVX-512 crash on older CPUs.

Sidecar DLLs

On Windows, the native binary depends on several DLLs shipped alongside it. The backend prepends this folder to the subprocess's PATH so the DLLs are found at load time: 

env["PATH"] = binary_dir + os.pathsep + existing_path

If you move the binary elsewhere, keep the DLLs next to it or the process will fail to start with a missing-DLL error.

doc

The Manifest

runtime/runtime.env is a shell-sourceable file written by the bootstrap after every other stage has completed. It records exactly which binaries were installed and where they live, so the launcher scripts do not have to hard-code paths.

Format

One KEY=VALUE per line, in .env-style syntax. Comments start with #. Paths are absolute and unquoted — the launcher scripts handle path separators themselves.

Fields

KeyMeaning
RUNTIME_PLATFORMwindows | linux | macos
RUNTIME_ARCHx86_64 | aarch64
RUNTIME_PYTHON_VERSIONPinned Python version (e.g. 3.12.11)
RUNTIME_PHP_VERSIONThe PHP version that actually got installed
RUNTIME_SQLITE_VERSIONSQLite version in its own encoding
RUNTIME_PYTHONAbsolute path to python.exe / python3
RUNTIME_PHP_CLIAbsolute path to php.exe / php
RUNTIME_PHP_CGIAbsolute path to php-cgi.exe / php-cgi
RUNTIME_SQLITEAbsolute path to sqlite3.exe / sqlite3

Missing binaries

If a binary was skipped or failed to install, its key is left with an empty value: 

RUNTIME_PHP_CGI=

Launcher scripts check for the empty value and can decide whether the missing binary is fatal for the task at hand. A missing PHP, for example, only disables the notes app — the chat and graph features continue to work.

How launcher scripts use it

Unix (bash):

#!/usr/bin/env bash
set -euo pipefail

if [ ! -f runtime/runtime.env ]; then
    echo "Runtime not installed. Run:"
    echo "    python bootstrap/setup.py"
    exit 1
fi

set -a
source runtime/runtime.env
set +a

"$RUNTIME_PYTHON" -m uvicorn backend.main:app \
    --host 127.0.0.1 --port 8000

Windows (batch):

@echo off
if not exist "runtime\runtime.env" (
    echo Runtime not installed. Run:
    echo     python bootstrap\setup.py
    exit /b 1
)

for /f "usebackq tokens=1,* delims==" %%a in ("runtime\runtime.env") do (
    if not "%%a"=="" if not "%%a:~0,1%"=="#" set "%%a=%%b"
)

"%RUNTIME_PYTHON%" -m uvicorn backend.main:app --host 127.0.0.1 --port 8000

Why a manifest file?

  • Single source of truth. The launcher does not need to know whether the platform uses python.exe or bin/python3.
  • Easy to inspect. When debugging a startup problem, cat runtime/runtime.env tells you exactly which binary the launcher will use.
  • Detects partial installs. The manifest is written last, so its presence means every preceding stage succeeded. The launcher's absence check is therefore a one-line "is the runtime ready?" test.
  • Machine-readable. Scripts (bash, batch, Python, PowerShell) can all parse it without a library.
Do not edit this file by hand. It is regenerated by write_runtime_env() at the end of every successful bootstrap. Any manual edits are lost on the next run.

Regenerating

Any successful bootstrap run regenerates the manifest — including runs that skip most stages: 

python bootstrap/setup.py --skip-php --skip-sqlite --skip-deps --skip-vendor

This re-writes the manifest with the current paths after the Python stage completes. Useful when the folder was moved to a different absolute path.

Safe to Delete

Everything inside runtime/ is regenerable. This page explains what each removal costs and how to restore it.

Path Safe? Effect Restore
runtime/_downloads/ ✅ Frees ~90 MB. Next bootstrap re-downloads. setup.py
runtime/python/ ✅ Backend cannot start. MCP subprocess cannot start. setup.py
runtime/php/ ✅ /php/ routes return 500. Rest of the app is unaffected. setup.py
runtime/sqlite/ ✅ None. Only the manual-inspection CLI is lost. setup.py
runtime/llama-server/ ✅ llama-cpp falls back to the Python module. Re-download the native ZIP
runtime/runtime.env ✅ Launchers report "run bootstrap first". setup.py
runtime/ (whole) ✅ Full reset. Nothing survives. setup.py

What is not safe

Nothing inside runtime/ holds user data. But three folders outside runtime/ are irreplaceable and should never be deleted as a shortcut:

PathContains
sessions.db Every chat session and graph run ever recorded
php_app/data/app.db Every note the user has written in the PHP app
models/*.gguf Multi-gigabyte model files. Re-downloadable but slow.
These are outside runtime/. If you are resetting the runtime, make sure your delete command targets runtime/ only, not the project root.

Full reset

The nuclear option — remove everything and rebuild from scratch:

Windows:

> rmdir /s /q runtime
> python bootstrap\setup.py

Unix:

$ rm -rf runtime
$ python bootstrap/setup.py

This deletes the cache too, so it will re-download everything (~90 MB). Expect 2–5 minutes depending on network speed.

Partial reset — fix one component

More common: something specific is broken and you want to reinstall only that. Use the --skip-* flags:

GoalCommand
Reinstall PHP only setup.py --force --skip-python --skip-sqlite --skip-deps --skip-vendor
Reinstall Python + deps setup.py --force --skip-php --skip-sqlite --skip-vendor
Rebuild manifest only setup.py --skip-php --skip-sqlite --skip-deps --skip-vendor
Regenerate SQLite only setup.py --force --skip-python --skip-php --skip-deps --skip-vendor

Freed space

PathTypical size
_downloads/~90 MB
python/~120 MB (bare) + deps
php/~40 MB
sqlite/~3 MB
llama-server/~10–50 MB (if present)
Total~250 MB+
Delete the cache first for quick wins. If you need disk space and the runtime is working, deleting _downloads/ is the safest single action — it frees the most space with no functional impact.

Helper functions

Four helper functions encapsulate the platform difference so no other code needs to care: 

def python_binary(plat):
    return RUNTIME / "python" / (
        "python.exe" if plat["is_windows"] else "bin/python3"
    )

def php_cli_binary(plat):
    return RUNTIME / "php" / (
        "php.exe" if plat["is_windows"] else "php"
    )

def php_cgi_binary(plat):
    return RUNTIME / "php" / (
        "php-cgi.exe" if plat["is_windows"] else "php-cgi"
    )

def sqlite_binary(plat):
    return RUNTIME / "sqlite" / (
        "sqlite3.exe" if plat["is_windows"] else "sqlite3"
    )

Executable bit

On Unix, binaries need the executable bit set. The bootstrap does this after extraction: 

try:
    cgi_exe.chmod(cgi_exe.stat().st_mode | 0o755)
    cli_exe.chmod(cli_exe.stat().st_mode | 0o755)
except OSError:
    pass

On Windows no equivalent step is needed — .exe files are executable by extension.

Path separators in the manifest

Paths in runtime.env use the platform's native separator. The batch launcher on Windows and the bash launcher on Unix both parse the file without modification: 

# Windows manifest
RUNTIME_PYTHON=C:\Users\Admin\Desktop\3olution_Agent_Graph_Project\runtime\python\python.exe

# Unix manifest
RUNTIME_PYTHON=/home/user/3olution_agent_graph/runtime/python/bin/python3
Copying across platforms. The runtime folder is not portable between platforms. A runtime/ built on Windows will not work on Linux and vice versa. Re-run the bootstrap on the target platform.

Whitespace in paths

The bootstrap handles paths containing spaces on both platforms. The manifest does not quote paths — the launcher scripts use set -a on Unix and set "VAR=VALUE" on Windows, both of which preserve spaces correctly. Subprocess calls pass the path as a single list element, so the shell never sees it unquoted.

Troubleshooting

"Runtime is incomplete" from --check

setup.py --check returns exit code 1 when any required component is missing. The output marks each missing item with [error]: 

> python bootstrap/setup.py --check

[ok]   Python: C:\...\runtime\python\python.exe  (Python 3.12.11)
[ok]   PHP CLI: C:\...\runtime\php\php.exe
[ok]   PHP CGI: C:\...\runtime\php\php-cgi.exe
[ok]     PHP 8.4.15 (cgi-fcgi) (built: ...)
[ok]   php.ini: C:\...\runtime\php\php.ini
[ok]   SQLite CLI: C:\...\runtime\sqlite\sqlite3.exe
[ok]   Manifest: C:\...\runtime\runtime.env

Common failure messages and their fixes:

MessageFix
Python: missing Run full bootstrap without --skip-python.
Python: <detail> Binary exists but does not run. Delete runtime/python/ and re-run.
PHP CGI: missing Run bootstrap without --skip-php.
php.ini: missing Run the PHP-only reinstall (see below).
SQLite CLI: missing Optional. Run without --skip-sqlite if you want it.

Download fails with HTTP 403 or 404

The pinned version was probably retired. Check the version candidate lists at the top of setup.py and add a newer version. For PHP Windows, the URL structure is: 

https://windows.php.net/downloads/releases/php-8.4.15-Win32-vs17-x64.zip

Browse windows.php.net/download/ to confirm which versions are currently listed.

"Archive is too small after download"

Almost always a captive portal or corporate proxy returning an HTML error page instead of the actual file. Verify with: 

> curl -I https://windows.php.net/downloads/releases/php-8.4.15-Win32-vs17-x64.zip
HTTP/1.1 200 OK
Content-Length: 32618504
Content-Type: application/zip

If Content-Type is text/html, you are behind a login wall. Configure your proxy or use a different network.

Antivirus quarantines php-cgi.exe

Some consumer AV products flag freshly-extracted PHP binaries from windows.php.net. This is a false positive — the official ZIP is signed and the binaries carry the PHP project's signature.

Options:

  • Add <project>\runtime\php\ to the AV exclusion list.
  • Use Windows Defender, which does not false-positive on these.
  • Install PHP system-wide (XAMPP, Chocolatey) and set AGENT_PHP_BINARY in .env.

"Could not find driver" from the notes app

The php.ini is missing or the extensions are not enabled. Check: 

> runtime\php\php.exe -m
[PHP Modules]
...
pdo_sqlite
sqlite3
...

If those two lines are absent, the php.ini is not being loaded. Confirm it exists: 

> dir runtime\php\php.ini

If missing, run the PHP-only reinstall:

python bootstrap/setup.py --force --skip-python --skip-sqlite --skip-deps --skip-vendor

"Unsupported CPU: <arch>"

The bootstrap only knows x86_64 and aarch64/arm64. On 32-bit x86 or an exotic architecture, download the runtimes manually and set AGENT_PHP_BINARY plus a suitable system Python.

pip install fails on a specific package

Some packages need a C compiler. On Windows, install the Microsoft C++ Build Tools and re-run. On Linux, install build-essential and python3-dev.

A faster alternative: install wheels from a pre-built index. Add --only-binary :all: to the pip line temporarily to see which packages lack wheels.

Bootstrap crashes with a Python traceback

Re-run with --verbose to see the full stack:

python bootstrap/setup.py --verbose

Common causes:

  • Running under a Python older than 3.8 (exit code 2, clear message).
  • A read-only runtime/ directory (check permissions).
  • Disk full during extraction.
  • Antivirus blocking a .exe from being written.

Cache corruption

If a download completed but the extracted binary is broken, the cached archive is the suspect. Delete it and force a fresh download: 

> rmdir /s /q runtime\_downloads
> python bootstrap\setup.py --force

On Unix:

$ rm -rf runtime/_downloads
$ python bootstrap/setup.py --force

Backend starts but /php/ returns 500

Check three things:

  1. Does runtime/php/php-cgi.exe exist?
  2. Does runtime/php/php.ini exist?
  3. Does runtime/php/php.exe -m list pdo_sqlite?

If any answer is no, re-run the PHP installer. If all are yes, check the backend log for the exact error and the PHP stderr output.

Launcher reports "run bootstrap first"

The runtime/runtime.env manifest is missing. This happens when the bootstrap never completed successfully, or when the manifest was deleted. Re-run: 

python bootstrap/setup.py

If the components are already installed, the script skips the downloads and only regenerates the manifest — it takes a couple of seconds.

Still stuck?

Capture the full output of --check and setup.py --verbose, and include:

  • Your OS and version (winver, uname -a)
  • The Python version running the bootstrap (python --version)
  • The full contents of runtime/runtime.env, if it exists
  • Any antivirus or corporate proxy in the path
