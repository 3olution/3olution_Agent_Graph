Custom Nodes Cookbook

Reference implementations for eight common agent patterns. Each node combines an LLM call with Python control flow, so the graph editor stops being "prompt → LLM → answer" and starts becoming a small program. Drop demo_agent_patterns.py into backend/graph/custom_nodes/, restart the backend, and each node appears in the palette under Custom Patterns.

Overview

The Agent Graph ships with sixteen built-in node types — inputs, outputs, LLM calls, tool invocations, text operations, control flow, and utilities. Those are the primitives. This cookbook shows what you can build with them by writing custom nodes: small Python functions that register themselves as new node types and appear in the editor's palette.

Every pattern on this page is a composition of existing primitives, packaged as a single reusable node. The graph engine does not care how the function is implemented — it only cares about the signature contract (async def fn(ctx, inputs, params) -> dict). That means anything you can do in Python, you can do inside a node.

The philosophy in one sentence

Built-in nodes are the assembly language; custom nodes are the standard library. When a workflow pattern repeats across multiple graphs — a refinement loop, an ensemble vote, a router that classifies then fans out — promote it to a custom node once, and reuse it forever.

What this cookbook demonstrates

PatternNodeReach for it when…
Sequential follow-up custom.agent_chain You want each LLM turn to see the previous answer — refinement ladders, escalation, multi-step reasoning
Parallel workers custom.agent_pool You have a list of items and want one LLM call per item, in parallel, order preserved
Dynamic routing custom.agent_router The LLM should decide which of up to five downstream branches gets the value
Map custom.map_llm Transform every item in a list via an LLM call; the "map" half of map-reduce
Reduce custom.reduce_llm Combine a list into one answer; the "reduce" half of map-reduce
Iterative quality custom.critique_refine Draft → critique → refine until a score threshold is met
Ensemble voting custom.consensus Ask several models the same question; return the majority answer plus a disagreement score
Structured output custom.json_extract Reliable JSON from any LLM, with self-correction on parse failure

What the nodes do not do

  • They don't pass tools to the LLM. Every internal call uses disable_tools=True. If you need the model to invoke MCP tools mid-turn, use the built-in llm.chat node instead — it exposes a tools input.
  • They don't stream tokens. Each internal LLM call is a non-streaming chat completion. One node = one atomic result. That's exactly what a graph node should be.
  • They don't persist. Every node is stateless. To save a chain's transcript for later, attach a util.log node, or write a small custom.save_to_file node of your own.
  • They don't sandbox. A custom node has the same privileges as the backend process. Don't put subprocess.run(["rm", "-rf", "/"]) in one, and don't accept a custom node from an untrusted source.
Learning by example. Every section on this page ends with a working graph recipe — the actual node parameters, the actual edges, and the actual output you should see. Copy them into the editor to verify that the node is working before adapting it to your own use case.

The nine-line version

If you remember nothing else about custom nodes, remember the shape of the file: 

from ..model import NodeType, Port
from ..registry import register

async def _my_node(ctx, inputs, params):
    return {"result": "whatever"}

register(NodeType(
    name="custom.my_node",
    display="My Node",
    category="Custom",
    fn=_my_node,
))

Drop it in backend/graph/custom_nodes/, restart the backend, and the node appears in the palette. Everything else on this page is elaboration on those nine lines.

Installation

The eight nodes documented here live in a single file, demo_agent_patterns.py. Copy it into the custom nodes folder and restart the backend.

Step 1 — Copy the file

Download or copy the full source from the demo_agent_patterns.py section at the bottom of this page, then:

cp demo_agent_patterns.py backend/graph/custom_nodes/

The folder is created automatically on first backend startup, and it usually already contains example_nodes.py and README.md. If it doesn't exist yet, create it: 

mkdir -p backend/graph/custom_nodes
cp demo_agent_patterns.py backend/graph/custom_nodes/

Step 2 — Restart the backend

python run.py backend

There is no hot reload for custom nodes. The loader runs once at package import, at startup.

Step 3 — Verify the registration

The loader logs one line per custom node module. Search the backend log for: 

INFO | Loaded custom node module: demo_agent_patterns
INFO | Registered 8 custom pattern nodes: agent_chain, agent_pool, agent_router, map_llm, reduce_llm, critique_refine, consensus, json_extract

The second line is the one demo_agent_patterns.py emits at module import — it's an explicit breadcrumb. If you see the first line but not the second, the module imported but something failed before the logger.info(...) at the bottom of the file. Scroll up for a traceback.

Step 4 — Confirm in the palette

Open /graph (or the Graph Editor page in the desktop client). Right-click on the canvas. The categories should include:

What the loader does (and does not do)

BehaviourDetail
Loads *.py files Any module in the folder whose name does not start with _
Skips _*.py Private helpers, disabled modules — rename a module to _demo.py to turn it off without deleting it
Isolates failures A module that raises on import is logged at ERROR level and skipped. Other modules still load.
Disables entirely Set AGENT_LOAD_CUSTOM_NODES=false in .env — useful when a bad node is blocking startup
Is idempotent Python caches imported modules. Re-running the loader does nothing.

Turning individual nodes off

Three options, in increasing order of disruption:

  1. Comment out the register(...) call. The function stays in the file but the node no longer appears in the palette. Good for a temporary disable during development.
  2. Rename the file. Prefix with an underscore: _demo_agent_patterns.py. The loader skips it entirely.
  3. Set the env flag. AGENT_LOAD_CUSTOM_NODES=false disables the whole folder — including example_nodes.py. Use this when something is blocking startup and you need to debug the backend without custom nodes.
Multiple files, one namespace. Node names must be globally unique across all custom node files. If you copy example_nodes.py and edit it without changing the name="..." strings, the second registration silently overwrites the first.

Verifying with a hello-world graph

The simplest possible sanity check: a graph with one input.text, one custom.agent_chain with a single prompt, and one output.text.

  1. Drag input.text onto the canvas. Set its value to "Say hello".
  2. Drag custom.agent_chain onto the canvas. Set prompts to ["{input}"].
  3. Drag output.text onto the canvas.
  4. Connect: input.text.text → agent_chain.initial.
  5. Connect: agent_chain.final → output.text.text.
  6. Click Run.

The result bar shows the model's reply. If it does, the node is working. If the result bar is empty, check the backend log for the LLM call's error message.

The Custom Node Contract

A node type is a small dataclass plus a Python function. The graph engine does not care what the function does internally — it only knows about the signature and the declared ports.

The function signature

async def my_node(ctx, inputs, params) -> dict:
    ...
    return {"output_name": value, ...}
ArgumentTypeWhat it holds
ctx ExecutionContext ctx.app is the shared state dict — {"llm", "mcp", "store", "agent", "llama_server"}. ctx.outputs is the per-node result map from upstream nodes, keyed by node ID.
inputs dict Values from connected upstream nodes, keyed by input port name. A port that has no incoming edge is either missing from the dict or set to None.
params dict The widget values configured on the node itself. Same shape as the params list on the NodeType, but populated with what the user actually typed rather than the defaults.

The return value is a dict keyed by output port name. Every declared output port should have a key in the return value; extra keys are ignored. A missing key means the port is unconnected for that run, which is fine — downstream nodes will just see None.

The NodeType fields

FieldRequiredPurpose
name ✅ Globally unique identifier, conventionally category.subname. The engine matches on this string, so renaming is a breaking change.
display ✅ Label shown in the palette and on the canvas node
category ✅ Palette group. Use "Custom Patterns" here.
fn ✅ The async function above. None is technically allowed (an abstract node), but the engine will not execute it.
description — Tooltip shown in the palette search
inputs — List of Port objects. Defaults to no inputs.
outputs — List of Port objects. Defaults to no outputs.
params — List of Param objects. Defaults to no widgets.
color — Node background. Defaults to a mid-grey. Use a hue that matches the category.

The Port fields

optionalFalseWhether the port can be left unconnected. Purely advisory.

The palette → node → execution lifecycle

1. Backend import time
       └── register(NodeType(...)) stores the type in the registry

2. Graph editor loads
       └── GET /api/graph/litegraph-types returns every registered type
       └── The frontend calls LiteGraph.registerNodeType for each

3. User drags the node from the palette
       └── Node instance created with the widget defaults

4. User configures widgets and connects ports
       └── Node properties and edges stored in the graph's serialised form

5. Click Run
       └── POST /ws/graph → Graph.from_dict() → _topo_sort() → node.fn()

6. Node executes
       └── ctx.app holds the shared state
       └── inputs holds upstream values
       └── params holds widget values
       └── return value stored in ctx.outputs[node_id]
       └── Downstream nodes see it as their inputs

The bare-minimum valid node

Strip everything down to the essentials and you get this. Sixteen lines, one LLM call, one output. 

from ..model import NodeType, Port
from ..registry import register

async def _hello(ctx, inputs, params):
    llm = ctx.app.get("llm")
    if llm is None:
        raise RuntimeError("LLM not available")
    name = str(inputs.get("name") or "world")
    resp = await llm.chat(
        [{"role": "user", "content": f"Say hello to {name}"}],
        disable_tools=True,
    )
    return {"greeting": resp.choices[0].message.content or ""}

register(NodeType(
    name="custom.hello",
    display="Hello",
    category="Custom",
    inputs=[Port("name", "string", optional=True)],
    outputs=[Port("greeting", "string")],
    fn=_hello,
))

That is the entire contract. Every other pattern on this page is an elaboration — loops, asyncio, parsing, retries — all inside the same signature.

The Eight Patterns

Each node below is documented in detail in its own section. This page is the index — one glance, one decision, one reference to the deep dive.

At a glance

Node Shape LLM calls Best for
custom.agent_chain Serial N (one per prompt) Refinement ladders, multi-step reasoning, escalation
custom.agent_pool Parallel N (one per item) Batch processing, per-row enrichment, bulk translation
custom.agent_router Serial 1 (classification only) Ticket triage, intent routing, dynamic fan-out
custom.map_llm Parallel N (one per item) Transform every list element; half of map-reduce
custom.reduce_llm Serial 1 Fold a list into one answer; half of map-reduce
custom.critique_refine Serial loop 2N (critique + refine, until threshold) Writing, code review, anything that benefits from iteration
custom.consensus Parallel N (one per model) Fact-checking, majority-vote answers, disagreement detection
custom.json_extract Serial loop 1 + retries Structured output from any LLM

How to pick one

Do you have a LIST of items?
  ├── Yes → Do you want one result per item or one combined result?
  │         ├── One per item    → custom.map_llm    (or custom.agent_pool)
  │         └── One combined    → custom.map_llm → custom.reduce_llm
  │
  └── No  → Do you want to try DIFFERENT MODELS on the same question?
            ├── Yes → custom.consensus
            └── No  → Do you want ITERATIVE IMPROVEMENT?
                      ├── Yes → custom.critique_refine
                      └── No  → Do you need STRUCTURED OUTPUT?
                                ├── Yes → custom.json_extract
                                └── No  → Do you need DYNAMIC BRANCHING?
                                          ├── Yes → custom.agent_router
                                          └── No  → Do you want MULTI-STEP
                                                    SEQUENTIAL PROMPTS?
                                                    ├── Yes → custom.agent_chain
                                                    └── No  → You probably
                                                              want the built-in
                                                              `llm.chat` node.

What makes a node "worth being a custom node"

The graph engine already has control.foreach, which runs an operation once per list element. Why does custom.map_llm exist then?

Concerncontrol.foreachcustom.map_llm
Sub-node config User must connect a child graph inside the foreach node One prompt template parameter
Concurrency Serial by default Parallel, semaphore-capped
Error handling Stops the whole loop Returns errors list; valid results still usable
Order guarantee Yes (serial) Yes (index-sorted after gather)

The rule of thumb: when a composition of primitives becomes a "shape" that repeats — map, reduce, chain, ensemble — promote it to a custom node with the smallest possible configuration surface. The user gets one node, three widgets, and no wiring.

All eight nodes compose. Any node's output can feed any node's input. Stacking them is the point — a single graph can chain, pool, route, then extract structured JSON, then refine the result, in one linear pipeline. See the Composition recipes section for six worked examples.

Composition Recipes

Six worked examples. Each one is a complete graph you can reproduce in the editor, with node wiring, parameter values, and the expected result.

Recipe 1 — Map-reduce summarisation

Summarise a batch of documents, then combine the summaries into one report. 

input.json ─► custom.map_llm ─► custom.reduce_llm ─► output.text
              (results)         (items ← results)

Node configuration

NodeParameterValue
input.jsonvalue["doc one text…", "doc two text…", …]
(one string per document)
custom.map_llmpromptSummarise this document in 2 sentences: {item}
concurrency4
model(default)
providerauto
custom.reduce_llmreduce_promptCombine these summaries into one report:\n\n{results}
separator\n\n
model(default)

Wiring

input.json.data → custom.map_llm.items
custom.map_llm.results → custom.reduce_llm.items
custom.reduce_llm.result → output.text.text

What happens

  1. input.json parses the array into a Python list.
  2. map_llm fires one LLM call per document, up to 4 at a time. Result order matches input order.
  3. reduce_llm joins the summaries with numbered prefixes and asks the LLM to merge them.
  4. The final text appears in the result bar and on the output.text node.

Timing: with 10 documents and 4-way concurrency, expect roughly ceil(10/4) = 3 rounds — 3× the per-document latency, not 10×.

Recipe 3 — Triage with router + specialised branches

Classify an incoming ticket into one of three categories, then run a different prompt for each category.

input.text ─► router (branch_1 ─► custom.agent_chain (tech flow)   ─┼─► output.text
                └──► branch_2 ─► custom.agent_chain (other flow)   ─┘

Router configuration

- billing

Respond with only the category name.

Ticket: {input}

Each branch's agent_chain

Point each branch at the same custom.agent_chain node but with different prompts. Since only one branch fires per run, the other two chains are skipped silently — None goes into their initial input, but they never run because the graph engine short-circuits on disconnected ports.

Actually, the graph engine does not short-circuit by default — every node runs. To skip unused branches, either (a) run a separate graph per ticket type after the router emits its classification, or (b) use the router's chosen_index output and a control.branch chain. Both are legitimate; the graph editor makes it easy to try either.

Router fallback behaviour. If the LLM returns text that does not contain any branch name, the router falls back to branch_0 and logs a warning. Check the run log if a ticket ends up in the wrong category. Tuning router_prompt to enumerate the exact spelling of each category reduces this dramatically.

Recipe 4 — Ensemble fact-check

Ask three different models the same question. The node returns the majority answer and a 0-1 agreement score. 

input.text ─► custom.consensus ─► output.text
              (prompt)

Node configuration

ParameterValue
modelsllama3.2, qwen2.5, mistral:7b
providerollama
temperature0.7

Prerequisite: all three models must be pulled into Ollama. 

ollama pull llama3.2
ollama pull qwen2.5
ollama pull mistral:7b

What happens

  1. Three LLM calls fire in parallel — one per model.
  2. Each answer is fingerprinted by its first five tokens, lowercased.
  3. The fingerprint with the most matches is the "majority".
  4. Agreement is the fraction of valid responses that voted for the majority.

Reading the output:

  • answer is the majority answer text.
  • agreement ≥ 0.66 means strong consensus — high confidence.
  • agreement ≈ 0.33 means the models disagreed — treat the answer with suspicion.
  • all_responses is the full per-model breakdown for inspection.

Recipe 5 — Structured extraction from email

Turn free-form text into a validated JSON object. 

input.text ─► custom.json_extract ─► output.text
              (text)                  (JSON string)

Node configuration

ParameterValue
schema 
{
  "type": "object",
  "properties": {
    "customer_name": {"type": "string"},
    "order_id": {"type": "string"},
    "amount": {"type": "number"},
    "currency": {"type": "string"}
  }
}
max_retries2
model(default)

What happens

  1. The node sends the extraction prompt with the schema and text.
  2. The model responds with JSON (possibly fenced in markdown).
  3. The node strips any code fence and parses the JSON.
  4. On success: valid=True, data is the parsed object.
  5. On failure: the parse error is appended to the retry prompt, and the call is retried.
  6. After max_retries + 1 failures: valid=False, data=None, errors lists every attempt's reason.

Downstream, you can attach a control.branch on valid to route the success path and the failure path separately.

Recipe 6 — Writing assistant with quality threshold

Draft, grade, improve — repeat until the grade hits 9/10 or the retry budget is exhausted. 

input.text ─► custom.critique_refine ─► output.text
              (task)

Node configuration

ParameterValue
taskWrite a 200-word product description for a noise-cancelling headphone.
quality_threshold9.0
max_iterations3
model(default)

What happens

  1. Iteration 1: generate a first draft from task.
  2. Critique the draft — the response contains SCORE: and ISSUES: lines.
  3. Parse the score. If ≥ 9.0, stop and return.
  4. Otherwise refine with the critique embedded.
  5. Repeat up to max_iterations cycles.

The history output is a list of every iteration, with the draft, the critique text, and the parsed score. Point history at a util.log node to see the whole evolution in the run log, or at output.text for a compact summary.

The threshold is not a guarantee. If the model consistently gives inflated scores, the loop exits after one iteration with the original draft. Consider explicitly asking for a harsh critique in critique_prompt — "Be harsh, find at least three issues" — to spread the score across the 1-10 range more realistically.

Combining recipes

These recipes compose. A realistic graph might:

  1. input.json with a list of customer emails
  2. custom.map_llm to extract structured fields per email (one per item)
  3. custom.reduce_llm to produce a combined report
  4. custom.critique_refine to polish the report to a quality threshold
  5. output.text to display it

That is five nodes, one branch, and zero Python code. The whole pipeline runs on the graph engine, and each step is individually testable by clicking any node and inspecting its output in the result bar.

custom.agent_chain node

Agent Chain (sequential) — follow-up trigger
1 input · 3 outputs

custom.agent_chain

Run a list of prompts one after another. Each prompt sees the previous answer via the {previous} placeholder, which is what makes the "follow-up" pattern work without any loop code in the graph itself.

Ports

DirectionNameTypePurpose
Input initial any The user's original input. Available as {input} in every prompt template.
Output final string The last step's answer.
Output transcript list One entry per step: {step, prompt, response}.
Output steps number How many steps actually ran (matches len(transcript)).

Parameters

NameTypeDefault
system_prompt text ""
prompts json 
["{input}", "Improve this: {previous}"]
modelselect (all.models)""
provider select auto
stop_on_errorbooltrue

Placeholder reference

PlaceholderSubstituted with
{input}The initial input, unchanged for every step
{previous}The previous step's answer (empty string on step 1)
{step}The 1-based step number

When stop_on_error is false

A failed step is recorded in the transcript with "response": "[step N error: …]", and the chain continues. The final answer is the last step that succeeded — or the last failure message if every step failed. Use this when a downstream step can recover from an earlier failure (e.g. "translate, then simplify, then check grammar" where the "check grammar" step can work on the original text if the translation failed).

When to reach for it

  • Refinement ladders. "Draft → critique → rewrite → tighten" is exactly what this node is for.
  • Multi-step reasoning. "Extract facts → deduce consequences → state a conclusion" as three prompts that each see the previous answer.
  • Escalation. "Try a simple reply → if rejected, try a more apologetic one → if still rejected, escalate to a supervisor tone" — the LLM decides which escalation it needs based on {previous}.
  • Few-shot bootstrapping. Chain a "write an example" step, then "write N more like the example" step.

When NOT to reach for it

When the steps are independent. If prompt B does not need prompt A's answer, use custom.agent_pool instead — it runs the calls in parallel and finishes 3-4× faster.

Serial by design. Each step depends on the last, so this node is inherently serial. Three steps at 3 seconds each means 9 seconds total. If that is too slow, either shorten the individual prompts or consider whether the steps really need to be sequential.

Difference from custom.map_llm

Both nodes fire one LLM call per item in parallel. The difference is the output:

agent_poolmap_llm
Results shape List of dicts with {index, item, response, error} List of strings only

In practice: use agent_pool when you want the full per-item metadata; use map_llm when you are going to reduce the results into one answer.

Order is preserved despite parallelism. Even though the LLM calls complete in a non-deterministic order, the node sorts the results back into input order before returning. Downstream nodes see a stable list.

custom.agent_router node

Router (LLM branch) — dynamic fan-out
1 input · 8 outputs

custom.agent_router

Ask the LLM to classify the input into one of up to five named categories, then route the value to the matching output port. This is how you get content-based branching in a graph that otherwise runs deterministically.

Ports

DirectionNameType
Inputinputany
Outputbranch_0any
Outputbranch_1any
Outputbranch_2any
Outputbranch_3any
Outputbranch_4any
Outputchosenstring
Outputchosen_indexnumber
Outputreasonstring

The branch_N outputs are mutually exclusive: only the chosen branch receives the input value. The others are None. This is the routing primitive — attach a different downstream subgraph to each branch, and only the matching one fires.

Parameters

NameTypeDefault
branches text positive,negative,neutral
router_prompt text 
Classify the following input into exactly one of these categories: {branches}.

Respond with only the category name, nothing else.

Input: {input}
modelselect""
providerselectauto

The branches parameter

A comma-separated string of up to five category names. The position in the list determines which output port each one maps to:

branches valuePort mapping
billing,tech,other billing → branch_0
tech → branch_1
other → branch_2

Extra names beyond five are silently truncated. Names with whitespace are stripped. Empty names are ignored.

How the router decides

  1. The {branches} placeholder is replaced with a comma-joined list.
  2. The {input} placeholder is replaced with the input value.
  3. The prompt is sent to the LLM (with temperature=0.0).
  4. The response is lowercased and each branch name is checked as a substring.
  5. The first branch whose name appears in the response wins.
  6. If no branch matches, the node falls back to branch_0 and logs a warning.

Debugging the classification

Point the reason output at a util.log node to see exactly what the LLM said. Common reasons a classification fails:

SymptomCauseFix

The reduce is not a summary

Context window limits. Reduce concatenates every item into one prompt. If the input list is large (say 100 items of 2 KB each), the prompt is 200 KB — likely past the model's context window. The models parameter

Provider settingModel names should be

How voting works

  1. Each model's answer is fingerprinted: lowercased, first five tokens, joined with single spaces.
  2. All valid answers are grouped into buckets by fingerprint.
  3. The bucket with the most members wins.
  4. answer is the first response in the winning bucket (they are usually identical or near-identical).
  5. agreement = winning bucket size / total valid responses.

Reading the agreement score

AgreementInterpretation
1.0 All models gave the same answer. High confidence in the answer.
≥ 0.66 Most models agreed. Reasonable confidence — the outlier is worth inspecting.
≈ 0.5 Split decision. Treat the answer with skepticism.
≤ 0.33 Every model gave a different answer. This is often a fact the models are not confident about.

What fingerprinting does not catch

The fingerprint is a first-five-tokens heuristic, not a semantic comparison. Two answers that mean the same thing but start differently ("The answer is 96" vs. "96 is the answer") will land in different buckets and be treated as disagreements.

This is fine for factual questions with short answers ("What is 12×8?"), and bad for open-ended questions ("Describe the causes of the French Revolution"). For open-ended consensus, consider adding a small reduce step after the node to compare the answers semantically.

Cost and latency

All N model calls fire in parallel — the total latency is the slowest model, not the sum. However, if all models are hosted behind the same rate limit, they may queue.

At 3 models × 200 tokens each, expect ~600 tokens billed per consensus call. Not expensive for occasional use, but noticeable if you put this node in a loop.

The models must be pulled. If a model name is not pulled in Ollama, its call fails and it is excluded from the vote (error populated, no answer). If every model fails, the node returns an empty answer and agreement=0.0.

What "schema" means here

The schema is a JSON Schema document, but the node does not strictly validate against it. It uses the schema as part of the prompt (the LLM is told the schema and asked to fill it), and it validates only that the output parses as valid JSON.

This is a deliberate tradeoff: strict JSON Schema validation requires a library like jsonschema and would reject otherwise-usable output over minor issues (a missing optional field, a number where a string was expected). The practical goal is "parseable JSON, roughly the right shape", not "byte-exact schema conformance".

If you need strict validation, add a downstream custom.validate_json node — or extend json_extract to run the parsed data through a validator before returning.

Bracketing with control.branch

Route the success and failure paths separately: 

       ┌── valid=true  ─► output.text (data)
extract┤
       └── valid=false ─► util.log (errors)  →  custom.critique_refine (retry)

The valid output is a boolean that works directly with control.branch's condition input.

Retry budget sanity. With max_retries=2, that's 3 total attempts. With max_retries=5, that's 6 attempts — usually enough to recover from a stubborn model, but if 6 attempts all fail, the schema is probably wrong, not the model. Check the errors list — if every error is "JSON decode failed", the schema is malformed. If errors vary ("JSON decode failed", "missing required field"), the model is genuinely struggling with the task and a different prompt would help more than more retries.

doc

Design Principles

Ten rules distilled from the eight nodes on this page. They apply to every custom node you write.

1. One node, one job

A node that does two things is two nodes pretending to be one. When "search and download" fails, you don't know which half broke. Split it into search and download, and let the graph editor compose them.

2. Fail with a message, not a silent empty return

If custom.critique_refine gets no task input, it raises ValueError("custom.critique_refine: 'task' input (or param) required"). The engine catches the exception, turns it into a red node-error event, and logs a traceback. The user sees exactly what went wrong.

The alternative — returning {"final": ""} — makes the failure look like a normal empty result. Worse.

Exception: when the failure is per-item and not per-node (like in agent_pool), embed the error in the output dict so other items are not affected. Node-level failures raise; item-level failures are returned.

3. Return JSON-safe values

The engine calls _safe() on every output value before serialising. Anything non-serialisable is stringified. But stringifying is not the same as "returning the right thing" — a datetime object that gets stringified to "2025-01-15 12:34:56" is different from a proper ISO 8601 string with a timezone.

Prefer primitives: str, int, float, bool, None, list, dict. Stringify anything exotic yourself, using a specific format.

4. Cap your concurrency

Any node that spawns parallel LLM calls should use asyncio.Semaphore(n) with an n that defaults to something reasonable (4 is good). Unbounded asyncio.gather() over 100 items will hammer the provider and either rate-limit or crash. 

sem = asyncio.Semaphore(concurrency)

async def run_one(item):
    async with sem:
        return await do_work(item)

results = await asyncio.gather(*[run_one(i) for i in items])

5. Preserve order across parallel calls

asyncio.gather() returns results in the order of the input coroutines — but only if every coroutine returns successfully. If you use return_exceptions=True or you collect results into a dict keyed by index, sort before returning: 

results = sorted(results, key=lambda r: r["index"])

Downstream nodes should not have to care that the work was parallel.

6. Do not stream tokens

A node returns one atomic value. If you need streaming, the built-in llm.chat node already handles it — use that instead of writing a custom node.

The reason: a custom node that streams tokens has to interact with the graph engine's progress events, which complicates the node considerably. Atomic returns keep every custom node simple.

7. Do not pass tools unless you have to

LLM calls without tools are faster, cheaper, and more predictable. Adding tool schemas to every internal call is unnecessary unless the pattern genuinely needs the model to decide to invoke a tool mid-step.

All eight nodes on this page use disable_tools=True. If you write a node that needs tool use, follow the same pattern — pass a disable_tools parameter so users can opt in.

8. Make the widget surface small

Each parameter is a widget the user has to configure. Every added parameter is one more chance to misconfigure the node. Aim for 3-5 widgets per node. When you're tempted to add more, ask whether the extra configuration could be a second node that composes.

9. Follow the naming convention

ThingConvention
Node name custom.category.subname — lowercased, dot-separated
Node display Title Case with a parenthetical hint: "Agent Chain (sequential)"
category Title Case: "Custom Patterns", "Custom", or a use-case label
Port names snake_case, verbs or nouns: prompt, results, valid
Param names snake_case, matching the port names when they represent the same concept
Module filename snake_case.py, plural if it contains multiple related nodes: demo_agent_patterns.py

10. Log once at import

Every module should emit one logger.info(...) line at module scope, after all registrations. This is what tells the user "yes, my module loaded and everything inside registered". 

logger.info(
    "Registered 8 custom pattern nodes: agent_chain, agent_pool, "
    "agent_router, map_llm, reduce_llm, critique_refine, consensus, "
    "json_extract"
)

If the line appears but the nodes are not in the palette, the problem is in the frontend (the /api/graph/litegraph-types response). If the line does not appear, the problem is in the module import — scroll up in the log for the traceback.

Bonus: prefer composition over a bigger node

custom.critique_refine does not internally translate, extract JSON, or call tools. It does exactly one thing — refine until good enough. Everything else is the caller's job.

This is the single most important rule. A node that tries to be everything becomes unmaintainable, unguessable, and untestable. A node that does one thing can be composed with other one-thing nodes to do anything.

Troubleshooting

Every failure mode with a specific fix. If a failure is not listed here, the log message from the backend startup is the next step.

Node does not appear in the palette

  1. Check the backend log for the module name. Search for: 
    INFO | Loaded custom node module: demo_agent_patterns
    If this line is missing, the module was not imported.
  2. Check the filename. Files starting with _ are skipped by the loader. Rename _demo.py → demo.py.
  3. Check the folder. The file must be in backend/graph/custom_nodes/. Not in backend/graph/, not in scripts/.
  4. Check for import errors. Scroll up in the log for a traceback. The loader logs the full exception with logger.exception at ERROR level. Fix the import, restart the backend.
  5. Check the env flag. AGENT_LOAD_CUSTOM_NODES=false disables the whole folder. Unset it and restart.

"RuntimeError: LLM client not available"

The node was called, but ctx.app["llm"] is None. This means the backend started without a working LLM client.

  • Check GET /api/health. The primary_llm block should have a valid base_url and model.
  • Check .env — AGENT_LLM_BASE_URL should point at a running Ollama (or another OpenAI-compatible endpoint).
  • If AGENT_LLM_WARMUP=true, the startup log should contain either "Primary LLM warmup complete" or "Primary LLM warmup failed". If it failed, the endpoint is unreachable.

"LLM call failed" or "timeout"

The node ran, but the LLM call inside it did not complete. Every error message is passed through with the exception text. Common causes:

Message containsCauseFix
Connection refused Ollama or the LLM endpoint is not running Start Ollama (ollama serve) or the remote endpoint
model 'X' not found The model name is wrong or not pulled ollama pull <model> or fix the model name
timed out The model is loading or the request is genuinely slow Increase AGENT_LLM_TIMEOUT in .env
does not support tools The node bypasses tools, but the built-in chat function may still send them Verify disable_tools=True is set in every call
context length exceeded The prompt is too long for the model's context window Shorten the input or reduce max_tokens

"custom.agent_chain: 'prompts' must be a non-empty JSON array"

The prompts parameter is empty, is a plain string instead of a JSON array, or failed to parse. Verify:

  • The param value starts with [ and ends with ].
  • Each element is a quoted string ("...").
  • Commas separate elements — no trailing comma after the last element.

Valid:

["{input}", "Improve this: {previous}"]

Invalid:

"say hello"
{input}, "improve"
["{input}", "Improve this: {previous}",]

"custom.agent_router: branch fallback to branch_0"

The LLM's response did not contain any branch name. Two fixes:

  1. Make the router prompt stricter. Explicitly list the exact spellings: 
    Classify into exactly one of:
  billing
  tech-support
  other

Respond with ONLY the category name. No explanation.
  2. Check the reason output. Point it at a util.log node to see what the LLM actually said. If it said "I classify this as billing", the substring match for "billing" should succeed — if it didn't, there's an issue with the model output encoding.

"custom.critique_refine: 'task' required"

Neither the task input port nor the task parameter has a value. Connect an input.text node to the task input, or fill in the task parameter on the node.

"custom.consensus: 'models' must be a comma-separated list"

The models parameter is empty. Set it to at least two model names: 

llama3.2, qwen2.5

With only one model, the "majority" vote is trivially that model's answer, which defeats the purpose — use a single llm.chat node instead.

All consensus responses failed

Every model in the models parameter failed its call. The all_responses output lists each one's error. Common causes:

  • Some or all model names are not pulled. Check with ollama list.
  • The provider parameter is wrong. If the models are Ollama tags, set provider=ollama. If they are GGUF filenames, you can't use consensus — only one GGUF is loaded at a time.

"All JSON extraction attempts failed"

The errors output lists every parse failure. Read them:

Error patternCause
All errors are "JSON decode failed" The model is not producing valid JSON. Tighten the extract_prompt — explicit "no markdown, no explanation" often helps.
Errors include "unexpected end of string" The response was truncated. Increase max_tokens in the model settings, or reduce the input length.
Errors include "Expecting value: line 1 column 1" The response starts with something other than { or [. The code-fence stripper failed — the model used a different fence style. Check the raw output.
Errors include "invalid schema parameter" The schema parameter itself is not valid JSON. Fix the schema widget.

Node runs but output is empty

The node returned successfully but produced no visible output. Check each output port:

  • final / result / answer — the LLM may have returned an empty string. Check the backend log for the raw response.
  • transcript / results / history — should be a list, not a string. If it's empty, the operation did not run any items.
  • valid / score / agreement — numeric outputs. If they are 0, the parse failed silently.

Quick test: attach a util.log node to the suspect output. The log dock shows the raw value as JSON. That is the ground truth.

The graph hangs on a custom node

If a node takes > 6 minutes and never completes, the stall timer in the frontend is not the issue — the node is stuck. Common causes:

  • LLM call with no timeout. All eight nodes use the standard llm.chat() which respects AGENT_LLM_TIMEOUT (120s default). If you wrote your own node, make sure it uses the same client.
  • Infinite loop. custom.critique_refine has a max_iterations cap. If you wrote a loop without one, the backend is still running it.
  • Deadlock on a semaphore. If you spawn parallel work but the semaphore count is 0 or the tasks block on a resource that never frees, the node hangs forever. Kill the backend and restart.

Removing a broken node

When a custom node is blocking startup and you cannot edit the file:

  1. Rename the folder's offending file to start with _: 
    mv backend/graph/custom_nodes/bad_node.py \
   backend/graph/custom_nodes/_bad_node.py
  2. Or set the escape hatch: 
    AGENT_LOAD_CUSTOM_NODES=false
  3. Restart the backend. It will start without the custom nodes. Fix the file, then reverse the rename or the flag.

Still stuck?

Capture:

  • The output of GET /api/logs/recent?lines=500 — the last 500 log lines usually contain the failure context.
  • The output of GET /api/graph/litegraph-types | jq '.[] | .name' — confirms the node type is registered on the backend side.
  • python -c "import backend.graph.custom_nodes.demo_agent_patterns; print('OK')" — the module imports cleanly in isolation. If this fails, the problem is in the file.

Those three together will pinpoint the failure within one look.

def _decode_model_and_provider(
    raw_model: str | None,
    raw_provider: str | None,
) -> tuple[str | None, str]:
    """Decode the `provider::model` encoding the frontend sends."""
    provider = (raw_provider or "").strip().lower() or "auto"
    model: str | None = None

    raw = (raw_model or "").strip()
    if raw and raw not in ("(default)",):
        if "::" in raw:
            prov_part, model_part = raw.split("::", 1)
            prov_part = prov_part.strip().lower()
            model_part = model_part.strip()
            if prov_part:
                provider = prov_part
            if model_part:
                model = model_part
        else:
            model = raw

    return model, provider


def _get_llm(ctx):
    llm = ctx.app.get("llm")
    if llm is None:
        raise RuntimeError(
            "LLM client not available in app state. "
            "Check the backend startup log — the primary LLM "
            "endpoint may be unreachable."
        )
    return llm


async def _one_chat(
    llm,
    user_content: str,
    *,
    model: str | None,
    provider: str,
    system: str = "",
    temperature: float = 0.0,
) -> str:
    """Single non-streaming LLM call. Returns the assistant text."""
    messages: list[dict] = []
    if system:
        messages.append({"role": "system", "content": system})
    messages.append({"role": "user", "content": user_content})

    resp = await llm.chat(
        messages,
        model=model,
        provider=provider,
        disable_tools=True,
        temperature=temperature,
    )
    msg = resp.choices[0].message
    return msg.content or ""


def _safe_format(template: str, **kwargs: Any) -> str:
    """
    str.format() with a fallback for missing keys.

    A user prompt containing `{unknown_key}` would normally raise
    KeyError. Here it is left verbatim so the LLM sees the literal
    text instead of the whole node failing.
    """
    try:
        return template.format(**kwargs)
    except (KeyError, IndexError):
        return template

#  1. custom.agent_chain — sequential prompts with follow-up
# ══════════════════════════════════════════════════════════════════════

async def _agent_chain(ctx, inputs, params):
    """
    Run a list of prompts in sequence, feeding each answer to the next.

    This is the "follow-up trigger" pattern: every turn has access
    to the previous turn's output, so you can build refine chains,
    multi-step reasoning, or escalation ladders without writing
    any loop code.

    Templates support three placeholders:
        {input}     — the initial input (fixed across all steps)
        {previous}  — the previous step's answer (empty on step 1)
        {step}      — the 1-based step number
    """
    llm = _get_llm(ctx)

    initial = str(inputs.get("initial") or params.get("initial", ""))
    system = str(params.get("system_prompt", ""))
    stop_on_error = bool(params.get("stop_on_error", True))

    # prompts can be a JSON array (recommended) or a single string.
    raw_prompts = params.get("prompts", [])
    if isinstance(raw_prompts, str):
        try:
            raw_prompts = json.loads(raw_prompts)
        except json.JSONDecodeError:
            raw_prompts = [raw_prompts]
    if not isinstance(raw_prompts, list) or not raw_prompts:
        raise ValueError(
            "custom.agent_chain: 'prompts' must be a non-empty "
            "JSON array of strings."
        )

    model, provider = _decode_model_and_provider(
        params.get("model"), params.get("provider"),
    )

    transcript: list[dict] = []
    previous = ""
    for i, tmpl in enumerate(raw_prompts, start=1):
        prompt = _safe_format(
            str(tmpl),
            input=initial,
            previous=previous,
            step=i,
        )

        try:
            answer = await _one_chat(
                llm, prompt,
                model=model, provider=provider, system=system,
            )
        except Exception as exc:
            logger.warning(
                "agent_chain step {} failed: {}", i, exc,
            )
            if stop_on_error:
                raise
            answer = f"[step {i} error: {exc}]"

        transcript.append({
            "step": i,
            "prompt": prompt,
            "response": answer,
        })
        previous = answer

    return {
        "final": previous,
        "transcript": transcript,
        "steps": len(transcript),
    }

#  2. custom.agent_pool — parallel workers over a list
# ══════════════════════════════════════════════════════════════════════

async def _agent_pool(ctx, inputs, params):
    """
    Run a prompt across N items in parallel, bounded by a concurrency
    semaphore.

    Each "agent" is an independent LLM call. The output preserves
    the input order, so downstream nodes see a stable list.
    """
    llm = _get_llm(ctx)

    items = inputs.get("items") or params.get("items", []) or []
    if not isinstance(items, list):
        items = [items]
    if not items:
        return {"results": [], "merged": "", "count": 0, "errors": []}

    prompt_tpl = str(params.get("prompt_template", "{item}"))
    model, provider = _decode_model_and_provider(
        params.get("model"), params.get("provider"),
    )
    concurrency = max(1, int(params.get("concurrency", 4)))
    merge_sep = str(params.get("merge_separator", "\n\n---\n\n"))

    sem = asyncio.Semaphore(concurrency)

    async def run_one(index: int, item: Any) -> dict:
        async with sem:
            prompt = _safe_format(
                prompt_tpl, item=item, index=index,
            )
            try:
                answer = await _one_chat(
                    llm, prompt,
                    model=model, provider=provider,
                )
                return {
                    "index": index,
                    "item": str(item),
                    "response": answer,
                    "error": None,
                }
            except Exception as exc:
                logger.warning(
                    "agent_pool item {} failed: {}", index, exc,
                )
                return {
                    "index": index,
                    "item": str(item),
                    "response": "",
                    "error": str(exc),
                }

    unordered = await asyncio.gather(
        *[run_one(i, it) for i, it in enumerate(items)]
    )
    results = sorted(unordered, key=lambda r: r["index"])

    merged = merge_sep.join(
        r["response"] for r in results if r["response"]
    )
    errors = [r for r in results if r["error"]]

    return {
        "results": results,
        "merged": merged,
        "count": len(results),
        "errors": errors,
    }

#  3. custom.agent_router — LLM-based branching
# ══════════════════════════════════════════════════════════════════════

async def _agent_router(ctx, inputs, params):
    """
    Use the LLM to classify the input into one of up to five branches,
    then route the value to the matching output port.

    Only the chosen branch receives the value; the others receive
    None. Downstream nodes can rely on this — a branch that never
    fires is simply not traversed.
    """
    llm = _get_llm(ctx)

    value = inputs.get("input")
    empty_out = {
        "chosen": "", "chosen_index": -1, "reason": "no input",
        "branch_0": None, "branch_1": None, "branch_2": None,
        "branch_3": None, "branch_4": None,
    }
    if value is None:
        return empty_out

    branches_raw = str(params.get("branches", "positive,negative,neutral"))
    branches = [b.strip() for b in branches_raw.split(",") if b.strip()][:5]
    if not branches:
        raise ValueError(
            "custom.agent_router: 'branches' must be a comma-separated "
            "list of at least one category name."
        )

    router_prompt = str(params.get(
        "router_prompt",
        "Classify the following input into exactly one of these "
        "categories: {branches}.\n\n"
        "Respond with only the category name, nothing else.\n\n"
        "Input: {input}",
    ))
    model, provider = _decode_model_and_provider(
        params.get("model"), params.get("provider"),
    )

    prompt = _safe_format(
        router_prompt,
        branches=", ".join(branches),
        input=value,
    )
    answer = (await _one_chat(
        llm, prompt, model=model, provider=provider, temperature=0.0,
    )).strip()

    chosen_idx = -1
    chosen = ""
    for i, b in enumerate(branches):
        if b.lower() in answer.lower():
            chosen_idx = i
            chosen = b
            break

    # If the LLM refused to pick a branch, fall back to the first so
    # the graph keeps running instead of stalling.
    if chosen_idx == -1:
        chosen_idx = 0
        chosen = branches[0]
        logger.warning(
            "agent_router: LLM response {} did not match any branch; "
            "falling back to '{}'", answer, chosen,
        )

    out = {
        "chosen": chosen,
        "chosen_index": chosen_idx,
        "reason": answer,
    }
    for i in range(5):
        out[f"branch_{i}"] = value if i == chosen_idx else None
    return out

#  4. custom.map_llm — map a prompt over a list
# ══════════════════════════════════════════════════════════════════════

async def _map_llm(ctx, inputs, params):
    """
    Process each item with an LLM call and return a parallel list of
    results.

    This is the "map" half of map-reduce. Combine with
    `custom.reduce_llm` to get the full pattern.
    """
    llm = _get_llm(ctx)

    items = inputs.get("items") or params.get("items", []) or []
    if not isinstance(items, list):
        items = [items]
    if not items:
        return {"results": [], "errors": [], "count": 0}

    prompt_tpl = str(params.get("prompt", "{item}"))
    model, provider = _decode_model_and_provider(
        params.get("model"), params.get("provider"),
    )
    concurrency = max(1, int(params.get("concurrency", 4)))

    sem = asyncio.Semaphore(concurrency)

    async def run(index: int, item: Any) -> tuple[int, str | None, str | None]:
        async with sem:
            try:
                prompt = _safe_format(
                    prompt_tpl, item=item, index=index,
                )
                answer = await _one_chat(
                    llm, prompt,
                    model=model, provider=provider,
                )
                return (index, answer, None)
            except Exception as exc:
                return (index, None, str(exc))

    triples = await asyncio.gather(
        *[run(i, it) for i, it in enumerate(items)]
    )
    triples = sorted(triples, key=lambda t: t[0])

    results: list[Any] = []
    errors: list[dict] = []
    for i, content, err in triples:
        results.append(content if content is not None else "")
        if err:
            errors.append({"index": i, "error": err})

    return {
        "results": results,
        "errors": errors,
        "count": len(results),
    }

#  5. custom.reduce_llm — fold a list into one answer
# ══════════════════════════════════════════════════════════════════════

async def _reduce_llm(ctx, inputs, params):
    """
    Combine a list of results into one answer via an LLM call.

    This is the "reduce" half of map-reduce. It formats the input
    list with numbered prefixes so the LLM can see each item
    distinctly, then asks it to merge them.
    """
    llm = _get_llm(ctx)

    items = inputs.get("items") or params.get("items", []) or []
    if not isinstance(items, list):
        items = [items]
    if not items:
        return {"result": ""}

    reduce_prompt = str(params.get(
        "reduce_prompt",
        "Combine the following items into one coherent summary. "
        "Preserve every distinct point. Do not invent details.\n\n"
        "{results}",
    ))
    model, provider = _decode_model_and_provider(
        params.get("model"), params.get("provider"),
    )
    separator = str(params.get("separator", "\n\n"))

    formatted = separator.join(
        f"[{i + 1}] {item}" for i, item in enumerate(items)
    )
    prompt = _safe_format(
        reduce_prompt,
        results=formatted,
        count=len(items),
    )

    answer = await _one_chat(
        llm, prompt, model=model, provider=provider,
    )
    return {"result": answer}

# ══════════════════════════════════════════════════════════════════════
#  6. custom.critique_refine — iterative refinement
# ══════════════════════════════════════════════════════════════════════

def _parse_score(text: str) -> float:
    """Extract the first 1-10 numeric score from a critique."""
    for line in text.splitlines():
        if "score" in line.lower():
            digits = "".join(
                c for c in line if c.isdigit() or c == "."
            )
            try:
                return float(digits)
            except ValueError:
                return 0.0
    # No SCORE line found — fall back to the first standalone number.
    for word in text.split():
        try:
            return float(word)
        except ValueError:
            continue
    return 0.0


async def _critique_refine(ctx, inputs, params):
    """
    Draft → critique → refine loop.

    Runs up to `max_iterations` cycles. Stops early when the
    critique's score reaches `quality_threshold`.

    If no `draft` is provided, the first iteration generates one
    from the `task`. This makes the node usable either as a
    "start from scratch and iterate" or as "polish this existing
    draft".
    """
    llm = _get_llm(ctx)

    task = str(inputs.get("task") or params.get("task", "")).strip()
    if not task:
        raise ValueError(
            "custom.critique_refine: 'task' input (or param) required"
        )

    current = str(inputs.get("draft") or "").strip()
    system = str(params.get("system_prompt", ""))

    critique_tpl = str(params.get(
        "critique_prompt",
        "Critique the following draft for the task below.\n\n"
        "Task: {task}\n\nDraft:\n{draft}\n\n"
        "Respond in exactly this format, on two lines:\n"
        "SCORE: <a number 1-10>\n"
        "ISSUES: <one specific improvement>\n",
    ))
    refine_tpl = str(params.get(
        "refine_prompt",
        "Task: {task}\n\n"
        "Current draft:\n{draft}\n\n"
        "Critique:\n{critique}\n\n"
        "Produce an improved draft. Output the draft only — no "
        "explanations, no critique, no meta commentary.",
    ))

    model, provider = _decode_model_and_provider(
        params.get("model"), params.get("provider"),
    )
    threshold = float(params.get("quality_threshold", 8.0))
    max_iter = max(1, int(params.get("max_iterations", 3)))

    history: list[dict] = []
    score = 0.0

    for iteration in range(1, max_iter + 1):
        # First iteration with no draft: generate one.
        if not current:
            try:
                current = await _one_chat(
                    llm,
                    f"Complete the following task:\n\n{task}",
                    model=model, provider=provider, system=system,
                )
            except Exception as exc:
                logger.warning(
                    "critique_refine: initial draft generation "
                    "failed: {}", exc,
                )
                return {
                    "final": "",
                    "iterations": 0,
                    "score": 0.0,
                    "history": [],
                    "error": str(exc),
                }

        # Critique
        critique_prompt = _safe_format(
            critique_tpl, task=task, draft=current,
            iteration=iteration,
        )
        try:
            critique = await _one_chat(
                llm, critique_prompt,
                model=model, provider=provider,
            )
        except Exception as exc:
            logger.warning(
                "critique_refine: critique failed at iter {}: {}",
                iteration, exc,
            )
            critique = f"[critique error: {exc}]"

        score = _parse_score(critique)

        history.append({
            "iteration": iteration,
            "draft": current,
            "critique": critique,
            "score": score,
        })

        # Stop early if the score is high enough.
        if score >= threshold:
            logger.info(
                "critique_refine: threshold {} met at iteration {} "
                "(score {})", threshold, iteration, score,
            )
            break

        # Don't refine after the last iteration — we'd never use it.
        if iteration >= max_iter:
            break

        # Refine
        refine_prompt = _safe_format(
            refine_tpl, task=task, draft=current,
            critique=critique, score=score,
        )
        try:
            current = await _one_chat(
                llm, refine_prompt,
                model=model, provider=provider, system=system,
            )
        except Exception as exc:
            logger.warning(
                "critique_refine: refine failed at iter {}: {}",
                iteration, exc,
            )
            break

    return {
        "final": current,
        "iterations": len(history),
        "score": score,
        "history": history,
    }

#  7. custom.consensus — multi-model voting
# ══════════════════════════════════════════════════════════════════════

def _fingerprint(text: str, tokens: int = 5) -> str:
    """Lowercase, first-N-token signature used for majority voting."""
    return " ".join(text.lower().split()[:tokens])


async def _consensus(ctx, inputs, params):
    """
    Ask several models the same question in parallel, then return
    the majority answer and a 0-1 agreement score.

    Majority is determined by the first five tokens of each answer
    (case-insensitive). This is a fast heuristic, not semantic
    voting — but for factual questions ("What is 12×8?") it works
    well because the answer is short and starts with the same word.
    """
    llm = _get_llm(ctx)

    prompt = str(inputs.get("prompt") or params.get("prompt", "")).strip()
    if not prompt:
        raise ValueError(
            "custom.consensus: 'prompt' input (or param) required"
        )

    models_raw = str(params.get("models", ""))
    models = [m.strip() for m in models_raw.split(",") if m.strip()]
    if not models:
        raise ValueError(
            "custom.consensus: 'models' must be a comma-separated "
            "list of model names (e.g. 'llama3.2, qwen2.5, mistral:7b')."
        )

    provider = str(params.get("provider", "auto")).strip().lower() or "auto"
    temperature = float(params.get("temperature", 0.7))

    async def ask(model_name: str) -> dict:
        try:
            answer = await _one_chat(
                llm, prompt,
                model=model_name, provider=provider,
                temperature=temperature,
            )
            return {
                "model": model_name,
                "answer": answer,
                "error": None,
            }
        except Exception as exc:
            return {
                "model": model_name,
                "answer": "",
                "error": str(exc),
            }

    responses = await asyncio.gather(*[ask(m) for m in models])

    valid = [r for r in responses if r["answer"]]
    if not valid:
        return {
            "answer": "",
            "all_responses": responses,
            "agreement": 0.0,
            "majority_count": 0,
        }

    # Count fingerprints.
    buckets: dict[str, list[str]] = {}
    for r in valid:
        key = _fingerprint(r["answer"])
        buckets.setdefault(key, []).append(r["answer"])

    majority_key = max(buckets, key=lambda k: len(buckets[k]))
    majority_answers = buckets[majority_key]
    majority_answer = majority_answers[0]
    agreement = len(majority_answers) / len(valid)

    return {
        "answer": majority_answer,
        "all_responses": responses,
        "agreement": round(agreement, 3),
        "majority_count": len(majority_answers),
    }


register(NodeType(
    name="custom.consensus",
    display="Consensus (multi-model vote)",
    category="Custom Patterns",
    description=(

        "the majority answer plus an agreement score. Useful for "
        "fact-checking, sanity checks, and cross-model ensembles."
    ),
    inputs=[Port("prompt", "string")],
    outputs=[
        Port("answer", "string"),
        Port("all_responses", "list"),
        Port("agreement", "number"),
        Port("majority_count", "number"),
    ],
    params=[
        Param("prompt", "text", "",
              description="Question (used if prompt input is empty)"),
        Param("models", "text", "llama3.2, qwen2.5, mistral:7b",
              description=(
                  "Comma-separated model names to query in parallel."
              )),
        Param("provider", "select", "auto",
              choices=["auto", "ollama", "llama_cpp", "fallback"],
              description=(
                  "Provider applied to every model. Set to 'ollama' "
                  "when the model names are Ollama tags."
              )),
        Param("temperature", "number", 0.7,
              description="Sampling temperature for every model"),
    ],
    color="#2a2a5f",
    fn=_consensus,
))

#  8. custom.json_extract — schema-validated JSON

def _strip_code_fence(text: str) -> str:
    """Remove ```json … ``` fences the LLM may add despite instructions."""
    text = text.strip()
    if not text.startswith("```"):
        return text
    lines = text.split("\n")
    if len(lines) < 2:
        return text
    # Drop the opening fence line.
    lines = lines[1:]
    # Drop the closing fence if present.
    if lines and lines[-1].strip().startswith("```"):
        lines = lines[:-1]
    return "\n".join(lines).strip()


async def _json_extract(ctx, inputs, params):
    """
    Ask the LLM to produce JSON matching a schema, validate the
    result, and retry on parse failure.

    On success: `data` holds the parsed object, `valid` is True.
    On failure: `data` is None, `valid` is False, `errors` lists
    every attempt's failure reason.

    The retry prompt includes the previous parse error so the model
    can correct its mistake — much more reliable than blind retries
    with the same prompt.
    """
    llm = _get_llm(ctx)

    text = str(inputs.get("text") or params.get("text", "")).strip()
    if not text:
        return {
            "data": None,
            "valid": False,
            "errors": ["empty input"],
            "raw": "",
        }

    raw_schema = params.get("schema", "{}")
    if isinstance(raw_schema, str):
        try:
            schema = json.loads(raw_schema)
        except json.JSONDecodeError as exc:
            return {
                "data": None,
                "valid": False,
                "errors": [f"invalid schema parameter: {exc}"],
                "raw": "",
            }
    else:
        schema = raw_schema

    extract_tpl = str(params.get(
        "extract_prompt",
        "Extract structured data from the following text according "
        "to this JSON schema:\n\n{schema}\n\n"
        "Respond with ONLY valid JSON. No markdown fences, no "
        "explanation, no preamble.\n\n"
        "Text:\n{text}",
    ))
    model, provider = _decode_model_and_provider(
        params.get("model"), params.get("provider"),
    )
    max_retries = max(0, int(params.get("max_retries", 2)))

    errors: list[str] = []
    last_raw = ""

    for attempt in range(max_retries + 1):
        prompt = _safe_format(
            extract_tpl,
            schema=json.dumps(schema, indent=2),
            text=text,
        )
        if attempt > 0:
            prompt = (
                f"Previous attempt failed with: {errors[-1]}\n\n"
                f"Try again. Output only valid JSON.\n\n{prompt}"
            )

        try:
            raw = await _one_chat(
                llm, prompt,
                model=model, provider=provider, temperature=0.0,
            )
        except Exception as exc:
            errors.append(f"attempt {attempt + 1}: LLM call failed: {exc}")
            continue

        last_raw = raw
        cleaned = _strip_code_fence(raw)
        try:
            data = json.loads(cleaned)
        except json.JSONDecodeError as exc:
            errors.append(
                f"attempt {attempt + 1}: JSON decode failed: {exc}"
            )
            continue

        return {
            "data": data,
            "valid": True,
            "errors": errors,
            "raw": cleaned,
        }

    return {
        "data": None,
        "valid": False,
        "errors": errors,
        "raw": last_raw,
    }
