MCP Tool Server

A FastMCP-compatible subprocess that exposes a small set of deterministic tools — math, time, filesystem, text — to the agent over the Model Context Protocol. Dropping a new .py file into tools/ is the entire workflow for adding a new capability. The backend spawns this server as a stdio child process and calls its tools through the LLM's function-calling interface.

Overview docs

mcp_server — what it does
doc

Overview

The mcp_server package is a small Python application that implements the Model Context Protocol over stdio. It is not the backend — it is a child process that the backend spawns at startup, and it is not the LLM — it is a collection of pure Python functions that the LLM can request the backend to invoke.

What the server provides

  • A registry of tools (currently nine) that the LLM sees as callable functions during a chat turn.
  • The stdio transport that backend/mcp_client.py connects to.
  • The schema generation — the SDK reads each tool's signature, type hints, and docstring, and produces the JSON schema that the LLM reads.

What the server does not provide

  • No HTTP server. The MCP protocol over stdio is entirely request/response on the child's stdin and stdout.
  • No persistence. Tools are stateless functions. Anything that needs to survive between calls goes into the backend's SQLite store.
  • No LLM client. The server never talks to an LLM. It only answers tool calls from the backend, which is the layer that actually drives the model.
  • No authentication. The stdio transport inherits the backend's process permissions. Anyone who can send a request to the backend can call every tool.

Why a separate process?

Isolation, language freedom, and reusability. See the Architecture section for the full rationale.

Entry points

CommandPurpose
python -m mcp_server Start the stdio server (blocking). Waits for JSON-RPC frames on stdin.
python -m mcp_server.server Same thing.

Architecture

The MCP server runs as a stdio subprocess of the backend. Communication is symmetric JSON-RPC over the child's stdin and stdout — the backend writes requests, the child writes responses.

Why a subprocess?

Running the MCP server as a separate process (rather than embedding it in the backend) provides three advantages:

  1. Isolation. A crashed tool cannot take down the backend. The backend detects the dead subprocess and logs a clear error, but stays up so the user can use chat without tools.
  2. Language freedom. The MCP protocol is language-agnostic. Today the server is Python; tomorrow it could be Node.js or Go, and the backend would not change.
  3. Reusability. The same MCP server can be attached to any other MCP-compatible client — Claude Desktop, Continue, Cursor, etc. — without modification.

Import graph inside the subprocess

server.py

The critical detail is the order: the shared instance must be created before any tool module imports it. That is why server.py imports _server first and tools second.

Transport details

  • Encoding. Newline-delimited JSON-RPC 2.0. One JSON object per line, no length prefix.
  • Buffering. The subprocess writes to stdout with line buffering. The SDK handles this. Do not print to stdout from a tool — it corrupts the stream. Use loguru or sys.stderr instead.
  • Startup. The child must complete its initialization handshake before the backend's session.initialize() returns. If the banner leaks into stdout, this handshake fails (see banner suppression).
Never print to stdout in a tool. The stdout channel is the JSON-RPC transport. A stray print() writes garbage into the middle of a response frame and the backend's SDK raises a parse error. Use loguru (writes to stderr) instead.

SDK Compatibility Shim

The MCP Python SDK renamed its high-level server class between major versions, and — for a while — moved it around between point releases. _server.py tries the newest path first and falls back through the alternatives.

The three import paths

SDK versionClass nameImport path
1.xFastMCPmcp.server.fastmcp
2.x (early)MCPServermcp.server
2.x (current)MCPServermcp.server.mcpserver

The resolution code

_SERVER_CLASS = None

try:
    # mcp >= 2.0 canonical path
    from mcp.server.mcpserver import MCPServer
    _SERVER_CLASS = MCPServer
except ImportError:
    try:
        # Some 2.x point releases exposed it directly
        from mcp.server import MCPServer
        _SERVER_CLASS = MCPServer
    except ImportError:
        try:
            # mcp 1.x fallback
            from mcp.server.fastmcp import FastMCP
            _SERVER_CLASS = FastMCP
        except ImportError as exc:
            raise ImportError(
                "Could not import a supported MCP server class …"
            ) from exc

Why not just pin the SDK?

Pinning is brittle for a project that is meant to run on whatever Python environment the user already has. Users who install with pip install mcp end up with whichever version is current at the time. The shim absorbs the difference so tool code never has to change.

What the tool modules see

Nothing. Every tool module imports from .._server, which is a stable path that does not change between SDK versions: 

from .._server import mcp

@mcp.tool()
def my_tool(x: int) -> int:
    """Docstring."""
    return x * 2

The @mcp.tool() decorator exists on both FastMCP (1.x) and MCPServer (2.x), with the same signature. Tool code is therefore portable across SDK versions with zero modification.

What happens on an unsupported SDK

If none of the three imports succeed, the module raises an ImportError with an actionable message naming every expected import path and pointing at pip install 'mcp>=2.0.0'. This is the only failure mode that prevents the server from starting, and it is loud.

In practice, only the first import runs. Modern installs pull mcp>=2.0.0, so mcp.server.mcpserver.MCPServer resolves on the first try. The fallback chain is a defensive measure, not a hot path.

Windows Event Loop Fix docs

mcp_server/_server.py — platform handling
doc

Windows Event Loop Fix

This is the subtlest part of the whole package. Without it, the MCP handshake fails roughly one time in five on Windows with a "Connection closed" error and no other diagnostics.

The bug

  1. Python 3.8+ on Windows defaults to ProactorEventLoop.
  2. Proactor supports asyncio.create_subprocess_exec but has known bugs reading from child process pipes.
  3. FastMCP's stdio transport continuously reads from its own stdin pipe.
  4. Result: the initial MCP handshake hangs roughly 20% of the time. It looks like a random "Connection closed" error on the backend side.

The fix

Switch to WindowsSelectorEventLoopPolicy before importing the SDK: 

import asyncio
import sys

if sys.platform == "win32":
    asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())

SelectorEventLoop has reliable pipe support. It lacks create_subprocess_exec, but the MCP server does not need that — it only reads and writes to its own stdio.

Why the ordering matters

The policy must be set before the SDK import. Some SDK versions capture the current event loop policy at import time; setting it afterwards has no effect. _server.py enforces the ordering by placing the set_event_loop_policy call above the from mcp... block: 

# ── Windows fix FIRST ─────────────────────────────────────────
if sys.platform == "win32":
    asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())

# ── SDK import SECOND ─────────────────────────────────────────
try:
    from mcp.server.mcpserver import MCPServer
    ...
except ImportError:
    ...

What the user sees without this fix

The backend log shows: 

WARNING | MCP connect attempt 1/2 failed: Connection closed
WARNING | MCP connect attempt 2/2 failed: Connection closed
ERROR   | MCP connection failed after 2 attempt(s).
Hint: run this to see the real error:
    python -m mcp_server.server

Running the server manually produces no error output because the hang is invisible from the child's perspective — it is waiting for data on a pipe that has silently broken.

Interaction with the backend

The backend's event loop policy is set separately in scripts/serve.py. The two processes are independent — each sets its own policy. This is correct: the backend needs Proactor for its own subprocess management, and the MCP server needs Selector for its stdio reads.

The cost of the fix is zero. SelectorEventLoop is not slower for this workload. The only feature it lacks is subprocess creation, which this server never does.

Banner Suppression

Both FastMCP (1.x) and MCPServer (2.x) print a Rich-rendered startup banner to stdout unless told otherwise. That banner contains box-drawing characters that are not valid JSON, and it corrupts the first JSON-RPC frame the backend tries to read.

What the banner looks like

╭─────────────────────────────────────────╮
│                                          │
│   ███╗   ███╗ ██████╗██████╗             │
│   ████╗ ████║██╔════╝██╔══██╗            │
│   ██╔████╔██║██║     ██████╔╝            │
│   ██║╚██╔╝██║██║     ██╔═══╝             │
│   ██║ ╚═╝ ██║╚██████╗██║                 │
│   ╚═╝     ╚═╝ ╚═════╝╚═╝                 │
│                                          │
│   FastMCP 2.0.0                          │
│   The fast, Pythonic way to build MCP …  │
│                                          │
╰─────────────────────────────────────────╯

Why this breaks the handshake

  1. The backend's stdio_client reads the child's stdout line by line, expecting JSON-RPC frames.
  2. The first line it reads is the top of the box (╭────…).
  3. json.loads() raises a decode error.
  4. The SDK treats a malformed frame as a fatal transport error and closes the connection.
  5. The backend logs "Connection closed" — with no reference to the banner, because the banner was already consumed by the parser.

The fix

def run() -> None:
    try:
        mcp.run(show_banner=False)
    except TypeError:
        # Older SDK — fall through to the plain call.
        mcp.run()

show_banner=False suppresses the box on both SDK families. mcp 1.0 does not accept the kwarg and raises TypeError; the fallback accepts the banner. That is a workaround for a specific old version — the server still works, just with a noisy first line that happens not to break the handshake on that version.

The fallback is imperfect. If you are running an SDK that needs the fallback (mcp 1.0) and you see a "Connection closed" error at startup, upgrade with pip install 'mcp>=2.0.0'. The banner suppression works reliably on every version that supports the kwarg.

Detecting the failure

The symptom in the backend log is: 

WARNING | MCP connect attempt 1/2 failed: Connection closed
WARNING | MCP connect attempt 2/2 failed: Connection closed
ERROR   | MCP connection failed after 2 attempt(s).

If you see this on a fresh install, check that the mcp version is at least 2.0.0: 

python -c "import mcp; print(mcp.__version__)"

If the version is older, upgrade. If it is newer and you still see the failure, run the server manually and pipe a request to it to see the raw output: 

python -m mcp_server.server
# In another terminal, the server should sit silent, waiting on stdin.
# If it prints a banner, that is the bug.

Tool Inventory

After the current batch, the MCP server exposes nine tools across four modules. Each one is a plain Python function decorated with @mcp.tool(). The SDK generates its JSON schema from the signature, type hints, and docstring.

math_tools.py

ToolSignatureNotes
add(a: float, b: float) → floatExact IEEE 754 addition
multiply(a: float, b: float) → floatExact IEEE 754 multiplication
sqrt(x: float) → floatRaises ValueError on negative input
power(base: float, exponent: float) → floatSupports fractional and negative exponents

These exist because LLMs are unreliable arithmetic engines. A model that confidently computes 1749 × 2134 in its head will be wrong some of the time; a tool call to multiply(1749, 2134) is always right.

time_tools.py

ToolSignatureReturns
current_time () → str ISO 8601 UTC timestamp, e.g. 2025-01-15T12:34:56.789012+00:00

Models have no internal clock. Without this tool, any question of the form "what time is it" is answered either with a refusal or a hallucinated timestamp.

filesystem_tools.py

ToolSignatureBehaviour
list_directory (path: str = ".") → str Newline-separated, sorted, no type info
read_file (path: str, max_bytes: int = 4096) → str UTF-8 only; truncated at max_bytes
No sandboxing. These tools run with the backend process's privileges. On a single-user machine that is the user's own account, which is fine. On a shared machine, do not expose the backend to untrusted clients without authentication in front of it.

text_tools.py

ToolSignatureReturns
word_count (text: str) → dict {"words": int, "characters": int, "unique_words": int}
shout (text: str) → str Uppercased text

word_count's dict return is stringified to JSON by the SDK. The LLM receives it as a JSON object in the tool result and can index into it by field name.

Schema generation

The SDK reads each tool's name, signature, type hints, and docstring to build the JSON schema that the LLM sees. For example: 

@mcp.tool()
def word_count(text: str) -> dict:
    """
    Count words and characters in a string.
    ...
    """

Becomes approximately: 

{
  "type": "function",
  "function": {
    "name": "word_count",
    "description": "Count words and characters in a string. ...",
    "parameters": {
      "type": "object",
      "properties": {
        "text": {"type": "string"}
      },
      "required": ["text"]
    }
  }
}

Return value handling

Anything a tool returns is converted to text on the way out. Strings pass through unchanged. Numbers, booleans, dicts, and lists are JSON-serialised. The LLM reads the text — it does not receive a typed object.

This means structured returns are convenient but not magical: the model has to parse the JSON back if it wants to index into it. For a simple "does this contain X" question, returning a formatted string is often cleaner than returning a dict.

Loader Pattern

Every non-underscore .py file in mcp_server/tools/ is imported automatically when the tools package is imported. That import triggers load_all(), which iterates the folder and calls importlib.import_module on each candidate.

How it works

def load_all() -> None:
    pkg_dir = Path(__file__).resolve().parent
    loaded = 0
    failed = 0

    for py_file in sorted(pkg_dir.glob("*.py")):
        stem = py_file.stem
        if stem.startswith("_"):
            continue

        module_name = f"{_PACKAGE}.{stem}"
        try:
            importlib.import_module(module_name)
            loaded += 1
        except Exception:
            logger.exception("Failed to load MCP tool module '{}'", stem)
            failed += 1

    if loaded or failed:
        logger.info("MCP tool loader: {} loaded, {} failed", loaded, failed)

Each imported module is expected to do exactly two things:

  1. from .._server import mcp — import the shared instance.
  2. Decorate functions with @mcp.tool() — register them on that instance.

There is no explicit "register" call. The decorator is the registration.

Skipping rules

PatternAction
*.py (top level)Loaded
_*.pySkipped (private helper)
__init__.pySkipped (starts with _)
__pycache__/Skipped (not matched by glob("*.py"))

Failure isolation

Each module is imported inside its own try/except. A module that raises on import — missing dependency, syntax error, bad relative import — logs a full traceback and is skipped. The remaining modules still load.

This is why a broken experimental tool cannot brick the entire server. If a tool file refuses to load, the backend simply sees fewer tools than it expected, and the log tells you which module failed.

Idempotency

load_all() can be called multiple times. Once a module is imported, Python caches it in sys.modules and a subsequent import_module is a no-op. Safe to call from tests.

The same pattern elsewhere in the project

The custom-node loader at backend/graph/custom_nodes/__init__.py uses the identical convention. Learning one means knowing the other:

AspectMCP toolsGraph custom nodes
Foldermcp_server/tools/backend/graph/custom_nodes/
RegistryThe mcp instanceThe registry module
Registration@mcp.tool()register(NodeType(...))
Skip prefix__
Failure handlingLog + continueLog + continue
Env disable(none built-in)AGENT_LOAD_CUSTOM_NODES
No hot reload. Adding a tool file has no effect until the backend is restarted. There is no file watcher in the MCP server. This is intentional: the backend spawns the subprocess once at startup and expects a stable tool list for the lifetime of the process.

Adding a Tool — End to End

A complete walkthrough that adds a new tool to the server. The whole workflow is: write a file, restart the backend, talk to the agent.

Step 1 — Create the module

Create mcp_server/tools/units_tools.py: 

from .._server import mcp

@mcp.tool()
def km_to_miles(km: float) -> float:
    """Convert kilometers to miles (1 km ≈ 0.621371 mi)."""
    return km * 0.621371

Three lines of logic, plus the import and the decorator. That is a complete MCP tool.

Step 2 — Restart the backend

python run.py backend

Step 3 — Watch the log

Look for these lines during startup: 

INFO | Loaded MCP tool module: math_tools
INFO | Loaded MCP tool module: time_tools
INFO | Loaded MCP tool module: filesystem_tools
INFO | Loaded MCP tool module: text_tools
INFO | Loaded MCP tool module: units_tools
INFO | MCP tool loader: 5 loaded, 0 failed
INFO | Spawning MCP server: ... -m mcp_server.server
INFO | MCP session initialised

Five loaded, zero failed. If you see "5 loaded, 1 failed", scroll up for the traceback — the loader logs it at ERROR level.

Step 4 — Ask the agent

In the chat UI: 

How many miles is 5 kilometers?

The agent:

  1. Sends the tool schema for km_to_miles to the LLM as part of the chat request.
  2. Receives a tool_call for km_to_miles(5) in the streaming response.
  3. Invokes the MCP tool with the parsed arguments.
  4. Receives 3.106855 as the tool result.
  5. Sends a second LLM turn with the tool result appended to the conversation.
  6. Answers: "5 kilometers is about 3.1 miles."

What you did not have to touch

  • server.py
  • _server.py
  • tools/__init__.py
  • Any backend file
  • Any frontend file

The auto-loader picked up the new module. The decorator registered the tool. The SDK generated the schema. The backend's tool listing includes it on the next turn.

The rules, condensed

  1. Filename must not start with _. Files starting with underscore are skipped by the loader so you can keep private helpers there.
  2. Import mcp from .._server, not from ..server. The latter triggers a circular import: 
    # ✅ Correct
from .._server import mcp

# ❌ Circular — raises ImportError
from ..server import mcp
  3. Decorate with @mcp.tool(). The decorator is what registers the function. Without it the function is invisible to the LLM.
  4. The docstring is prompt engineering. The LLM reads it to decide when to call the tool. Write it as an instruction: what the tool does, what it needs, what it returns. One line is often enough.
  5. Type hints become parameter types. Use float, int, str, bool, list[str], dict[str, int]. The SDK translates them into JSON schema types.
  6. Return JSON-serializable values. Strings, numbers, booleans, dicts, lists, or None. Anything else gets stringified.
  7. Async functions work too. A tool can be async def and use await — the SDK handles it.
  8. Never print to stdout. That channel is the JSON-RPC transport. Use loguru.

Testing a tool in isolation

Verify a tool module imports cleanly without starting the whole server: 

python -c "import mcp_server.tools.units_tools; print('OK')"

Call a specific tool function directly: 

python -c "
from mcp_server.tools.math_tools import add, sqrt
print(add(2, 3))
print(sqrt(144))
"

The tool functions are ordinary Python functions. The @mcp.tool() decorator attaches metadata but does not change the call signature.

That is the entire workflow. If you can write a Python function, you can add a tool. No registration boilerplate, no configuration file, no schema to hand-write.

Tool Design Guide docs

mcp_server/tools/README.md — design principles
doc

Tool Design Guide

A tool is an instruction to a language model as much as it is a Python function. The name, docstring, and parameter names all end up in the schema the model reads. Small choices in those strings have outsized effects on how reliably the model uses the tool.

One job per tool

search_and_download is worse than search plus download. The model can compose the two simpler tools into the same behaviour, and it has more ways to recover when one step goes wrong.

Fail with a message, not a raise

Return "Error: file not found" rather than raising FileNotFoundError. The model reads the tool result and can try a different path, or tell the user what went wrong. A raised exception becomes a generic "Error calling tool 'read_file': ..." string with the same information but less context for the model to act on.

Exception to the rule: if the failure is a programmer error (bad argument shape, missing dependency), raise. The user needs to see it in the logs, not have the model apologise for it.

Name tools verb-first

add, multiply, read_file, current_time. Consistent with the built-in tools, and easier for the model to select from a list where everything reads as an action.

Keep descriptions short and imperative

One line is often enough: 

"""Convert kilometers to miles (1 km ≈ 0.621371 mi)."""

Long docstrings make the tool schema bigger and slow down every LLM request, without measurably improving the model's decision to call the tool.

Document edge cases

The constraints the model needs to know go into the docstring:

  • "rejects negatives"
  • "returns ISO 8601"
  • "UTF-8 only"
  • "truncates at 4 KB"
  • "path is relative to the project root"

A model that knows the tool rejects negatives will not waste a turn calling it with a negative and then apologising.

Prefer primitives to structured returns

If the answer is a number, return a number. If it is a sentence, return a string. dict and list returns are useful when the caller has to index into them, but for many questions a formatted string is what the user actually wants, and the model will just re-render the JSON anyway.

Keep the tool list small

Every tool appears in every chat request. Twenty tools means the model spends attention choosing between them. A tight set of six or eight well-scoped tools is faster, cheaper, and more accurate than fifty overlapping ones.

Do not do LLM work inside a tool

A tool that itself calls an LLM is a tool that can hang, cost money, and produce non-deterministic results. The MCP server is a deterministic function library; keep it that way. Compose LLM calls at the graph layer (where llm.chat exists) or in a single agent turn.

Cross-check: the built-in tools

ToolDocstring style
add "Add two numbers together. Use this for any arithmetic addition the user asks for. Prefer this over computing in your head."
read_file Documents the max_bytes default, the truncation behaviour, the UTF-8 requirement, and the return type on failure.
current_time Documents the exact return format and tells the model to render it in a friendly format rather than paste the raw ISO string.

The docstrings are longer than the code. That is the point — the docstring is the interface the model sees; the code is an implementation detail.

What is not a tool

These are graph nodes, not MCP tools. They live in backend/graph/nodes.py and backend/graph/custom_nodes/:

  • input.text, input.number, input.json
  • llm.chat, llm.prompt
  • tool.call, tool.list
  • control.branch, control.foreach, control.merge
  • Everything under the "Custom" category

MCP tools are callable by the LLM during a chat, or by the tool.call graph node. Graph nodes are callable by the graph engine. The two registries are separate.

Debugging

A new tool does not appear

Check these in order:

  1. Backend log for the loader line. Look for: 
    INFO  | Loaded MCP tool module: my_tools
INFO  | MCP tool loader: 5 loaded, 0 failed
    If my_tools is not listed, the file name is being skipped or the module failed to import.
  2. File name starts with _? Underscore-prefixed files are skipped by design. Rename it.
  3. Import is from .._server? 
    from .._server import mcp   # ✅
from ..server import mcp    # ❌ circular import
  4. File is in the right folder? mcp_server/tools/, not mcp_server/.
  5. Did you restart the backend? There is no hot reload. Stop and start again.

Testing a module in isolation

python -c "import mcp_server.tools.my_tools"

If that raises, the traceback tells you exactly what is wrong — a typo, a missing import, a syntax error.

Testing a specific tool function

python -c "
from mcp_server.tools.math_tools import add, sqrt
print(add(2, 3))
print(sqrt(144))
"

The tool functions are ordinary Python functions. Calling them directly bypasses MCP entirely.

"Connection closed" at startup

The most common cause is the Rich startup banner leaking into stdout before the first JSON-RPC frame. See the Banner suppression section for the full story.

Second most common cause: a tool module printed to stdout during import. Search your tool files for print(. Every print() in the subprocess corrupts the transport. Replace with logger.info().

"MCP connection failed after 2 attempt(s)"

The subprocess either failed to start or failed to complete its initialization handshake. The backend logs a hint: 

Hint: run this to see the real error:
    python -m mcp_server.server

Run that command directly. If the server starts and sits silently, the problem is on the backend side (see "Connection closed" above). If it prints a traceback, the problem is on the server side — most likely the MCP SDK version.

Checking the SDK version

python -c "import mcp; print(mcp.__version__)"

Anything older than 2.0.0 may need the banner fallback path and is more likely to encounter compatibility issues. Upgrade with: 

pip install 'mcp>=2.0.0'

Watching the raw stdio stream

For low-level debugging, you can pipe a request into the server and see its raw response: 

echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}}' \
    | python -m mcp_server.server

The response is a single JSON line on stdout. If you see a Rich banner before it, the suppression is not working.

A tool raises at runtime

The exception is caught by the SDK and returned to the backend as an error string in the tool result. The model sees it and can react. The backend log shows: 

ERROR | Tool 'my_tool' failed: <exception>

If the failure is deterministic and the tool's own docstring does not warn the model about it, add the constraint to the docstring. That is often more useful than changing the code.

Checking which tools the LLM sees

The backend logs every chat request at DEBUG level: 

DEBUG | LLM request (auto, batch): model=... messages=... tools=N

If tools is 0 and you expect it to be 9, the tool listing failed. Check the backend log for "Failed to list MCP tools" or "MCP session not connected".

No stdout, ever. If debugging the MCP server ever seems impossible, search every file in mcp_server/ for print(. There should be zero hits. This single rule prevents the majority of "the server is silent and the backend says the connection closed" bugs.

"""
Shared MCP server instance.
https://3olution.com

This module owns the global `mcp` object that every tool module
decorates against. It also handles the two compatibility shims that
would otherwise need to be duplicated in every tool file:

    1. The Windows event loop policy fix. On Windows, Python's
       default ProactorEventLoop is incompatible with stdio
       subprocesses; FastMCP will randomly hang during the initial
       handshake. Setting SelectorEventLoopPolicy before importing
       the SDK fixes it.

    2. The mcp 1.x / 2.x class name change. mcp 1.x exposes
       `FastMCP`; mcp 2.x renamed the class to `MCPServer` and
       moved it to `mcp.server.mcpserver`. We try the 2.x import
       first and fall back to 1.x.

================================================================
  WHY A SEPARATE MODULE
================================================================

  Tool modules live in `tools/` and need to import the `mcp`
  instance. If the instance were created inside `server.py`, then
  importing a tool file would trigger a circular import:

        server.py
          imports tools/__init__.py
            imports tools/math_tools.py
              imports server.py  ← circular

  By placing the instance in `_server.py`, the cycle is broken:

        server.py
          imports _server.py       ← OK, no cycles
          imports tools/__init__.py
            imports tools/math_tools.py
              imports _server.py   ← already loaded, fine
"""

from __future__ import annotations

import asyncio
import sys


# ══════════════════════════════════════════════════════════════════════
#  Windows event loop fix
# ══════════════════════════════════════════════════════════════════════
#
#  MUST run before importing the MCP SDK. Python 3.8+ on Windows
#  defaults to ProactorEventLoop, which implements subprocess
#  creation but has known bugs when reading from the subprocess's
#  pipes. FastMCP's stdio transport reads from pipes continuously;
#  Proactor's pipe handling causes the initial handshake to hang
#  roughly 20% of the time.
#
#  SelectorEventLoop has reliable pipe support. It lacks
#  subprocess.create_subprocess_exec, but the MCP server does not
#  need that — it only reads and writes to its own stdio.

if sys.platform == "win32":
    asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())


# ══════════════════════════════════════════════════════════════════════
#  SDK import with 1.x / 2.x compatibility
# ══════════════════════════════════════════════════════════════════════
#
#  The MCP Python SDK renamed its high-level server class between
#  major versions:
#
#      mcp 1.x:  from mcp.server.fastmcp import FastMCP
#      mcp 2.x:  from mcp.server.mcpserver import MCPServer
#
#  Some 2.x point releases also exposed MCPServer directly from
#  mcp.server. We try the newest path first, fall back through the
#  alternatives, and finally accept the 1.x name.

_SERVER_CLASS = None

try:
    # mcp >= 2.0 canonical path
    from mcp.server.mcpserver import MCPServer  # type: ignore[import-not-found]
    _SERVER_CLASS = MCPServer
except ImportError:
    try:
        # Some 2.x point releases exposed it directly
        from mcp.server import MCPServer  # type: ignore[import-not-found,no-redef]
        _SERVER_CLASS = MCPServer
    except ImportError:
        try:
            # mcp 1.x fallback
            from mcp.server.fastmcp import FastMCP  # type: ignore[import-not-found,no-redef]
            _SERVER_CLASS = FastMCP
        except ImportError as exc:
            raise ImportError(
                "Could not import a supported MCP server class from "
                "the installed `mcp` package.\n"
                "Expected one of:\n"
                "    mcp.server.mcpserver.MCPServer    (mcp >= 2.0)\n"
                "    mcp.server.MCPServer              (some 2.x)\n"
                "    mcp.server.fastmcp.FastMCP        (mcp 1.x)\n"
                "Install a supported version with:\n"
                "    pip install 'mcp>=2.0.0'"
            ) from exc


# ══════════════════════════════════════════════════════════════════════
#  The shared instance
# ══════════════════════════════════════════════════════════════════════
#
#  Every tool module does:
#
#      from .._server import mcp
#
#  and then decorates its functions with `@mcp.tool()`. The
#  decorator registers the tool on this instance.

mcp = _SERVER_CLASS("3olution Tools")


# ══════════════════════════════════════════════════════════════════════
#  Entry point
# ══════════════════════════════════════════════════════════════════════

def run() -> None:
    """
    Start the MCP server over stdio.

    Tries `show_banner=False` first. The banner is a Rich-rendered
    box that includes box-drawing characters (╭, │, ╰). Those are
    not valid JSON-RPC and corrupt the first message the client
    reads, causing an immediate "Connection closed" on the backend
    side. Suppressing it is essential on all platforms.

    Older SDK versions (mcp 1.0) do not accept the `show_banner`
    kwarg and raise TypeError. We catch that and call run() without
    arguments — the banner will appear but the server still works.
    """
    try:
        mcp.run(show_banner=False)
    except TypeError:
        # Older SDK — fall through to the plain call.
        mcp.run()

"""
Auto-loader for MCP tool modules.
https://3olution.com

Every non-underscore .py file in this folder is imported when the
tools package is imported. Each tool module is expected to:

    1. Import the shared instance:  from .._server import mcp
    2. Decorate its functions with @mcp.tool()

The decorator registers the tool on the shared instance. There is no
explicit `load()` call — the import of this package does the work.

================================================================
  LOADER BEHAVIOUR
================================================================

  Failures are isolated. If one tool module fails to import (missing
  dependency, syntax error, bad import), the loader logs a full
  traceback and continues loading the remaining modules. The
  backend will see fewer tools than expected, but it will not
  crash.

  This design means a broken experimental tool cannot brick the
  whole server. You can comment out or rename the offending file
  to remove it from the palette.

================================================================
  FILE NAMING CONVENTION
================================================================

  Files whose names start with an underscore (_private.py) are
  skipped. Use this for shared helpers that are not themselves
  tool definitions:

      tools/
          __init__.py         ← this file, auto-runs on import
          README.md           ← documentation
          math_tools.py       ← loaded
          time_tools.py       ← loaded
          text_tools.py       ← loaded
          _helpers.py         ← skipped (leading underscore)
"""

from __future__ import annotations

import importlib
from pathlib import Path

from loguru import logger


_PACKAGE = "mcp_server.tools"


def load_all() -> None:
    """
    Import every tool module in this folder.

    Idempotent: a second call re-imports the same modules, which
    Python's import system treats as a no-op. Safe to call from
    tests.
    """
    pkg_dir = Path(__file__).resolve().parent
    loaded = 0
    failed = 0

    for py_file in sorted(pkg_dir.glob("*.py")):
        stem = py_file.stem

        # Skip __init__.py and any explicitly-private module.
        if stem.startswith("_"):
            continue

        module_name = f"{_PACKAGE}.{stem}"

        try:
            importlib.import_module(module_name)
            logger.info("Loaded MCP tool module: {}", stem)
            loaded += 1
        except Exception:
            logger.exception(
                "Failed to load MCP tool module '{}'. "
                "Skipping — other tool modules will still load.",
                stem,
            )
            failed += 1

    if loaded or failed:
        logger.info(
            "MCP tool loader: {} loaded, {} failed", loaded, failed,
        )


# ══════════════════════════════════════════════════════════════════════
#  Run the loader on package import
# ══════════════════════════════════════════════════════════════════════
#
#  This side effect is what makes `from . import tools` sufficient
#  in server.py. No explicit call needed.

load_all()

"""
Math tools.
https://3olution.com

Basic arithmetic operations. All accept float arguments and return
a float. The LLM calls these for explicit "what is X op Y" questions
where the model wants deterministic arithmetic rather than its own
learned approximations.
"""

from __future__ import annotations

import math

from .._server import mcp


# ══════════════════════════════════════════════════════════════════════
#  Binary operations
# ══════════════════════════════════════════════════════════════════════

@mcp.tool()
def add(a: float, b: float) -> float:
    """
    Add two numbers together.

    Use this for any arithmetic addition the user asks for. Prefer
    this over computing in your head — the result is exact for
    floating-point values.
    """
    return a + b


@mcp.tool()
def multiply(a: float, b: float) -> float:
    """
    Multiply two numbers together.

    Use this for any multiplication the user asks for. The result
    is exact within IEEE 754 double precision.
    """
    return a * b


@mcp.tool()
def power(base: float, exponent: float) -> float:
    """
    Raise `base` to the power of `exponent`.

    Supports fractional and negative exponents (e.g. power(2, 0.5)
    returns sqrt(2), power(2, -1) returns 0.5).
    """
    return base ** exponent


# ══════════════════════════════════════════════════════════════════════
#  Unary operations
# ══════════════════════════════════════════════════════════════════════

@mcp.tool()
def sqrt(x: float) -> float:
    """
    Return the square root of a non-negative number.

    Raises a ValueError for negative inputs — imaginary results are
    not supported. The agent loop turns the raise into an error
    string in the conversation so the model can react.
    """
    if x < 0:
        raise ValueError("sqrt requires a non-negative number")
    return math.sqrt(x)

"""
Text manipulation tools.
https://3olution.com

Simple deterministic text operations. Each tool does one thing and
returns a primitive value, so the LLM can compose them.
"""

from __future__ import annotations

from .._server import mcp


@mcp.tool()
def word_count(text: str) -> dict:
    """
    Count words and characters in a string.

    Returns a dict with three fields:

        words         — number of whitespace-separated tokens
        characters    — total character count including whitespace
        unique_words  — number of distinct lowercased words

    Useful for essay-length checks, content analysis, and any
    question of the form "how many words is this?".
    """
    words = text.split()
    return {
        "words": len(words),
        "characters": len(text),
        "unique_words": len(set(w.lower() for w in words)),
    }

def shout(text: str) -> str:

    Convert the given text to uppercase.

    A trivial but useful demonstration tool: the LLM can call it
    when the user asks to "shout" a message, "yell" a string, or
    anything that maps to uppercasing. It also serves as the
    canonical example of a simple tool for anyone extending the
    server.
    """

mcp_server/tools/filesystem_tools.py

"""
Filesystem tools.
https://3olution.com

Read-only access to the local filesystem. These tools run with the
same privileges as the backend process, which is usually the user's
own account.

================================================================
  SECURITY NOTE
================================================================

  There is NO sandboxing. A user who can reach the chat interface
  can read any file the backend process can read. On a
  single-user machine this is fine. On a shared machine, do not
  expose the backend to untrusted clients without authentication
  in front of it.

  The tools do not support writing, deleting, or moving files. If
  you need those, write a new tool in a separate module and add
  explicit safeguards (allowlisted root directory, size limits,
  path validation).
"""

from __future__ import annotations

import os
from pathlib import Path

from .._server import mcp


@mcp.tool()
def list_directory(path: str = ".") -> str:
    """
    List the entries in a directory.

    The path is interpreted relative to the MCP server's working
    directory, which is the project root when the backend spawns it.

    Returns a newline-separated list of entry names, sorted
    alphabetically. Directories are not distinguished from files in
    the output — the caller can stat individual entries if needed.

    Returns a descriptive error string on failure (permission
    denied, not a directory, does not exist).
    """
    try:
        entries = sorted(os.listdir(path))
    except OSError as exc:
        return f"Error: {exc}"

    if not entries:
        return "(empty directory)"
    return "\n".join(entries)


@mcp.tool()
def read_file(path: str, max_bytes: int = 4096) -> str:
    """
    Read up to `max_bytes` bytes from a text file.

    The path is interpreted relative to the MCP server's working
    directory.

    The byte limit defaults to 4096 (4 KB) and is enforced by
    truncation, not rejection — reading a 10 MB file with the
    default limit returns the first 4 KB. This keeps the LLM's
    context window from being flooded by an accidental large read.

    Returns the decoded UTF-8 text. If the file is not valid UTF-8
    (binary, or a different encoding), returns an error string
    instead of raising.

    Use this to inspect configuration files, logs, source code, or
    any small text file the user asks about.
    """
    p = Path(path)
    if not p.is_file():
        return f"Error: not a file: {path}"

    try:
        data = p.read_bytes()[:max_bytes]
    except OSError as exc:
        return f"Error: {exc}"

    try:
        return data.decode("utf-8")
    except UnicodeDecodeError:
        return "Error: file is not valid UTF-8"

—

MCP Tool Modules

Every .py file in this folder is imported automatically when the MCP server starts. Each module registers its tools by decorating functions with @mcp.tool() against the shared mcp instance.

Adding a tool requires no changes to any other file — just drop a new .py file here and restart the backend.

Minimal example

Create my_tools.py:

from .._server import mcp


@mcp.tool()
def celsius_to_fahrenheit(celsius: float) -> float:
    """Convert a temperature from Celsius to Fahrenheit."""
    return celsius * 9 / 5 + 32

Restart the backend with python run.py backend. The celsius_to_fahrenheit tool is now available to the LLM in chats and callable from a tool.call node in the graph editor.

The rules

  1. File name must not start with _. Files starting with _ are skipped by the loader so you can keep private helpers there.
  2. Import mcp from .._server, not from ..server: 
    from .._server import mcp    # ✅ correct
from ..server import mcp     # ❌ circular import
  3. Decorate each tool with @mcp.tool(). The decorator reads the function's name, signature, type hints, and docstring to build the JSON schema the LLM sees.
  4. The docstring is prompt engineering. The LLM reads it to decide when to call the tool. Write it like an instruction: describe what the tool does, what it needs, and what it returns.
  5. Type hints become parameter types. Use float, int, str, bool, list[str], dict[str, int], etc. FastMCP / MCPServer translates these into JSON schema types automatically.
  6. Return JSON-serializable values. str, int, float, bool, dict, list, or None. Structured returns are stringified in the conversation.
  7. Async functions work too. A tool can be async def and use await — the server handles it.

Tool design tips

  • One job per tool. search_and_download is worse than search + download because the model can compose them.
  • Fail with a message, not a raise. Returning "Error: file not found" lets the model recover. Raising a bare exception produces a generic error the model cannot act on.
  • Name tools verb-first. add, multiply, read_file, current_time — consistent with the built-in tools.
  • Keep descriptions short and imperative. One line is often enough.
  • Document edge cases. "rejects negatives", "returns ISO 8601", "UTF-8 only" — these are the constraints the model needs.

What is NOT a tool

These are graph nodes, not MCP tools. They live in backend/graph/nodes.py and backend/graph/custom_nodes/:

  • input.text, input.number, input.json
  • llm.chat, llm.prompt
  • tool.call, tool.list
  • control.branch, control.foreach, control.merge
  • Everything under the "Custom" category

MCP tools are only callable by the LLM during a chat, or by the tool.call graph node. Graph nodes are only callable by the graph engine. They are separate registries.

Debugging

If a new tool doesn't appear:

  • Check the backend log for Failed to load MCP tool module: … or MCP tool loader: N loaded, M failed.
  • Verify the file name doesn't start with _.
  • Verify the import is from .._server import mcp.
  • Verify the file is in mcp_server/tools/, not mcp_server/.
  • Restart the backend — there is no hot reload.

To test a single module in isolation:

python -c "import mcp_server.tools.my_tools"

If that raises, the traceback tells you exactly what's wrong.

The old way (deprecated)

Before this folder existed, tools were defined inline in mcp_server/server.py. That still works in principle, but adding tools there bloats the file and mixes unrelated concerns. New tools should always go into this folder.

The compatibility shim in _server.py

The mcp Python SDK changed its public API between major versions:

SDK versionClass nameImport path
1.xFastMCPmcp.server.fastmcp
2.x (early)MCPServermcp.server
2.x (current)MCPServermcp.server.mcpserver

_server.py tries the 2.x canonical path first, then the early-2.x alternate, then falls back to 1.x. That means the same tool files work against any currently-installed SDK without modification.

If none of the three imports succeed, the module raises an ImportError with a specific, actionable message naming each expected import path and pointing at pip install 'mcp>=2.0.0'.

The Windows event loop fix

The subtle bug this avoids:

  • Python 3.8+ on Windows defaults to ProactorEventLoop.
  • Proactor supports asyncio.create_subprocess_exec but has known bugs reading from child process pipes.
  • FastMCP's stdio transport continuously reads from its own stdin pipe.
  • Result: the initial MCP handshake hangs ~20% of the time.

Setting WindowsSelectorEventLoopPolicy before importing FastMCP switches to SelectorEventLoop, which has reliable pipe support. The MCP server does not need create_subprocess_exec itself — it only reads and writes its own stdio — so the trade-off is free.

The policy must be set before the SDK import. _server.py enforces this ordering by placing the asyncio.set_event_loop_policy call above the from mcp... import ... block.

The banner suppression

FastMCP 1.x and MCPServer 2.x both print a Rich-rendered startup banner to stdout unless told otherwise. The banner contains box-drawing characters: 

╭─────────────────────────────────────────╮
│                                          │
│   ███╗   ███╗ ██████╗██████╗             │
│   ...

Those characters are not valid JSON. If the banner appears before the first JSON-RPC message, the backend's stdio reader tries to parse it and fails — producing a "Connection closed" error on the backend side and an apparently silent server.

run() calls mcp.run(show_banner=False) to suppress it. Older SDK versions do not accept the show_banner kwarg and raise TypeError; the except TypeError fallback calls plain mcp.run() and accepts the banner.

Loader pattern

The tool loader in tools/__init__.py mirrors the custom-node loader in backend/graph/custom_nodes/__init__.py. Same naming convention, same per-module try/except, same "drop a file and restart" workflow. Learning one means knowing the other. 

tools/
    __init__.py         ← loader, runs at import time
    README.md           ← documentation
    math_tools.py       ← auto-loaded
    time_tools.py       ← auto-loaded
    filesystem_tools.py ← auto-loaded
    text_tools.py       ← auto-loaded
    _helpers.py         ← skipped (leading underscore)
    __pycache__/        ← skipped (not a .py file at the top level)

Adding a new tool — end to end

Create mcp_server/tools/units_tools.py: 

from .._server import mcp

@mcp.tool()
def km_to_miles(km: float) -> float:
    """Convert kilometers to miles (1 km ≈ 0.621371 mi)."""
    return km * 0.621371

Restart the backend:

python run.py backend

Watch the backend log for:

INFO | Loaded MCP tool module: units_tools
INFO | MCP tool loader: 5 loaded, 0 failed
INFO | Spawning MCP server: ... -m mcp_server.server
INFO | MCP session initialised

Ask the chat UI: "How many miles is 5 kilometers?"

The agent will:

  1. send the tool schema to the LLM
  2. receive a tool_call for km_to_miles(5)
  3. invoke the MCP tool
  4. receive 3.106855
  5. answer "5 kilometers is about 3.1 miles."

No changes to server.py, _server.py, tools/__init__.py, or any other file are needed.

Testing a tool in isolation

To verify a tool module imports cleanly without starting the whole server: 

python -c "import mcp_server.tools.math_tools; print('OK')"

To test a specific tool function directly:

python -c "
from mcp_server.tools.math_tools import add, sqrt
print(add(2, 3))
print(sqrt(144))
"

The tool functions are ordinary Python functions. The @mcp.tool() decorator attaches metadata but does not change the call signature.
