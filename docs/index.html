Overview docs

Project root — what this is
doc

Overview

3olution Agent Graph is a full-stack AI agent framework. It combines a FastAPI backend, an MCP tool server, a LiteGraph-based visual workflow editor, and a browser-based chat UI into a single self-contained project. A portable runtime bootstrap means it runs on any machine with a working Python 3.8+ interpreter — no system-wide Python, PHP, or SQLite required.

What the stack does

LayerResponsibility
Python backend Agent loop, LLM routing (Ollama / fallback / llama-cpp), MCP tool integration, graph execution, session persistence
MCP server Deterministic tool provider — math, filesystem, time, text
Web chat UI Browser chat with streaming tokens, thinking blocks, and tool events
Web graph editor LiteGraph.js node editor for building and running agent workflows
Settings page Install llama-cpp-python, manage Ollama models, pull/delete models
PyQt6 desktop Native desktop client with embedded Chromium or native widgets
PHP notes app Server-rendered PHP app served through the Python backend via CGI
SQLite storage Persistent conversation history and graph run archive

Key design principles

  • No build step. The frontend is plain HTML, CSS, and JavaScript. There is no bundler, no transpilation, no framework. What you edit is what the browser runs.
  • Self-contained runtime. bootstrap/setup.py downloads portable Python, PHP, and SQLite into runtime/. Nothing is installed system-wide. Deleting the folder and re-running the bootstrap fully resets the environment.
  • Transport-agnostic event schema. The agent emits the same event dict whether it is delivered over WebSocket, SSE, or batched JSON. Any client that can consume one transport can be swapped for any other without changing the parsing logic.
  • One job per module. Five backend modules (config, state, retry, thinking, storage) import nothing from the rest of the backend. They can be tested in isolation and re-used by the desktop client.
  • Fail loud, fail clearly. Every startup step is best-effort — the backend boots even if the LLM, MCP server, or llama-cpp subprocess is missing. Each failure logs a specific, actionable message rather than a generic "something went wrong".

What is gitignored and why

Every ignored path falls into one of five buckets:

BucketExamplesReason
Generated by bootstrap runtime/ ~300 MB of binaries, re-downloadable
Downloaded at runtime web/vendor/, models/ Network-fetched; large
Written by the app logs/, sessions.db, php_app/data/*.db User data
User-specific .env, .vscode/ Not portable
OS clutter .DS_Store, Thumbs.db Not code

The rule: if a file can be regenerated from source code + .env + bootstrap/setup.py, it goes in .gitignore. See .gitignore for the full file.

Two Workflows docs

Developer vs. end-user installation
doc

Two Workflows

The project ships two independent launcher paths. They run the same backend code; only the Python interpreter differs.

Developer workflow

Uses the Python interpreter already on PATH.

python run.py setup      # create .venv/, install deps
python run.py backend    # start the backend
python run.py desktop    # start the PyQt6 client
python run.py native     # native widgets, no embedded browser
python run.py mcp        # run the MCP server in the foreground
python run.py vendor     # force-refresh LiteGraph files
ProsCons
Familiar virtualenv semantics · fast iteration · no 300 MB download · uses the system Python's site-packages for compilers and dev tools Requires Python 3.10+ on PATH · no PHP or SQLite CLI installed · does not work on a machine without Python

Portable (end-user) workflow

Downloads a self-contained runtime into runtime/.

./setup.sh && ./start.sh         # Linux / macOS
setup.ps1 ; start.bat             # Windows

Or, manually:

python bootstrap/setup.py         # download runtime
python bootstrap/setup.py --check # report what's installed
python bootstrap/setup.py --force # reinstall everything
ProsCons
Zero system dependencies · works from a USB stick · identical across Windows, macOS, and Linux · ships PHP and the SQLite CLI 2–5 minute first-run download (~250 MB) · uses its own private Python, so system-level packages are unavailable

Which one should I use?

ScenarioRecommended
First-time install, want everything to just workPortable
Development on the Python code onlyDeveloper
Shared machine, no admin rightsPortable
Air-gapped environment with a pre-cached runtime/_downloads/Portable
CI runner with a pinned Python already presentDeveloper
You want the PHP notes app to work out of the boxPortable
Both workflows coexist. You can run bootstrap/setup.py to get the portable runtime, and also use python run.py setup with a system Python. They do not conflict — each keeps its own interpreter in a different folder.

Quick Start docs

From zero to running in five steps
doc

Quick Start

1. Clone the repository

git clone https://github.com/3olution/agent-graph.git
cd agent-graph

2. Install the runtime

Portable (recommended for first-time installs):

python bootstrap/setup.py

Developer:

python run.py setup

3. Install and start an LLM

Ollama is the default and is what most users run locally:

ollama pull llama3.2
ollama serve

The backend defaults already point at http://localhost:11434/v1 with model llama3.2, so no .env edits are required.

To use a different OpenAI-compatible endpoint, copy .env.example to .env and set AGENT_LLM_BASE_URL, AGENT_LLM_API_KEY, and AGENT_LLM_MODEL.

4. Start the backend

./start.sh          # Linux / macOS
start.bat           # Windows
python run.py backend   # or, if using the developer workflow

Expected output ends with:

INFO | Backend ready — primary LLM=llama3.2 fallback=(none) llama_cpp=idle php=enabled

5. Open the UI

URLWhat
http://127.0.0.1:8000/Chat UI
http://127.0.0.1:8000/graphGraph editor
http://127.0.0.1:8000/settingsLLM & model management
http://127.0.0.1:8000/php/PHP notes app
http://127.0.0.1:8000/docsAuto-generated API browser

Verify the install

curl http://127.0.0.1:8000/api/health

Expected: a JSON object with "status": "ok" and subsystem fields for LLM, MCP, llama-cpp, PHP, and storage. 

pytest tests/ -v

Expected: 45 tests, all passing, in under a second.

Optional: install llama-cpp-python

Skip this step if you are happy using Ollama. If you want to run GGUF files directly through the backend:

  1. Open http://127.0.0.1:8000/settings.
  2. In the LLM Runtime card, click Show install options.
  3. The dropdown is pre-selected with the wheel recommended for your GPU (based on CUDA detection).
  4. Click Install. pip's output streams live into the log panel.
  5. Restart the backend so the newly installed module is loaded.
  6. Drop a .gguf file into models/ and load it from the chat header's Load GGUF button.
That is the entire setup. The backend, MCP server, web UI, graph editor, settings page, and PHP notes app are all running on a single port. Nothing else needs to be installed.

Module independence

Five modules import nothing from the rest of the backend: config, state, retry, thinking, and storage. They can be tested in isolation, imported by scripts, and re-used by the desktop client without pulling in FastAPI or the OpenAI SDK.

Startup sequence

  1. Logging — loguru console + rotating file sink.
  2. Environment checks — .env, web files, vendor files.
  3. LLMClient — construct three AsyncOpenAI instances (lazy).
  4. SessionStore — open SQLite, create tables.
  5. LlamaServerManager — spawn the llama-server subprocess (best-effort).
  6. MCPClient — spawn the MCP stdio server, initialize the session (best-effort).
  7. Agent — instantiate with the LLM client, MCP client, and store.
  8. Warmup — send a one-token ping to the primary LLM.
  9. Routers — mount the five routers.
  10. Static files — mount web/ at / last.

logs/ folder

Rotating daily log files
1 file ↗ Open full docs

logs/

The rotating daily log directory. Files are written by loguru on both the backend and the desktop client. The folder is committed to git (via a .gitkeep placeholder), but the *.log files themselves are gitignored.

What lives here

FileWritten byLevel
backend-YYYY-MM-DD.log Backend (loguru) DEBUG — startup, LLM requests, tool calls, subprocess output
desktop-YYYY-MM-DD.log Desktop client DEBUG — client lifecycle, forwarded backend lines
.gitkeep Repo Empty placeholder

Rotation and retention

  • Rotation: at midnight UTC.
  • Retention: AGENT_LOG_RETENTION_DAYS days (default 14). Files older than that are deleted automatically at rotation time.
  • Windows-safe: the file sink uses enqueue=True, which routes writes through a background thread. No file-locking conflicts with antivirus scanners.

A FastMCP-compatible stdio subprocess that exposes deterministic tools to the agent over the Model Context Protocol. The backend spawns this server at startup and calls its tools through the LLM's function-calling interface.

The nine built-in tools

ToolSignatureNotes
add(a: float, b: float) → floatExact IEEE 754 addition
multiply(a: float, b: float) → floatExact IEEE 754 multiplication
sqrt(x: float) → floatRejects negative inputs
power(base: float, exponent: float) → floatFractional and negative exponents supported
current_time() → strISO 8601 UTC timestamp
list_directory(path: str = ".") → strSorted newline-separated entries
read_file(path: str, max_bytes: int = 4096) → strUTF-8 only; truncated at max_bytes

shout(text: str) → strUppercases text

Adding a tool

Drop a new .py file into mcp_server/tools/. Restart the backend. The tool appears in the agent's tool list on the next turn. 

from .._server import mcp

@mcp.tool()
def km_to_miles(km: float) -> float:
    """Convert kilometers to miles (1 km ≈ 0.621371 mi)."""
    return km * 0.621371

Two critical rules

  • Import from .._server, not ..server. The latter creates a circular import.
  • Never print to stdout. That channel is the JSON-RPC transport. Use loguru instead.

Fully self-contained portable runtime created and managed by bootstrap/setup.py. Nothing here touches the host system's PATH, registry, or site-packages. The whole folder is safe to delete — the bootstrap recreates it from scratch.

The manifest

runtime.env is a shell-sourceable file that records exactly which binaries were installed and where. The launchers (start.sh / start.bat) source it to find the correct interpreter.

  2. Required substring — LiteGraph in JS, litegraph in CSS. Rejects generic 200 pages that are not the real file.

Why scripts/serve.py and not uvicorn directly?

serve.py handles three things that would otherwise require the user to remember them:

  1. Windows event-loop policy. uvicorn creates the loop at import time, so setting the policy inside backend/main.py is too late.
  2. sys.path for the reloader. On Windows, the reloader child uses multiprocessing spawn, which does not inherit sys.path mutations.
  3. loop="asyncio". uvicorn's auto-detection sometimes picks uvloop, which does not always work with the MCP SDK's stdio transport.

Python version gate

run.py refuses to run on Python < 3.10 with a clear error. The code uses X | Y type hints (3.10+), asyncio.to_thread (3.9+), and pydantic v2 patterns that need a modern interpreter.

Windows Defender note

The .env comments include three fixes for the "Access is denied" error when the backend spawns php.exe:

  1. Unblock the file: Get-ChildItem runtime\php -Recurse | Unblock-File
  2. Add a Defender exclusion: Add-MpPreference -ExclusionPath "$PWD\runtime\php"
  3. Disable PHP entirely: AGENT_PHP_ENABLED=false

The fix_php.bat and fix_php.ps1 scripts automate steps 1 and 2.

Why llama-cpp-python is not listed

It has platform-specific wheels (CPU / CUDA 11.8 / 12.1 / 12.4) that must match the user's GPU drivers. Bundling it would force a source build on machines without a matching wheel, which usually fails. Instead, backend/llama_installer.py detects the GPU and streams the correct pip install from the Settings page.

Version pinning strategy

Pinned to the minor version (>=X.Y.0) rather than the patch version so users get bug fixes and security patches without waiting for a release. Upper bounds are omitted deliberately, except for openai<2.0.0 — that major version changed the streaming delta shape in a way that would require changes to backend/agent.py's _consume_stream().

CONTRIBUTING.md

Development setup

Prerequisites:

  • Python 3.8+ on PATH for the bootstrap
  • Git
  • Optionally a C++ compiler for building packages from source
  • Optionally Ollama for a local LLM endpoint

Code style

Python

  • PEP 8 — four-space indents, snake_case functions, PascalCase classes
  • Type hints on every public function signature
  • from __future__ import annotations at the top of new modules
  • Docstrings on every module, class, and public function
  • ASCII only in comments and identifiers
  • ruff for linting and formatting
  • mypy for static type checking (not required to pass cleanly today)

JavaScript

  • 2-space indentation
  • "use strict"; at the top of every file
  • const and let, never var
  • async / await over .then() chains
  • Template literals for string interpolation
  • No frameworks, no bundler

CSS

  • kebab-case class names
  • CSS custom properties for themeable values
  • Flexbox and grid for layout
  • No CSS frameworks

Commit messages

Short imperative summary on the first line (≤50 chars). Blank line, then a longer explanation wrapped at 72 chars if needed.

Adding a node type

Two options:

  • Built-in node. Edit backend/graph/nodes.py, write an async def _my_node(ctx, inputs, params) -> dict function, register it with a register(NodeType(...)) call. Add tests to tests/test_nodes.py.
  • Custom node. Create backend/graph/custom_nodes/my_nodes.py. Import NodeType, Port, and Param from ..model, and register from ..registry. Register exactly as above. The loader picks up the new file automatically.

Adding an MCP tool

  1. Create a new .py file in mcp_server/tools/. Do not start the name with an underscore.
  2. Import the shared instance: from .._server import mcp.
  3. Decorate a function with @mcp.tool().
  4. Restart the backend.

Rules:

  • Never print to stdout — that channel is the JSON-RPC transport
  • Type hints become the parameter schema
  • Return JSON-serializable values
  • Keep docstrings short and imperative

Pull request checklist

  • Tests pass (pytest tests/ -v)
  • No new ruff warnings
  • Documentation updated if behavior changed
  • CHANGES.md has an entry under [Unreleased]
  • Commit messages are descriptive
  • No secrets in the diff
  • If the frontend changed, all three pages still render correctly
  • If the backend changed, the startup log has no new warnings

Reporting issues

Open an issue at github.com/3olution/agent-graph/issues and include:

  • Environment — OS, Python version, portable or system Python
  • Steps to reproduce
  • Expected vs. actual behavior
  • The last 200 lines of logs/backend-YYYY-MM-DD.log

Security issues

Do not open a public issue for a security vulnerability. Email security@3olution.com instead.

2.0.0 — the critical fixes

  • MCP subprocess "Connection closed" on Windows. AGENT_MCP_SERVER_COMMAND now defaults to sys.executable. The client resolves bare interpreter names to sys.executable, retries connect once with a fresh AsyncExitStack, and wraps Windows .ps1 / .cmd shims in cmd /c.
  • Silent 401 errors when .env is missing. Defaults now point at a local Ollama instance.
  • /graph and /settings returned 404. Explicit HTML routes are now registered before the static mount.
  • LiteGraph vendor files not auto-downloaded. Three layers of automatic download: run.py setup, run.py backend, and the FastAPI lifespan.
  • MCP server crash on older mcp SDK. run() calls mcp.run(show_banner=False) with a try/except TypeError fallback.
  • /favicon.ico 404 log noise. The backend now serves an inline SVG favicon at both /favicon.ico and /favicon.svg.

2.0.0 — what was added

  • Fallback LLM. Optional secondary endpoint for redundancy.
  • Auto-download of LiteGraph vendor files. With two validation gates and a two-mirror fallback chain.
  • Startup diagnostics. The FastAPI lifespan logs the effective configuration; /api/health returns structured state.
  • CONTRIBUTING.md and CHANGES.md.

Upgrade from 1.0.0 to 2.0.0

  1. Back up sessions.db if you have chat history to keep.
  2. Review .env. The fallback variables are new and optional; primary LLM defaults have changed.
  3. Delete web/vendor/ if incomplete. The next backend startup downloads the files automatically.
  4. Restart the backend.

No breaking changes to the HTTP API, WebSocket protocol, graph node schema, or MCP tool interface.

fix_php.bat / fix_php.ps1

A pair of scripts that diagnose and fix PHP execution permissions on Windows. They resolve the most common causes of the WinError 5: Access is denied error that appears when the backend tries to spawn php.exe.

What the script does

  1. Verifies the binary exists and is not suspiciously small.
  2. Removes Mark of the Web (Zone.Identifier ADS) with Unblock-File.
  3. Resets ACLs on runtime/php and php_app using icacls /reset and re-grants the current user full control.
  4. Adds Windows Defender exclusions for both folders and the php.exe process.
  5. Detects third-party antivirus via the Security Center WMI namespace and prints vendor-specific exclusion instructions.
  6. Tests execution by running php.exe --version.

Usage

fix_php.bat                  # run all fixes
fix_php.bat -SkipDefender    # skip Defender exclusion
fix_php.bat -SkipAcl         # skip ACL reset
fix_php.bat -SkipUnblock     # skip Mark of the Web removal
fix_php.bat -NoElevate       # do not prompt for elevation

Self-elevation

The .bat wrapper invokes PowerShell with -ExecutionPolicy Bypass so it runs regardless of the machine's default policy. The .ps1 script self-elevates via UAC when it needs administrator rights (for ACL changes and Defender exclusions).

CodeMeaning
0PHP works. Restart the backend.
1PHP still broken. Follow the printed instructions.
2Needs elevation. Right-click and choose Run as administrator.

test_php.py

Reproduces the exact subprocess call that backend/php_server.py makes, with the same environment, working directory, and arguments. Prints the exact exception class and message when PHP fails to launch.

When to use it

When the /php/ route returns a 500 with a generic error and the backend log does not make the cause obvious. This script isolates the PHP launch from the FastAPI layer so the failure mode is unambiguous.

Run

runtime\python\python.exe test_php.py

What it prints

  • Python interpreter path
  • PHP binary path and size
  • The exact subprocess.run invocation with all CGI environment variables
  • Exit code, stdout, and stderr from PHP
  • The exact exception class and message on failure
