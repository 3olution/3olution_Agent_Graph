Models & Logs Folders

Two runtime folders the backend manages automatically. models/ holds the GGUF weight files the local llama-cpp server loads on demand; logs/ holds the rotating daily log files the backend and desktop client write to. Neither folder is committed to git, but both are documented here so new users know exactly what goes in them and how to fill them.

Overview

The models/ folder holds GGUF weight files for the locally-managed llama-cpp server. It is created on first startup by backend/models_setup.py, and a README is written into it the first time it does not exist. Neither the folder's contents nor its README are committed to git — GGUF files are gigabytes each and are covered by .gitignore.

Do not commit model files. A single 7B Q4_K_M model is roughly 4.5 GB. Git LFS is not configured by default, and even with LFS the repository would be unusable on a fresh clone. Keep the folder empty in version control and drop files in locally.

What lives here

ExtensionPurposeExample
*.gguf Quantized model weights, loaded by llama-cpp llama-3.2-3b.Q4_K_M.gguf
*.gguf (embedding) Optional embedding model for /v1/embeddings bge-m3-Q8_0.gguf
README.md Written automatically on folder creation —
Anything else Ignored by the backend's listing function —

Who owns the folder

backend/models_setup.py is the single owner. It:

  1. Creates the folder on first startup (if it doesn't exist).
  2. Writes the README on first creation.
  3. Lists all .gguf files whenever the settings page or the model picker requests them.
  4. Resolves a model name like "Bonsai-8B.gguf" to an absolute path against this folder.

The model file itself is loaded into memory by the llama-cpp subprocess, which the backend spawns on demand. See backend/llama_server.py for that side of the picture.

Path resolution

resolve_model_path() accepts three shapes of input, tried in order:

  1. An absolute path that already exists as a file → returned as-is.
  2. A path relative to this folder → returned if the file exists.
  3. A path relative to the project root → returned if the file exists.

If none match, the function returns None and the caller produces a clear error. Bare filenames therefore resolve against models/, which is what you want 99% of the time.

Related folder: logs

The logs/ folder is the second runtime folder the backend manages. It is populated by loguru on the first log write — one daily file per process. See the logs folder section below.

Downloading GGUF Files

GGUF files are hosted on Hugging Face. The huggingface-cli tool is the easiest way to fetch them — it handles resume, integrity checks, and large files without timeouts.

Install the CLI

pip install huggingface-hub

Download a model

cd models
huggingface-cli download <repo-id> <filename>.gguf --local-dir .

Example:

huggingface-cli download TheBloke/Llama-2-7B-Chat-GGUF \
    llama-2-7b-chat.Q4_K_M.gguf --local-dir .

The file lands in models/ with the exact filename you passed. Restart the backend (or open the settings page) to see it in the model picker.

Popular model repositories

Llama 3.2 3Bbartowski/Llama-3.2-3B-Instruct-GGUF2.0 GB

Mistral 7BTheBloke/Mistral-7B-Instruct-v0.2-GGUF4.4 GB

Tips

  • Prefer Q4_K_M. It is the balanced default — see Quantization explained.
  • Use --local-dir . from inside models/, so the file lands in the right place without a later move.
  • Match the quant name to the file name. llama-3.2-3b.Q4_K_M.gguf tells you at a glance what you have.
  • Downloads can be paused and resumed. The CLI stores partial downloads in a cache directory and picks up where it left off.

Alternative: Ollama

If you would rather use Ollama's model library, you can skip this folder entirely. Ollama manages its own model storage (usually under ~/.ollama/models) and the backend talks to it via the primary LLM endpoint. The models/ folder is only used by the local llama-cpp server.

Both providers can coexist. The model picker in the chat UI lists Ollama models and local GGUF files side by side, tagged with their provider. You can route individual requests to either one.

Quantization Explained

A quantized model stores its weights at reduced precision. Instead of 16-bit floats (fp16), it uses 4-bit or 8-bit integers with a shared scale factor. This shrinks the file by 4× to 8× and speeds up inference on CPUs, at the cost of a small quality loss.

The suffix table

SuffixBitsQualitySize
Q2_K2LowestSmallest
Q3_K_S3Very low—
Q4_04Low—
Q4_K_M4Balanced — recommended default—
Q5_K_M5Good—
Q6_K6Very good—
Q8_08ExcellentLargest

Q4_K_M is the sweet spot for most users: the quality drop from full precision is minor, and the size is roughly a quarter of the original fp16 model.

What the letters mean

  • Q — quantized. Everything is a Q-something.
  • the number — bits per weight. Higher is larger and better.
  • _K — k-quant method. Uses a mixed scheme where some tensors are stored at higher precision than others. Generally better quality per byte than _0 and _1 variants.
  • _0, _1 — the older "legacy" quant methods. Still produced for compatibility, but _K variants dominate.
  • _S, _M, _L — small, medium, large. A k-quant family like Q4_K comes in these three sizes; Q4_K_M is the medium variant.

Choosing a quant

SituationRecommended
You have plenty of RAM and care about qualityQ6_K or Q8_0
Balanced — the default choiceQ4_K_M
You are tight on RAM or diskQ3_K_S or Q4_0
Absolute smallest, quality is secondaryQ2_K

Does the quant change the chat template?

No. The chat template is a separate concern — it lives in the model's metadata and determines how the prompt is formatted before it reaches the tokenizer. The backend's AGENT_LLAMA_CPP_CHAT_FORMAT setting tells the server which template to expect; it does not depend on the quant.

If a model produces garbage output, the chat template is wrong, not the quant. Common formats:

Model familyChat format
Llama 3.xllama-3
Llama 2llama-2
Mistralmistral
Qwen 2.xqwen
ChatML-based models (Hermes, Phi)chatml

The default is chatml, which works with the majority of current instruction-tuned models. If your model is derived from Llama 3 or Mistral, set the matching format.

Do not mix quants of the same model in the same folder without renaming. The backend resolves model names by filename. Two files with the same name but different content will confuse the model picker. Include the quant suffix in the file name — see Naming & subfolders.

Configuration

The startup model is set in .env at the project root:

AGENT_LLAMA_CPP_ENABLED=true
AGENT_LLAMA_CPP_MODEL=Bonsai-8B.gguf

The AGENT_LLAMA_CPP_MODEL value can be either:

  • A bare filename — resolved against models/.
  • An absolute path — used as-is.
  • A relative path with a subfolder — e.g. chat/llama-3.2-3b.Q4_K_M.gguf.

If the file is not found at startup, the backend logs a warning and continues. The user can load a different model from the settings page or the chat header's Load GGUF button without restarting the backend.

Other llama-cpp settings

VariableDefaultMeaning
AGENT_LLAMA_CPP_ENABLEDtrueEnable the local server subprocess
AGENT_LLAMA_CPP_MODELBonsai-8B.ggufStartup model filename or path
AGENT_LLAMA_CPP_N_CTX8192Context size (tokens)
AGENT_LLAMA_CPP_N_GPU_LAYERS-1GPU layers to offload; -1 = all, 0 = CPU-only
AGENT_LLAMA_CPP_CHAT_FORMATchatmlChat template to use
AGENT_LLAMA_CPP_ALIASlocalModel ID the server advertises
AGENT_LLAMA_CPP_ALLOW_RUNTIME_SWAPtrueAllow loading a different model at runtime

Runtime swap without restart

Even with a configured startup model, the user can switch models at runtime from:

  • The settings page → LLM Runtime section → model dropdown → Load.
  • The chat header's Load GGUF button.
  • A direct API call to POST /api/llama/runtime/load.

Runtime swaps stop the subprocess, start it again with the new model, and wait for readiness. The old model's VRAM is released during the stop, so a swap cannot run out of memory because both models are loaded at once.

Disabling the local server

If you only want to use Ollama or a remote OpenAI-compatible endpoint, set: 

AGENT_LLAMA_CPP_ENABLED=false

The backend will skip the llama-server startup, and the /api/llama/runtime/* endpoints will return 503. The models/ folder is still created (for consistency) but nothing reads from it.

Backend API

Five HTTP endpoints list and manage files in this folder.

MethodPathPurpose
GET/api/llama/runtime/modelsList all .gguf files in this folder
POST/api/llama/runtime/loadSwap the loaded model to a different file
POST/api/llama/runtime/unloadStop the subprocess, freeing VRAM
POST/api/llama/runtime/retryRestart the subprocess with the configured model
GET/api/llama/all-modelsUnified list — Ollama models + local GGUF files

Response shape — /api/llama/runtime/models

{
  "models": [
    {
      "name": "llama-3.2-3b.Q4_K_M.gguf",
      "path": "/abs/path/models/llama-3.2-3b.Q4_K_M.gguf",
      "size": 2012345678,
      "size_gb": 2.01,
      "loaded": false
    }
  ],
  "count": 1,
  "loaded": null,
  "models_dir": "/abs/path/models",
  "runtime_swap_enabled": true,
  "manager_present": true,
  "server_running": false
}

The loaded field is true only for the file the running subprocess actually has in memory. If the server is stopped, every file has loaded: false and the top-level loaded is null.

Response shape — /api/llama/all-models

{
  "models": [
    {
      "id": "ollama::llama3.2",
      "provider": "ollama",
      "model": "llama3.2",
      "display": "Ollama · llama3.2",
      "size_gb": 2.0,
      "loaded": null
    },
    {
      "id": "llama_cpp::llama-3.2-3b.Q4_K_M.gguf",
      "provider": "llama_cpp",
      "model": "llama-3.2-3b.Q4_K_M.gguf",
      "display": "Local GGUF · llama-3.2-3b.Q4_K_M.gguf",
      "size_gb": 2.01,
      "loaded": false
    }
  ],
  "count": 2
}

The id field is the encoded form provider::model that the frontend sends back when the user picks a model. The backend decodes it in LLMClient._resolve().

Loading a model

curl -X POST http://127.0.0.1:8000/api/llama/runtime/load \
     -H 'Content-Type: application/json' \
     -d '{"filename": "llama-3.2-3b.Q4_K_M.gguf"}'

If the server is not running, this starts it. If it is running with a different model, it stops and restarts with the new one. The operation is atomic from the caller's perspective.

Set AGENT_LLAMA_CPP_ALLOW_RUNTIME_SWAP=false to reject these requests with HTTP 403.

Unloading a model

curl -X POST http://127.0.0.1:8000/api/llama/runtime/unload

Stops the subprocess and frees the memory. The model file itself is not deleted — only unloaded.

Extension case sensitivity

The .gguf extension is case-sensitive on Linux and case-insensitive on Windows. The backend's listing function uses glob("*.gguf"), which is case-insensitive on Windows and case-sensitive elsewhere.

To avoid a subtle bug when moving files between platforms, keep the extension lowercase. Files named model.GGUF will list on Windows but not on Linux.

Naming & Subfolders

Use whatever names you like — the backend stores and reports the filename verbatim. The filename is also what the LLM sees when picking a model, so a clear name matters.

Recommended: include the quant and size

models/
    llama-3.2-3b.Q4_K_M.gguf
    qwen2.5-coder-7b.Q4_K_M.gguf
    gemma-2-9b.Q5_K_M.gguf

The pattern <family>-<size>.<quant>.gguf is unambiguous when you come back to the folder in six months. It also sorts alphabetically by model family.

Optional: use subfolders for organization

models/
    chat/
        llama-3.2-3b.Q4_K_M.gguf
    code/
        qwen2.5-coder-7b.Q4_K_M.gguf
    embedding/
        bge-m3-Q8_0.gguf

The backend's listing function does not recurse into subfolders. If you use subfolders, pass the relative path explicitly in AGENT_LLAMA_CPP_MODEL or the load request: 

AGENT_LLAMA_CPP_MODEL=chat/llama-3.2-3b.Q4_K_M.gguf

Trade-off: subfolders vs flat

AspectFlatSubfolders
Appears in model picker✔ immediately✘ must be loaded by path
Easy to scan visually✘ a wall of names✔ grouped by purpose
Works with Load GGUF button✔✔ (path accepted)
Works with AGENT_LLAMA_CPP_MODEL✔ bare name✔ relative path

For most users with two to five models, the flat layout is simpler. Subfolders pay off once you have a dozen or more, or when you want to keep chat and embedding models cleanly separated.

What not to do

  • Do not use spaces in filenames. They work but need quoting everywhere — the .env value, the load request, the CLI. Use dashes or underscores.
  • Do not use uppercase extensions. See Extension case sensitivity.
  • Do not rename after loading. The backend resolves the model name at load time. If you rename the file, the picker will not find it until the file is re-listed.
  • Do not put other file types in this folder. The backend only lists *.gguf. Notes, READMEs, and shell scripts sit alongside but are invisible to the model picker.

The README is overwritten? No.

The README file is written only when the folder is first created. If you edit it, your edits persist — the backend checks if not readme.exists() before writing. You can safely add your own notes.

Disk Space & RAM

Two different numbers matter: the file size on disk, and the memory footprint while the model is loaded. The first is static; the second grows with the context length and with how many layers are offloaded to the GPU.

File sizes on disk

Model sizeQ4_K_MQ8_0
3B params2.0 GB3.4 GB
7B params4.5 GB7.6 GB
13B params7.9 GB13.8 GB
70B params42 GB74 GB

Runtime memory

The llama-cpp server keeps the model weights in RAM (or VRAM) while loaded. On top of that, the KV cache — the attention state for the whole context window — grows with:

  • The context size (AGENT_LLAMA_CPP_N_CTX, default 8192). Doubling the context roughly doubles the cache.
  • The number of GPU layers (AGENT_LLAMA_CPP_N_GPU_LAYERS). Layers offloaded to the GPU consume VRAM; layers left on the CPU consume RAM.

Rough rule for KV cache at 8192 context, 32-layer 7B model: ~500 MB to 1 GB. Bigger contexts and bigger models scale this up linearly.

Practical sizing

Total RAM / VRAMComfortable max
8 GB3B Q4_K_M
16 GB7B Q4_K_M
32 GB13B Q4_K_M, or 7B Q8_0
64 GB+70B Q4_K_M (tight), or 13B Q8_0

These are rough. A GPU with 12 GB VRAM handles a 7B Q4_K_M with most layers offloaded; a CPU-only setup with 16 GB RAM handles the same model at a much slower tokens-per-second.

Reducing the footprint

  • Lower the context: AGENT_LLAMA_CPP_N_CTX=4096 halves the KV cache.
  • Use a smaller quant: Q3_K_S instead of Q4_K_M cuts the file by ~25%.
  • Set N_GPU_LAYERS=0 for CPU-only: all weights in system RAM, no VRAM pressure.
  • Unload when idle: the settings page has an Unload button that frees memory without deleting the file.
Loading is the bottleneck, not inference. The first request to a cold model spends 20–60 seconds reading the file from disk into memory. Once loaded, subsequent requests are much faster. The backend's AGENT_LLM_WARMUP setting sends a one-token ping at startup to move this cost off the first user message.

Verification

After dropping a GGUF file into this folder, confirm the backend has picked it up. Three ways, in increasing order of detail.

1. The settings page

Open /settings and look at the Local GGUF section of the model table. Your file should be listed with its size and a "loaded" indicator.

2. The API directly

curl http://127.0.0.1:8000/api/llama/runtime/models

Expected response:

{
  "models": [
    {
      "name": "llama-3.2-3b.Q4_K_M.gguf",
      "path": "/path/to/models/llama-3.2-3b.Q4_K_M.gguf",
      "size": 2012345678,
      "size_gb": 2.01,
      "loaded": false
    }
  ],
  "count": 1,
  "loaded": null,
  "models_dir": "/path/to/models",
  "runtime_swap_enabled": true,
  "manager_present": true,
  "server_running": false
}

3. The health endpoint

curl http://127.0.0.1:8000/api/health

The llama_cpp block confirms the manager is present and whether the subprocess is running: 

"llama_cpp": {
  "enabled": true,
  "running": false,
  "ready": false,
  "loaded_model": null,
  "base_url": "http://127.0.0.1:8080"
}

What "ready" means

The running field is True when the subprocess exists. The ready field is True when it also answers /v1/models. There is a brief window during startup when running is True but ready is False — the model is still loading.

Testing a load

curl -X POST http://127.0.0.1:8000/api/llama/runtime/load \
     -H 'Content-Type: application/json' \
     -d '{"filename": "llama-3.2-3b.Q4_K_M.gguf"}'

Successful response:

{
  "ok": true,
  "filename": "llama-3.2-3b.Q4_K_M.gguf",
  "path": "/path/to/models/llama-3.2-3b.Q4_K_M.gguf",
  "error": null,
  "previous": "Bonsai-8B.gguf"
}

The previous field shows which model was loaded before the swap. On the first load it is null.

Watching the load in progress

Loading a model takes seconds to minutes depending on size and disk speed. Watch the backend log for: 

INFO | Spawning llama-server (native, model size 2.00 GB,
       port 8080, alias 'local')
INFO | llama-server ready at http://127.0.0.1:8080
       (model=llama-3.2-3b.Q4_K_M.gguf, backend=native, alias=local)

If the load hangs, the log will show subprocess output lines at DEBUG level prefixed with [llama-server].

Troubleshooting docs

models/README.md — common failures
doc

Troubleshooting

SymptomCauseFix
File not listed Extension is not .gguf Rename the file
File listed but load fails File is truncated or corrupted Re-download; check the file size matches upstream
Load hangs at 90% Model is too large for available RAM Choose a smaller quant or a smaller model
unknown pre-tokenizer error AGENT_LLAMA_CPP_CHAT_FORMAT doesn't match the model Set the correct chat format (chatml, llama-2, mistral, qwen, etc.)
Out of memory on load VRAM or RAM insufficient for the chosen layers Set AGENT_LLAMA_CPP_N_GPU_LAYERS=0 for CPU-only, or reduce the number

File not listed at all

First check the extension. The backend's listing function matches glob("*.gguf"), so:

  • model.gguf → listed (Windows and Linux).
  • model.GGUF → listed on Windows, not on Linux.
  • model.ggml → not listed anywhere.
  • model.gguf.backup → not listed anywhere.

If you renamed a file to add .gguf, the old name is gone — the backend reads the current name from readdir on every listing request, so it does not cache.

File listed but load fails

Compare the on-disk size against the size reported on Hugging Face. A common failure is a partial download (interrupted, out of disk space). Re-download the file.

For deeper diagnostics, run the model through the llama.cpp CLI directly:

llama-cli -m models/llama-3.2-3b.Q4_K_M.gguf -p "Hello"

If that fails, the file is bad. If it succeeds, the problem is in the server's command-line flags — check the AGENT_LLAMA_CPP_CHAT_FORMAT and AGENT_LLAMA_CPP_N_CTX settings.

Load hangs near the end

Typically memory pressure. Windows swaps to disk and the load slows to a crawl; Linux triggers the OOM killer and the subprocess dies. Check the backend log for a llama-server exited with code … line.

Fixes, in order of preference:

  1. Use a smaller quant (Q4_K_M instead of Q8_0).
  2. Use a smaller model (3B instead of 7B).
  3. Reduce the context size (AGENT_LLAMA_CPP_N_CTX=2048).
  4. Reduce GPU offload (AGENT_LLAMA_CPP_N_GPU_LAYERS=0) so the weights stay in RAM where the OS can page them.

Unknown pre-tokenizer error

The chat format does not match the model's expected template. The model file itself contains tokenizer metadata, but the server needs to know how to format the prompt before the tokenizer runs.

Set the chat format in .env to match the model family:

AGENT_LLAMA_CPP_CHAT_FORMAT=llama-3

Restart the server (or just unload and reload the model) and the error goes away. Garbage output with no error is the same problem — the model is producing tokens but reading them against the wrong template.

Subprocess crashes on CPU without AVX-512

The llama-cpp-python wheels are compiled with AVX-512 instructions. On a CPU that lacks AVX-512 (Intel 9th gen and older), the first GGML kernel raises STATUS_ILLEGAL_INSTRUCTION (0xC000001D) and the process dies.

The fix is to use a native llama-server.exe binary (compiled with AVX2 or baseline instructions) instead of the Python module. The backend's find_llama_server() prefers the native binary automatically if one is present at runtime/llama-server/.

Download a native binary from github.com/ggml-org/llama.cpp/releases and extract it into runtime/llama-server/. Then restart the backend.

Still stuck?

Capture the output of:

  • GET /api/llama/runtime/models — is the file listed?
  • GET /api/llama/runtime/status — what does the manager think?
  • GET /api/logs/recent?lines=200 — what did the log say during the load?

Those three together usually identify the failure in one look.

The logs Folder

The logs/ folder is the second runtime folder the backend manages. It is populated by loguru on the first log write — one daily file per process. The folder is committed to git (via a .gitkeep placeholder), but the log files themselves are gitignored.

What lives here

FileWritten byContent
backend-YYYY-MM-DD.log Backend (loguru) Everything at DEBUG level: startup, LLM requests, tool calls, subprocess output
desktop-YYYY-MM-DD.log Desktop client (loguru) Desktop client lifecycle, window state, forwarded backend lines
.gitkeep Repo maintainers Empty placeholder so git tracks the folder

Rotation & retention

  • Rotation: at midnight UTC. The current day's file is named backend-2025-01-15.log; at 00:00 UTC a new file backend-2025-01-16.log starts and the old one is closed.
  • Retention: AGENT_LOG_RETENTION_DAYS days (default 14). Files older than that are deleted automatically by loguru at rotation time.

Level configuration

SinkLevelSetting
Console (stderr)INFOAGENT_LOG_LEVEL
File (this folder)DEBUGAGENT_LOG_FILE_LEVEL

The file sink captures everything — including the debug lines that would be noise on the console. This is by design: a bug report from a user can be diagnosed from the file without asking the user to re-enable verbose logging.

Safe on Windows

The file sink uses enqueue=True, which routes every log write through a background thread. This avoids the classic Windows issue where an antivirus scanner holds the file open while Python tries to rotate it. It also means logging never blocks the asyncio event loop.

Some lines may be lost on SIGKILL. If the process is killed with SIGKILL (or Ctrl+Break on Windows), lines still in the enqueue queue are lost. This is acceptable — the alternative is synchronous file writes on every log line, which is a significant performance cost on the hot path.

Viewing the logs

MethodCommand
Desktop clientView menu → View Logs… (Ctrl+L)
BrowserGET /api/logs/recent?lines=500&source=all
Terminal (Unix)tail -f logs/backend-*.log
Terminal (Windows)Get-Content logs\backend-*.log -Wait -Tail 50

Log file structure

Every line has the same format:

2025-01-15 12:34:56.789 | INFO     | backend.llm:142 — LLM request (auto, batch): model=llama3.2 messages=3 tools=9

The fields are:

  • Timestamp — millisecond precision, UTC.
  • Level — DEBUG, INFO, WARNING, ERROR.
  • Module:line — where the log call originated.
  • Message — the actual text.

Grep is your friend:

grep ERROR logs/backend-*.log
grep "llama-server" logs/backend-2025-01-15.log
grep "tool '" logs/backend-*.log

Making the file sink read-only

If the folder cannot be created (read-only filesystem, permission denied), the file sink is skipped and a warning is logged at the console level. The backend continues with console-only logging. This matches the desktop client's behaviour.

Disabling file logging

AGENT_LOG_TO_FILE=false

Set this in .env to disable the file sink entirely. Useful in containerized deployments where logs are collected from stdout instead.

3. Lists all `.gguf` files whenever the settings page or the model

4. Resolves a model name like `"Bonsai-8B.gguf"` to an absolute path

The model file itself is loaded into memory by the

demand.

---

## Downloading models

GGUF files are hosted on [Hugging Face](https://huggingface.co).

Configuring
The startup model is set in .env:

env
AGENT_LLAMA_CPP_ENABLED=true
AGENT_LLAMA_CPP_MODEL=Bonsai-8B.gguf
The value can be either:

A bare filename — resolved against this folder.

An absolute path — used as-is.

If the file isn't found at startup, the backend logs a warning and
continues. The user can load a different model from the settings
page or the chat header's Load GGUF button without restarting the
backend.

Backend API
The following endpoints list and manage files in this folder:

Method	Path	Purpose
GET	/api/llama/runtime/models	List all .gguf files
POST	/api/llama/runtime/load	Swap the loaded model
POST	/api/llama/runtime/unload	Stop the subprocess
POST	/api/llama/runtime/retry	Restart the subprocess
GET	/api/llama/all-models	Unified list (Ollama + GGUF)
The .gguf extension is case-sensitive on Linux and case-insensitive
on Windows. The backend's listing function uses glob("*.gguf"),
which is case-insensitive on Windows and case-sensitive elsewhere. To
avoid a subtle bug when moving files between platforms, keep the
extension lowercase.

Naming conventions
Use whatever names you like — the backend stores and reports the
filename verbatim. Two suggestions for multi-model setups:

Include the quant and size:

text
llama-3.2-3b.Q4_K_M.gguf
qwen2.5-coder-7b.Q4_K_M.gguf
Use subfolders for organization:

text
models/
    chat/
        llama-3.2-3b.Q4_K_M.gguf
    code/
        qwen2.5-coder-7b.Q4_K_M.gguf
The backend's listing function does not recurse into subfolders.
If you use subfolders, pass the relative path explicitly in
AGENT_LLAMA_CPP_MODEL or the load request:

env
AGENT_LLAMA_CPP_MODEL=chat/llama-3.2-3b.Q4_K_M.gguf

loaded, and KV cache usage grows with context length.

Troubleshooting
Symptom	Cause	Fix
File not listed	Extension is not .gguf	Rename the file
File listed but load fails	File is truncated or corrupted	Re-download; check the file size matches upstream
Load hangs at 90%	Model is too large for available RAM	Choose a smaller quant or a smaller model
unknown pre-tokenizer error	AGENT_LLAMA_CPP_CHAT_FORMAT doesn't match the model	Set the correct chat format (chatml, llama-2, mistral, qwen, etc.)
Out of memory on load	VRAM or RAM insufficient for the chosen layers	Set AGENT_LLAMA_CPP_N_GPU_LAYERS=0 for CPU-only, or reduce the number
