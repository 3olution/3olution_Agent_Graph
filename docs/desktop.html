Desktop Client

Two PyQt6 frontends backed by the same HTTP/WebSocket API as the web UI. desktop.app wraps the web UI in a native window using embedded Chromium (QWebEngineView); desktop.native_chat is a pure-QtWidgets fallback for environments without WebEngine. A shared BackendLauncher spawns and monitors the FastAPI subprocess, a native installer dialog handles llama-cpp wheel selection, and loguru writes a separate desktop-*.log stream.

Why two frontends?

Rebuilding the entire web UI — chat with streaming, graph editor, settings page, Ollama model management, PHP notes app — in native QtWidgets would double the maintenance burden for zero functional gain.

desktop.app sidesteps that by embedding the actual web UI inside a QWebEngineView. The result is a native-looking window (menu bar, toolbar, status bar, dock) with a single source of truth for the UI. When the web team adds a feature, the desktop client gets it for free.

desktop.native_chat exists for the environments where that strategy does not work: headless build machines, minimal Linux distributions that cannot install PyQt6-WebEngine, and the occasional user who simply prefers native widgets.

In desktop.app, this flow happens inside the embedded Chromium process — the same JavaScript that runs in a browser. In desktop.native_chat, the flow is driven by AgentWorker (a QThread) which reads the SSE stream and emits each parsed event as a Qt signal to the main thread.

Zero duplicated backend logic. Both desktop frontends and the web UI talk to the exact same FastAPI routes. The launcher spawns the same scripts/serve.py the terminal uses. There is no desktop-specific backend code.

Graceful WebEngine fallback

If PyQt6.QtWebEngineWidgets cannot be imported, desktop.app does not crash. It catches the ImportError, sets WEBENGINE_AVAILABLE = False, and installs a NoWebEngineWidget as the central widget instead.

The window still opens, the menu bar still works, the status bar still polls /api/health, and the log dock still receives backend output. Only the embedded browser view is missing — and the widget offers a button to open the UI in the system browser.

The import is guarded at the top of app.py. Three names are set to None when the import fails: QWebEngineView, QWebEngineSettings, and QWebEngineProfile. Every use site checks WEBENGINE_AVAILABLE first.

Two design decisions worth highlighting

1. Attach-first semantics

The launcher first checks whether a backend is already running at the configured URL. If one is found, it attaches to it instead of spawning a duplicate.

This makes it possible to develop against uvicorn --reload in a terminal and launch the desktop client separately without a port conflict, without a confusing "address already in use" error, and without two processes fighting over the same SQLite file.

2. The spawned_by_us flag

Only processes the launcher itself started are terminated on close. An externally-started backend is deliberately left running, because the user's terminal session controls its lifecycle.

The main window reads this flag in _stop_backend() and in closeEvent(). When the flag is False, the close prompt is skipped and a message box explains that the backend must be stopped from its own terminal.

Signals

SignalEmitted when
started() The backend answers /api/health with a 200 response. Fires once per lifecycle.
stopped() The subprocess has exited cleanly, either because the user requested a stop or because the process finished on its own.
failed(str) Startup failed or the subprocess exited unexpectedly. The string carries a human-readable reason.
log(str) One line of subprocess stdout or stderr. Fires on the reader thread.

Interpreter resolution

The subprocess must run with an interpreter that has the backend dependencies installed. The resolution order is:

  1. .venv/Scripts/python.exe on Windows, .venv/bin/python on Unix. This path exists when the developer ran python run.py setup.
  2. sys.executable — the interpreter running the desktop client. This is the fallback that works in packaged builds where the interpreter is bundled inside the PyInstaller archive.

Command construction

The launcher prefers scripts/serve.py because that script handles the Windows event-loop policy and the sys.path fixups the backend needs. If serve.py is missing, it falls back to a direct python -m uvicorn backend.main:app invocation. 

# Preferred
python scripts/serve.py

# Fallback
python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000

Process tree termination

Uvicorn spawns child processes for reload mode, and the MCP server and llama-cpp server are their own subprocesses. Plain Popen.terminate() leaves orphans behind.

The launcher uses a platform-conditional strategy:

PlatformMethod
Windows taskkill /F /T /PID <pid> — kills the entire process tree, including grandchildren.
Unix SIGTERM first, wait 5 s, then SIGKILL if the process is still alive.

Stop-all vs stop

Two distinct shutdown paths exist:

ActionWhat it does
stop() Terminates the subprocess tree directly. Used on close and from the Stop Backend menu action.
stop_all_async() First calls POST /api/system/stop-all so the backend can shut down the MCP and llama-cpp children gracefully, then waits 1.2 s, then force-kills the tree if it is still alive. Bound to Ctrl+Shift+Q.
Startup timeout is 60 seconds. The health endpoint responds as soon as uvicorn binds the port — it does not wait for the LLM to warm up. If the backend has not answered in 60 s, something is wrong. The failure dialog shows the last 40 lines of backend output to help diagnose.

install_dialog.py — pip streaming without a browser

The web settings page has its own installer UI. The native dialog exists for two cases:

  1. Users of desktop.native_chat, who never load the web UI.
  2. Users who prefer a native file dialog for pip's wheel choice.

Crucially, both UIs talk to the same backend endpoints: 

GET  /api/llama/install/status     — install state + recommendation
POST /api/llama/install/install    — pip install    (SSE)
POST /api/llama/install/uninstall  — pip uninstall  (SSE)

How the dialog works

1. Status detection

On construction, the dialog GETs /api/llama/install/status. The backend runs detect_llama_cpp() and recommend_wheel_index() — the same logic the web UI uses — and returns: 

{
  "installed": true,
  "version": "0.3.5",
  "gpu_offload": true,
  "cuda_version": "12.4",
  "recommended_wheel": "cu124",
  "recommended_reason": "CUDA 12.4 detected — using CUDA 12.4 build.",
  "in_venv": true,
  "venv_path": "C:\\...\\.venv",
  "python": "C:\\...\\.venv\\Scripts\\python.exe"
}

The dialog renders the recommendation banner, preselects the recommended wheel in the combo box, and disables the Uninstall button when nothing is installed.

2. SSE streaming without a browser

Server-Sent Events are a plain HTTP stream with a specific framing: 

data: {"type": "start", "command": "..."}

data: {"type": "line", "text": "Collecting llama-cpp-python[server]"}

data: {"type": "line", "text": "  Downloading wheel..."}

data: {"type": "success", "version": "0.3.5", "gpu_offload": true}

data: [DONE]

Python's httpx can consume this stream via client.stream(...) and iter_text(). The SSEWorker QThread does exactly that: it buffers chunks, splits on the blank-line frame separator (\n\n), strips the data: prefix, and JSON-parses the payload. 

class SSEWorker(QThread):
    event = pyqtSignal(dict)

    def run(self):
        with httpx.Client(timeout=None) as client:
            with client.stream("POST", self.url, json=self.payload) as response:
                buffer = ""
                for chunk in response.iter_text():
                    buffer += chunk
                    while "\n\n" in buffer:
                        frame, buffer = buffer.split("\n\n", 1)
                        for line in frame.split("\n"):
                            if line.startswith("data: "):
                                self.event.emit(json.loads(line[6:]))

Each parsed event is emitted as a Qt signal. The dialog's _on_sse_event slot dispatches on ev["type"]:

Event typeDialog action
startLog the command line and venv path
lineAppend one pip output line to the log area
successShow the green success notice, re-enable buttons, refresh status
errorShow the red error notice, re-enable buttons
doneHide the progress bar, re-enable everything

4. Uninstall with a confirmation

Uninstall is destructive (removes the package), so it prompts first. On Windows the prompt also warns that the backend may need to be stopped first — pip cannot replace DLLs that are currently mapped into the running Python process.

Why not use QProcess?

The original implementation used QProcess to spawn pip directly. That worked on Linux and macOS but had two problems on Windows:

  • Pip's progress output uses carriage returns for its progress bars, which QProcess's line-based reader handles poorly.
  • The pip process ran with the desktop client's environment, which did not always include the venv's Scripts directory on PATH.

Delegating pip to the backend (which already knows the correct venv and has a working subprocess runner) sidesteps both problems. The dialog becomes a pure SSE consumer.

Close-while-running behavior

If the user closes the dialog while an install is running, the dialog prompts for confirmation. If they confirm, the dialog closes and the SSEWorker QThread is left to finish on its own — the pip process on the backend keeps running to completion.

This is intentional: killing pip mid-install can leave a half-installed package with a corrupted .dist-info directory that is painful to repair. Letting the install finish is almost always the right call.

Windows DLL lock warning. When upgrading llama-cpp-python on Windows, the backend must be stopped first. The upgrade checkbox and the success notice both remind the user of this.

Logging & access filtering

The desktop log file

PathRotationRetention
logs/desktop-YYYY-MM-DD.log Midnight UTC 14 days

The desktop log directory is the same as the backend's (logs/), so the LogViewerDialog can show both sources side by side. Filtering by name prefix (backend-*.log vs desktop-*.log) separates them.

Why a separate file from backend/logging_config.py

The backend's logging_config imports backend.config, which in turn imports pydantic-settings. The desktop client does not need to pull in the whole backend config chain just to write logs — the values it needs (logs dir, retention days) are small and can be passed in as arguments.

Keeping the two files separate also means the desktop client can be packaged (PyInstaller) without including the backend config module, shaving a small amount off the bundle.

Sink configuration

SinkDestinationLevel
ConsolestderrINFO (default)
Filelogs/desktop-YYYY-MM-DD.logDEBUG (default)

The file sink uses enqueue=True — writes go through a background thread, so logging never blocks the Qt event loop. This matches the backend's behavior.

Access log filtering

Both desktop.app and the backend's logging filter HTTP access log entries whose status is 2xx or 3xx. This is critical because the desktop client's status bar polls /api/health every 10 seconds, the chat UI polls /api/ollama/ps every 5 seconds, and the graph editor polls /api/graph/runs on page load.

Without filtering, a 4-hour session would produce thousands of identical log lines such as: 

INFO:     127.0.0.1:54321 - "GET /api/health HTTP/1.1" 200 OK
INFO:     127.0.0.1:54322 - "GET /api/ollama/ps HTTP/1.1" 200 OK
INFO:     127.0.0.1:54323 - "GET /api/health HTTP/1.1" 200 OK
... (×10,000)

The filter uses a regex that matches the uvicorn access log format and extracts the status code: 

_ACCESS_LOG_RE = re.compile(
    r'^INFO:\s+\S+\s+-\s+"[A-Z]+\s+\S+\s+HTTP/[\d.]+"\s+(\d{3})\s',
)

def _is_routine_access_log(line: str) -> bool:
    m = _ACCESS_LOG_RE.match(line)
    if not m:
        return False
    try:
        code = int(m.group(1))
    except ValueError:
        return False
    return 200 <= code < 400

The filter preserves 4xx and 5xx entries — those are real problems worth keeping. A 404 on a missing route or a 500 on a broken PHP script is not routine, and the desktop client should surface it to the user.

GUI-only vs file-only. Routine access lines are still appended to the in-app log dock, because users watching a live session like to see the polling activity. They are just not written to the log file.

Safe on multiple launches

The desktop client is single-instance by design — the Qt application model does not support multiple GUI processes sharing the same window state. But if a user does launch two copies, loguru's enqueue=True and Python's append mode make both writers cooperate without corrupting the file. Lines may interleave, but no data is lost.

Read-only filesystem fallback

If the logs directory cannot be created — read-only filesystem, permission denied — the file sink is skipped and a warning is logged at the console level. The desktop client continues with console-only logging. This matches the backend's behavior.

Close behavior

The main window's closeEvent behaves differently based on how the backend was started:

Scenario On close
desktop.app spawned the backend Prompt: "Stop the backend and quit?" — stops on Yes, ignores the close on No
desktop.app attached to an external backend No prompt — external backend untouched, window closes immediately
desktop.native_chat window closes Nothing — the native client never spawns a backend

The stop-all accelerator

Ctrl+Shift+Q triggers the Stop All Processes action. This is different from closing the window:

  1. Sends POST /api/system/stop-all to the backend. The backend acknowledges immediately with {"status": "stopping"} and then shuts down the llama-cpp server, closes the MCP session, and terminates itself.
  2. The desktop launcher waits 1.2 seconds for the backend to complete its shutdown hook.
  3. If the subprocess is still alive after 1.2 seconds, the launcher force-kills the tree with taskkill /F /T on Windows or SIGTERM + SIGKILL on Unix.
  4. The window remains open and shows the log dock with the shutdown progress. The user can restart the backend from the Backend → Start Backend menu.

Window state persistence

The window geometry is saved to QSettings on close, under window/geometry. On the next launch it is restored automatically. If the settings key is missing — first launch, or after clearing the settings — the window opens at 1400 × 900. 

self.settings.setValue("window/geometry", self.saveGeometry())

The backend log dock is hidden by default. Toggle it from View → Show Backend Log, or via the toolbar's checkbox action. Its visibility is not persisted across launches — the dock always starts hidden.

Platform notes

Windows 10 / 11

  • CREATE_NO_WINDOW hides the subprocess console. The backend runs invisibly; its stdout and stderr are captured by the launcher's reader thread.
  • taskkill /F /T /PID <pid> terminates the entire process tree, including the MCP server and the llama-cpp server. This is required because uvicorn spawns child processes and plain terminate() would leave them orphaned.
  • The npx command used by some MCP servers is a .ps1 shim that cannot be spawned directly. The MCP client wraps it in cmd /c.
  • Antivirus software may flag freshly-extracted PHP binaries. See the bootstrap/ documentation for the exclusion list workaround.

Linux

Qt requires a handful of system libraries that are not always installed by default. On Debian / Ubuntu: 

sudo apt-get install -y \
    libxcb-cursor0 libxcb-xinerama0 libxcb-icccm4 \
    libxcb-image0 libxcb-keysyms1 libxcb-randr0 \
    libxcb-render-util0 libxcb-shape0 libxkbcommon-x11-0

PyQt6-WebEngine additionally requires: 

sudo apt-get install -y \
    libnss3 libxcomposite1 libxdamage1 libxrandr2 \
    libgbm1 libasound2 libpango-1.0-0 libcairo2

On Fedora / RHEL the equivalent package names differ slightly — see qt6-qtbase, nss, libXcomposite, etc.

Headless environments. If Qt cannot connect to a display server, the desktop client will not start. Use desktop.native_chat if you only need chat, or run the backend and open the web UI in a browser. For headless CI, no desktop client is needed at all.

macOS

  • The first launch of a PyInstaller bundle is blocked by Gatekeeper. Run this once to remove the quarantine flag: 
    xattr -dr com.apple.quarantine dist/3olutionAgentGraph.app
  • On Apple Silicon, the arm64 wheel of PyQt6-WebEngine is required. The x86_64 wheel will install but fail to load at runtime with a confusing "image not found" error.
  • The application menu integrates with the macOS menu bar. The Quit action is bound to Cmd+Q automatically by Qt.
  • Retina displays are detected automatically. The web UI renders at native resolution.

PyInstaller packaging

The desktop client can be packaged into a single-folder bundle with PyInstaller. Two flags are required to make QtWebEngine work: 

pyinstaller \
    --windowed \
    --name 3olutionAgentGraph \
    --collect-all PyQt6 \
    --collect-all PyQt6.QtWebEngineCore \
    --collect-all PyQt6.QtWebEngineWidgets \
    desktop/app.py

The --collect-all flags are essential — PyInstaller does not automatically detect Qt's plugin DLLs, and the resulting bundle would fail at runtime with "Could not find QtWebEngineProcess".

Connecting to a remote backend

The desktop client is not restricted to a local backend. Set AGENT_HOST and AGENT_PORT (or AGENT_DESKTOP_BACKEND for the native client) to point at a remote instance: 

# Point at a backend running on a different machine

set AGENT_PORT=8000
python -m desktop.app

The launcher will detect the remote backend via /api/health and attach to it. It will not spawn a local subprocess.

Prerequisites

The desktop client assumes the backend dependencies are already installed. If you have not run the bootstrap yet: 

python bootstrap/setup.py
python -m pip install PyQt6 PyQt6-WebEngine httpx

httpx is required by both frontends — the primary client uses it for the periodic /api/health probe and for stop-all; the native client uses it for the SSE chat stream.

PyQt6-WebEngine is optional. When it is missing, desktop.app still launches and shows a NoWebEngineWidget with a button to open the UI in the system browser.

First launch

The startup sequence is:

  1. setup_desktop_logging() — configures loguru, creates logs/ if missing, opens the file sink.
  2. A QApplication is created with the Fusion style and a dark palette.
  3. A DesktopApp window is created. The central widget shows the loading HTML.
  4. A QTimer.singleShot(50, self.backend.start) schedules the backend launch after the event loop begins processing events.
  5. The launcher probes /api/health. When the backend answers, the WebView is navigated to http://127.0.0.1:8000/.
  6. The status bar starts polling every 10 seconds.

Attaching to an existing backend

If a backend is already running at the configured URL — for example, you started uvicorn --reload in a terminal — the launcher attaches to it instead of spawning a duplicate. The toolbar's Stop Backend button is disabled in this case, because the launcher does not own the process.

Overriding the port

set AGENT_PORT=9000

The launcher passes the port through to the subprocess via the AGENT_PORT environment variable, and the WebView navigates to the matching URL.

Common issues

"Qt platform plugin 'xcb' could not be loaded"

Missing X11 libraries on Linux. Install libxcb-cursor0 and friends (see the Platform notes section).

"Could not find QtWebEngineProcess"

PyInstaller bundle missing a plugin. Rebuild with --collect-all PyQt6.QtWebEngineCore.

Backend fails to start

The failure dialog shows the last 40 lines of backend output. Common causes: port already in use (another backend is running), missing dependencies, or a syntax error in the backend code. Run python run.py backend in a terminal to see the full traceback.

"Backend did not become ready within 60 seconds"

The health endpoint responds as soon as uvicorn binds the port. If it does not within 60 seconds, something is wrong. Check that the port is not in use and that the venv has the backend dependencies.

def _is_routine_access_log(line: str) -> bool:
    """True if the line is a successful HTTP access log entry."""
    m = _ACCESS_LOG_RE.match(line)
    if not m:
        return False
    try:
        code = int(m.group(1))
    except ValueError:
        return False
    return 200 <= code < 400

def _handle_download(request) -> None:
    """
    Handle a download initiated by the embedded browser.

    Shows a Save As dialog with a sensible default filename. If the
    user cancels, the download is cancelled.
    """
    try:
        suggested = request.downloadFileName() or "download"
    except Exception:
        suggested = "download"

    target, _ = QFileDialog.getSaveFileName(
        None,
        "Save File",
        str(DOWNLOAD_DIR / suggested),
        "All Files (*.*)",
    )
    if not target:
        request.cancel()
        logger.info("Download cancelled by user: {}", suggested)
        return

    try:
        request.setDownloadDirectory(str(Path(target).parent))
        request.setDownloadFileName(Path(target).name)
        request.accept()
        logger.info("Download accepted: {} → {}", suggested, target)
    except Exception as exc:
        logger.warning("Could not accept download: {}", exc)
        try:
            request.cancel()
        except Exception:
            pass


def _connect_download_handler() -> None:
    """
    Wire the download handler into QtWebEngine's default profile.

    QtWebEngine has no "enable downloads" flag — downloads are
    always enabled. The only requirement is connecting to the
    profile's downloadRequested signal.
    """
    if not WEBENGINE_AVAILABLE:
        return
    try:
        profile = QWebEngineProfile.defaultProfile()
        profile.downloadRequested.connect(_handle_download)
        logger.debug("Download handler connected")
    except Exception as exc:
        logger.warning("Could not connect download handler: {}", exc)

    def _reload(self) -> None:
        """Read the tail of the newest matching log file."""
        source = self.source_combo.currentData()
        n_lines = self.lines_spin.value()

        if source == "backend":
            patterns = ["backend-*.log"]
        elif source == "desktop":
            patterns = ["desktop-*.log"]
        else:
            patterns = ["backend-*.log", "desktop-*.log"]

        files: list[Path] = []
        for pat in patterns:
            files.extend(self.log_dir.glob(pat))

        if not files:
            self.text.setPlainText(
                f"(no log files found in {self.log_dir})"
            )
            return

        files.sort(key=lambda p: p.stat().st_mtime, reverse=True)
        latest = files[0]

        try:
            with latest.open("r", encoding="utf-8", errors="replace") as f:
                all_lines = f.readlines()
            tail = all_lines[-n_lines:]
            self.text.setPlainText("".join(tail))
            self.info_label.setText(
                f"File: {latest.name}   |   "
                f"showing last {len(tail)} of {len(all_lines)} lines   |   "
                f"Log directory: {self.log_dir}"
            )
        except Exception as exc:
            self.text.setPlainText(f"Error reading {latest}: {exc}")

        sb = self.text.verticalScrollBar()
        sb.setValue(sb.maximum())

"""
Backend process launcher for the desktop client.
https://3olution.com

Responsibilities:

  1. Detect whether a backend is already running at the configured
     address. If one is found, attach to it instead of spawning a
     duplicate.

  2. Otherwise, spawn `scripts/serve.py` as a subprocess using the
     correct interpreter (the .venv or portable runtime), and
     monitor it for readiness.

  3. Stream the subprocess's stdout and stderr to the desktop
     client's log dock and to logs/backend-*.log.

  4. Handle graceful shutdown: on close, terminate the subprocess
     tree (taskkill /T on Windows, SIGTERM + SIGKILL on Unix).

================================================================
  SIGNALS
================================================================

  The launcher emits Qt signals:

      started()      — the backend is ready to serve requests
      stopped()      — the subprocess has exited cleanly
      failed(str)    — startup failed with the given message
      log(str)       — one line of subprocess output

  The main window connects to these to update its status bar and
  log dock.

================================================================
  THREADING MODEL
================================================================

  The launcher runs on the Qt event loop's thread (the main GUI
  thread), because it uses Qt's QTimer for polling readiness.

  Subprocess output is read on a background threading.Thread, and
  that thread emits `log` signals. Qt signals are safe to emit
  from any thread — the receiving slot runs on the thread that the
  QObject lives on.

================================================================
  INTERPRETER RESOLUTION
================================================================

  The subprocess must run with an interpreter that has the backend
  dependencies installed. The resolution order is:

    1. .venv/Scripts/python.exe   (Windows)
       .venv/bin/python            (Unix)

    2. sys.executable — the interpreter running the desktop client.

  The first path exists when the developer ran `python run.py setup`.
  The second is a fallback that works in packaged builds where the
  interpreter is bundled inside the PyInstaller archive.
"""

from __future__ import annotations

import os
import subprocess
import sys
import threading
import time
from pathlib import Path

import httpx
from PyQt6.QtCore import QObject, QTimer, pyqtSignal

#  Constants
# ══════════════════════════════════════════════════════════════════════

# How long the launcher waits for the backend to answer /api/health.
# Large cold-load models can take a while to warm up, but the health
# endpoint responds as soon as uvicorn is up — long before the LLM
# is warm. 60 s is generous.
STARTUP_TIMEOUT_SECONDS = 60.0

# How often the readiness poll fires.
HEALTH_POLL_INTERVAL_MS = 500

# Timeout for individual health probes. Kept short so a hung probe
# does not delay the whole startup.
HEALTH_REQUEST_TIMEOUT = 1.5

# Timeout for the graceful stop-all API call.
STOP_ALL_REQUEST_TIMEOUT = 5.0

# How long to wait between terminating the subprocess and force-
# killing it if it does not exit on its own.
GRACEFUL_STOP_TIMEOUT = 5.0


# ══════════════════════════════════════════════════════════════════════
#  Helpers

def _venv_python(project_root: Path) -> Path | None:
    """
    Return the path to the venv Python if a venv exists, else None.
    """
    if sys.platform == "win32":
        candidate = project_root / ".venv" / "Scripts" / "python.exe"
    else:
        candidate = project_root / ".venv" / "bin" / "python"
    return candidate if candidate.exists() else None


def _resolve_interpreter(project_root: Path) -> str:
    """
    Return the interpreter to run the backend with.

    Prefers the venv Python; falls back to the interpreter running
    this process.
    """
    venv = _venv_python(project_root)
    if venv is not None:
        return str(venv)
    return sys.executable


def _check_health(url: str) -> bool:
    """
    Return True if the backend at `url` answers /api/health with 200.

    Never raises — any failure mode is reported as False.
    """
    try:
        r = httpx.get(f"{url}/api/health", timeout=HEALTH_REQUEST_TIMEOUT)
        return r.status_code == 200
    except Exception:
        return False


def _terminate_tree(proc: subprocess.Popen) -> None:
    """
    Terminate a subprocess and all of its children.

    On Windows, uses taskkill /T because uvicorn spawns child
    processes for reload mode and for the MCP server. Plain
    terminate() leaves orphans.

    On Unix, uses SIGTERM first, escalates to SIGKILL after the
    graceful timeout.
    """
    if proc.poll() is not None:
        return

    if sys.platform == "win32":
        subprocess.run(
            ["taskkill", "/F", "/T", "/PID", str(proc.pid)],
            capture_output=True,
            creationflags=subprocess.CREATE_NO_WINDOW,
        )
    else:
        proc.terminate()
        try:
            proc.wait(timeout=GRACEFUL_STOP_TIMEOUT)
        except subprocess.TimeoutExpired:
            proc.kill()
            try:
                proc.wait(timeout=2.0)
            except subprocess.TimeoutExpired:
                pass

class BackendLauncher(QObject):
    """
    Spawns and monitors the backend.

    Usage:

        launcher = BackendLauncher(project_root=Path("."))
        launcher.started.connect(on_started)
        launcher.failed.connect(on_failed)
        launcher.log.connect(on_log)
        launcher.start()
    """

    # ── Signals ──────────────────────────────────────────────────────
    started = pyqtSignal()
    stopped = pyqtSignal()
    failed = pyqtSignal(str)
    log = pyqtSignal(str)

    # ── Lifecycle ────────────────────────────────────────────────────

    def __init__(
        self,
        project_root: Path,
        host: str = "127.0.0.1",
        port: int = 8000,
    ) -> None:
        super().__init__()
        self.project_root = project_root.resolve()
        self.host = host
        self.port = port
        self.url = f"http://{host}:{port}"

        self._proc: subprocess.Popen | None = None
        self._reader_thread: threading.Thread | None = None
        self._ready_timer: QTimer | None = None
        self._health_deadline: float = 0.0
        self._stopping = False

        # True if WE started the process. False if we attached to one
        # that was already running. Used to decide whether to stop the
        # backend on close.
        self.spawned_by_us = False

    def is_running(self) -> bool:
        """True if the subprocess we started is still alive."""
        return self._proc is not None and self._proc.poll() is None

    # ── Start ────────────────────────────────────────────────────────

    def start(self) -> None:
        """
        Attach to an existing backend, or spawn a new one.

        The attach path is important during development: the user
        usually has `uvicorn --reload` running in a terminal and
        launches the desktop client to check the UI. Detecting the
        running backend avoids a port conflict and avoids the
        confusion of two backends fighting over the same SQLite
        file.
        """
        # Already running? Emit started and return.
        if self.is_running():
            self.started.emit()
            return

        # Health probe — attach if a backend is up.
        if _check_health(self.url):
            self.log.emit(
                f"Backend already running at {self.url} — attaching."
            )
            self.spawned_by_us = False
            self.started.emit()
            return

        # Otherwise spawn.
        self._spawn()

    # ── Stop ─────────────────────────────────────────────────────────

    def stop(self) -> None:
        """
        Terminate the subprocess (if we started it).

        Called on application close. If we attached to an external
        backend, does nothing to it — the user manages that backend
        themselves.
        """
        self._stopping = True

        if self._ready_timer is not None:
            self._ready_timer.stop()
            self._ready_timer = None

        if self._proc is None:
            return

        if not self.spawned_by_us:
            self._proc = None
            self.stopped.emit()
            return

        self.log.emit("Stopping backend…")
        _terminate_tree(self._proc)

        if (
            self._reader_thread is not None
            and self._reader_thread.is_alive()
        ):
            self._reader_thread.join(timeout=2.0)

        self._proc = None
        self.spawned_by_us = False
        self.stopped.emit()

    async def stop_all_async(self) -> None:
        """
        Call the backend's /api/system/stop-all endpoint, then
        ensure the process is gone.

        The desktop client's Stop All menu action uses this instead
        of `stop()`, because it triggers a coordinated shutdown of
        the MCP subprocess and the llama-cpp server as well.
        """
        self._stopping = True

        # Ask the backend to shut down cleanly.
        try:
            async with httpx.AsyncClient(
                timeout=STOP_ALL_REQUEST_TIMEOUT,
            ) as client:
                await client.post(f"{self.url}/api/system/stop-all")
            self.log.emit("Backend acknowledged stop-all request.")
        except Exception as exc:
            self.log.emit(
                f"Stop-all API call failed ({exc}); "
                f"falling back to kill."
            )

        # Give the backend a moment to run its shutdown hook.
        import asyncio
        await asyncio.sleep(1.2)

        # If it is still alive, kill the tree.
        if self._proc is not None and self._proc.poll() is None:
            self.log.emit("Backend still alive — killing process tree.")
            _terminate_tree(self._proc)

        if self._ready_timer is not None:
            self._ready_timer.stop()
            self._ready_timer = None

        self._proc = None
        self.spawned_by_us = False
        self.stopped.emit()

    # ── Spawn ────────────────────────────────────────────────────────

    def _spawn(self) -> None:
        """
        Launch the backend subprocess.

        Prefers scripts/serve.py (which handles the Windows event
        loop policy and sys.path fixes) but falls back to a direct
        uvicorn invocation if serve.py is missing.
        """
        serve_py = self.project_root / "scripts" / "serve.py"
        interpreter = _resolve_interpreter(self.project_root)

        if serve_py.exists():
            cmd = [interpreter, str(serve_py)]
        else:
            cmd = [
                interpreter, "-m", "uvicorn",
                "backend.main:app",
                "--host", self.host,
                "--port", str(self.port),
            ]

        # Environment for the subprocess.
        env = os.environ.copy()
        env["PYTHONIOENCODING"] = "utf-8"
        env["PYTHONUTF8"] = "1"

    def _read_output(self, proc: subprocess.Popen) -> None:
        """
        Read the subprocess's stdout and emit each line as a signal.

        Runs in a daemon thread. When the process exits, emits
        `failed` if the exit was unexpected.
        """
        try:
            if proc.stdout is None:
                return
            for line in proc.stdout:
                line = line.rstrip("\r\n")
                if line:
                    self.log.emit(line)
        except Exception:
            pass
        finally:
            try:
                rc = proc.wait(timeout=5)
            except Exception:
                rc = -1
            if not self._stopping and self.spawned_by_us:
                self.failed.emit(
                    f"Backend exited unexpectedly (exit code {rc})"
                )

        """
        Poll /api/health until the backend responds or the timeout
        expires.
        """

        # emit a `failed` signal.
        if self._proc is not None and self._proc.poll() is not None:
            if self._ready_timer is not None:
                self._ready_timer.stop()
                self._ready_timer = None
            return

        if _check_health(self.url):
            if self._ready_timer is not None:
                self._ready_timer.stop()
                self._ready_timer = None
            self.log.emit(f"Backend is ready at {self.url}")
            self.started.emit()
            return

        if time.monotonic() > self._health_deadline:
            if self._ready_timer is not None:
                self._ready_timer.stop()
                self._ready_timer = None
            self.failed.emit(
                f"Backend did not become ready within "
                f"{int(STARTUP_TIMEOUT_SECONDS)} seconds. "
                f"Check the backend log for details."
            )
            self.stop()

class SSEWorker(QThread):
    """
    Reads a Server-Sent Events stream from the backend and emits each
    parsed JSON event as a Qt signal.

    Used for both install and uninstall streaming.
    """

    event = pyqtSignal(dict)

    def __init__(
        self,
        url: str,
        payload: dict | None,
        label: str = "operation",
    ) -> None:
        super().__init__()
        self.url = url
        self.payload = payload
        self.label = label

    def run(self) -> None:
        try:
            with httpx.Client(timeout=None) as client:
                method = "POST" if self.payload is not None else "POST"
                with client.stream(
                    method,
                    self.url,
                    json=self.payload if self.payload is not None else None,
                    headers={"Accept": "text/event-stream"},
                ) as response:
                    if response.status_code != 200:
                        response.read()
                        self.event.emit({
                            "type": "error",
                            "message": f"HTTP {response.status_code}",
                        })
                        return

                    buffer = ""
                    for chunk in response.iter_text():
                        if not chunk:
                            continue
                        buffer += chunk
                        while "\n\n" in buffer:
                            frame, buffer = buffer.split("\n\n", 1)
                            for line in frame.split("\n"):
                                if not line.startswith("data: "):
                                    continue
                                data = line[6:]
                                if data == "[DONE]":
                                    return
                                try:
                                    self.event.emit(json.loads(data))
                                except json.JSONDecodeError:
                                    continue
        except Exception as exc:
            self.event.emit({
                "type": "error",
                "message": f"{self.label} stream failed: {exc}",
            })

"""
Logging setup for the desktop application.
https://3olution.com

Mirrors the backend's logging setup:

    - A console sink at INFO level for the terminal
    - A rotating file sink at DEBUG level for diagnostics
    - Files written to the same `logs/` folder as the backend,
      with a `desktop-` prefix instead of `backend-`

================================================================
  WHY A SEPARATE FILE FROM backend/logging_config.py
================================================================

  The backend's logging_config imports backend.config, which in
  turn imports pydantic-settings. The desktop client does NOT need
  to pull in the whole backend config chain just to write logs —
  the values it needs (logs dir, retention days) are small and can
  be passed in as arguments.

  Keeping the two files separate also means the desktop client can
  be packaged (PyInstaller) without including the backend config
  module, shaving a small amount off the bundle.

================================================================
  ROTATION AND RETENTION
================================================================

  Files rotate at midnight UTC and are named:

      logs/desktop-YYYY-MM-DD.log

  Retention is 14 days, matching the backend. The retention policy
  is enforced per loguru sink, so the desktop log and backend log
  are pruned independently.

================================================================
  SAFE ON MULTIPLE LAUNCHES
================================================================

  The desktop client is single-instance by design — the Qt
  application model does not support multiple GUI processes
  sharing the same window state. But if a user does launch two
  copies, loguru's `enqueue=True` and Python's append mode make
  both writers cooperate without corrupting the file. Lines may
  interleave, but no data is lost.
"""

from __future__ import annotations

import sys
from pathlib import Path

from loguru import logger


def setup_desktop_logging(
    log_dir: Path,
    console_level: str = "INFO",
    file_level: str = "DEBUG",
    retention_days: int = 14,
) -> None:
    """
    Configure loguru for the desktop application.

    Removes any existing handlers (including the default stderr
    sink that loguru installs at import time) so the desktop
    client's logging is self-contained.

    Parameters
    ----------
    log_dir
        Directory for log files. Created if missing.
    console_level
        Minimum level written to stderr. The desktop client runs
        with a visible terminal during development; users who
        launch the packaged executable see nothing on stderr
        (console=False in the PyInstaller spec), which is fine.
    file_level
        Minimum level written to the log file. Defaults to DEBUG
        so that user bug reports contain full diagnostics.
    retention_days
        Number of daily log files to keep before pruning.
    """
    # Remove every existing handler (there is exactly one by default).
    logger.remove()

    # ── Console sink ─────────────────────────────────────────────────
    console_format = (
        "{time:YYYY-MM-DD HH:mm:ss} | "
        "{level: <8} | "
        "{name}:{line} — "
        "{message}"
    )
    logger.add(
        sys.stderr,
        level=console_level.upper(),
        format=console_format,
        colorize=True,
        backtrace=True,
        diagnose=False,
    )

    # ── File sink ────────────────────────────────────────────────────
    try:
        log_dir.mkdir(parents=True, exist_ok=True)
        log_file = log_dir / "desktop-{time:YYYY-MM-DD}.log"

        file_format = (
            "{time:YYYY-MM-DD HH:mm:ss.SSS} | "
            "{level: <8} | "
            "{name}:{line} — {message}"
        )
        logger.add(
            str(log_file),
            rotation="00:00",
            retention=f"{retention_days} days",
            level=file_level.upper(),
            format=file_format,
            encoding="utf-8",
            enqueue=True,
            backtrace=True,

class AgentWorker(QThread):
    """
    Runs one agent turn off the UI thread.

    Emits each event as a dict via the `event` signal. Prefers the
    SSE streaming endpoint so tokens arrive live; falls back to the
    non-streaming /api/chat endpoint if SSE is unavailable.
    """

    event = pyqtSignal(dict)

    def __init__(
        self,
        message: str,
        history: list[dict],
        session_id: str | None = None,
    ) -> None:
        super().__init__()
        self.message = message
        self.history = history
        self.session_id = session_id

    def run(self) -> None:
        payload = {
            "message": self.message,
            "history": self.history,
            "session_id": self.session_id,
        }

        # ── Primary path: SSE streaming ─────────────────────────────
        try:
            with httpx.Client(timeout=None) as client:
                with client.stream(
                    "POST",
                    f"{BACKEND}/api/chat/stream",
                    json=payload,
                    headers={"Accept": "text/event-stream"},
                ) as response:
                    if response.status_code != 200:
                        response.read()
                        raise RuntimeError(f"HTTP {response.status_code}")

                    buffer = ""
                    for chunk in response.iter_text():
                        if not chunk:
                            continue
                        buffer += chunk

                        # SSE frames are separated by a blank line.
                        while "\n\n" in buffer:
                            frame, buffer = buffer.split("\n\n", 1)
                            for line in frame.split("\n"):
                                if not line.startswith("data: "):
                                    continue
                                data = line[6:]
                                if data == "[DONE]":
                                    return
                                try:
                                    self.event.emit(json.loads(data))
                                except json.JSONDecodeError:
                                    continue
                    return
        except Exception:
            pass

        # ── Fallback path: non-streaming POST ───────────────────────
        try:
            with httpx.Client(timeout=300.0) as client:
                resp = client.post(f"{BACKEND}/api/chat", json=payload)
                resp.raise_for_status()
                for ev in resp.json():
                    self.event.emit(ev)
        except Exception as exc2:
            self.event.emit({
                "type": "final",
                "content": f"Connection error: {exc2}",
                "messages": self.history,
            })

Two design decisions worth highlighting:

Attach-first semantics. The launcher first checks whether a backend is already running at the configured URL. This makes it possible to develop against uvicorn --reload in a terminal and launch the desktop client separately without a port conflict.

spawned_by_us flag. Only processes the launcher itself started are terminated on close. An externally-started backend is left running, because the user's terminal session controls its lifecycle.

install_dialog.py — pip streaming without a browser

The dialog consumes the same /api/llama/install/install and /api/llama/install/uninstall SSE endpoints the web settings page uses. The SSEWorker QThread wraps httpx.Client.stream(...) and parses each data: frame into a Python dict, emitting it as a Qt signal.

The wheel recommendation comes from /api/llama/install/status, which in turn calls backend.llama_installer.recommend_wheel_index() — the same CUDA detection logic the web UI uses. So switching between the native dialog and the web page produces identical recommendations.

Access log filtering

Both desktop.app and backend.logging_config filter HTTP access log entries whose status is 2xx or 3xx. This is critical because the desktop client's status bar polls /api/health every 10 seconds, the chat UI polls /api/ollama/ps every 5 seconds, and the graph editor polls /api/graph/runs on page load. Without filtering, a 4-hour session would produce thousands of identical log lines.

The filter preserves 4xx and 5xx entries — those are real problems worth keeping.
