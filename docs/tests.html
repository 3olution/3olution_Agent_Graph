Test Suite

A focused pytest suite that covers the pure-logic parts of the codebase — the graph engine's topological sort, the JSON-safety helper, and every built-in node function. The integration surface (FastAPI routes, MCP subprocess, LLM clients) is deliberately excluded because it depends on external services that would require mocking infrastructure outweighing the value of the tests.

Overview

The tests/ folder contains a small but dense pytest suite. It targets the parts of the project where:

  • A bug is most likely to hide — the topological sort algorithm and the node functions have non-trivial logic.
  • A fast test loop is most valuable — the engine can be iterated on without spinning up a server or a model.
  • Coverage is cheap to write — no mocking, no fixtures, no external services.

File layout

tests/
├── __init__.py         package marker + usage docs
├── test_engine.py      pure logic: topological sort, JSON safety
└── test_nodes.py       built-in node functions and graph parsing

Coverage at a glance

Test file Tests Covers
test_engine.py 15 _topo_sort() (linear, fan-out, fan-in, diamond, disconnected, empty, single, cycles, dangling edges) and _safe()
test_nodes.py 30+ Registry, input nodes, output nodes, LLM prompt builder, text templating, control flow (branch, merge, foreach), utility nodes, Graph.from_dict()

Design principles

1. Pure logic only

Every test calls a function directly with plain Python data and asserts on the return value. No HTTP requests, no subprocesses, no model inference. The suite runs in under a second.

2. No global state

The node tests import the registry, which is populated at package-load time. Beyond that, no test writes to shared state. Tests can run in any order and in parallel.

3. Explicit async markers

Every async test is decorated with @pytest.mark.asyncio. The suite does not depend on a pytest.ini or pyproject.toml configuration — it runs from a plain pip install pytest pytest-asyncio.

4. Failure messages that name the problem

Test names describe the behaviour under test, not the function being called. test_topo_sort_diamond reads better in a failure report than test_toposort_4.

The canary test. test_registry_has_builtins asserts that at least 16 node types are registered. If the registry ever ends up empty — a broken import in nodes.py, a circular dependency — this test fails with a clear message before the other 30+ node tests fail with confusing "None has no attribute" errors.

What the tests are not

This is not a full integration test suite. It does not exercise the FastAPI application, the MCP protocol, the LLM client, or any of the runtime subprocesses. See What is not tested for the full list and the reasoning.

Running the Tests

Full suite, verbose

pytest tests/ -v

Runs every test in both files. The -v flag prints one line per test with its name and PASSED/FAILED status.

Full suite, quiet

pytest tests/

Prints one dot per test, then a summary. Useful in a CI log where the individual test names would be noise.

One file

pytest tests/test_engine.py -v
pytest tests/test_nodes.py -v

One test

pytest tests/test_engine.py::test_topo_sort_diamond -v

Pattern matching

pytest tests/ -k "topo_sort" -v
pytest tests/ -k "branch or merge" -v
pytest tests/ -k "not delay" -v

The -k flag filters test names by substring or expression. It is the fastest way to iterate on a specific area without re-running everything.

Stop at first failure

pytest tests/ -x -v

Useful during development — a single failure is easier to read than a cascade of downstream failures caused by it.

Show local variables in failures

pytest tests/ -l

Prints the value of local variables at the point of a failure. Combine with -v for full context.

Summary of the useful flags

Flag Effect
-v Verbose — one line per test
-x Stop at the first failure
-k EXPR Only run tests matching the name expression
-l Show local variables on failure
-q Quiet — minimal output
--tb=short Shorter tracebacks
--tb=line One line per traceback — for large failures
-p no:cacheprovider Skip the .pytest_cache directory

Dependencies & Async docs

Dependencies & Async

What to install

pip install pytest pytest-asyncio
Package Purpose
pytest The test runner. Discovers test_*.py, collects test_* functions, and reports results.
pytest-asyncio Support for async def test functions. Required for the node tests, which call async node functions.

Both are in the project's requirements-dev.txt (if present) or can be installed ad-hoc. Neither is required by the backend itself — a production deployment does not need them.

Async configuration

pytest-asyncio requires one of two configurations to know which tests to run in async mode:

Option 1 — explicit markers (this suite's choice)

Every async test is decorated with @pytest.mark.asyncio: 

@pytest.mark.asyncio
async def test_input_text():
    nt = get("input.text")
    result = await nt.fn(None, {}, {"value": "hello"})
    assert result == {"text": "hello"}

This is what test_nodes.py does. The advantage is that the suite is self-contained — no pytest.ini or pyproject.toml needed.

Option 2 — global auto mode

Set asyncio_mode = "auto" in a config file: 

[tool.pytest.ini_options]
asyncio_mode = "auto"

Then every async def test runs automatically without a marker. This is what larger projects often choose, but it requires a configuration file.

Why the suite uses option 1. A project that ships tests should not require a configuration file just to run them. The explicit-marker approach lets a user copy tests/ into another project and run it immediately.

Async event loop

Each async test gets a fresh event loop by default. This matters because node functions are stateless — they do not hold any cross-test state — but it also means a bug that only shows up on the second invocation of a function would not be caught. For the current suite, that is not a concern.

Importing from the backend

The tests import from backend.graph.*. This requires the project root to be on sys.path. When running pytest from the project root, this is automatic — pytest adds the current directory to sys.path as long as the tests folder contains an __init__.py.

If you run pytest from a different directory: 

cd /path/to/project
pytest tests/ -v

Or set PYTHONPATH: 

PYTHONPATH=. pytest tests/ -v

What the imports look like

from backend.graph.engine import _safe, _topo_sort
from backend.graph.model import Edge, Graph, Node
from backend.graph.registry import get

All three come from the graph subpackage. Importing backend.graph at module load time triggers the registry's built-in node registration as a side effect — which is what makes the get("input.text") lookups in test_nodes.py work.

No conftest.py

The suite does not use a conftest.py. There are no fixtures, no shared setup, no teardown. Every test is self-contained.

No coverage configuration

Running pytest --cov=backend would work if pytest-cov is installed, but the suite does not include a coverage threshold or configuration. Coverage of integration code is not the goal — coverage of the pure-logic parts is, and that is already near 100%.

test_engine.py

Covers the pure-logic parts of backend/graph/engine.py. The full execute() generator is not tested because it depends on a populated registry, a live app state dict, and every node's implementation being deterministic — all integration-level concerns.

The topological sort is the critical algorithm — everything else in the engine is a straightforward loop around it.

Tests in this file

_topo_sort — happy path

Test Graph shape Assertion
test_topo_sort_linear a → b → c Result is exactly [a, b, c]
test_topo_sort_fan_out root → left, root → right Root first; the two children in either order
test_topo_sort_fan_in a → merge, b → merge Both roots before merge
test_topo_sort_diamond a → b → d, a → c → d a first, d last, b and c before d
test_topo_sort_disconnected Two independent chains Both chains sorted, all four nodes present
test_topo_sort_single_node One node, no edges Result is [only]
test_topo_sort_empty No nodes, no edges Result is []

_topo_sort — error cases

Test Input Assertion
test_topo_sort_cycle_raises Two-node cycle a ↔ b ValueError with "cycle" in the message
test_topo_sort_self_loop_raises Self-loop a → a ValueError with "cycle"
test_topo_sort_three_node_cycle_raises a → b → c → a ValueError with "cycle"
test_topo_sort_ignores_dangling_edges Edges referencing unknown nodes Result is just [a]; the bad edges are silently ignored
Why the "cycle" substring matters. Callers detect the cycle case by matching the message, so the test asserts on the substring rather than the exact wording. That way the test does not break if the message is reworded, but it does break if the word cycle disappears — which would break the caller.

_safe — JSON-safety helper

Test Input Assertion
test_safe_primitive str, int, float, bool, None Every primitive passes through unchanged
test_safe_container list, dict Containers of serialisable values pass through
test_safe_unserialisable datetime instance Result is a str containing the year
test_safe_custom_object User class with __str__ Result is the output of str(obj)

The purpose of _safe() is to keep the graph_done event from raising when a node returns something JSON cannot serialise. The tests confirm that the function handles the two realistic cases — a datetime and a custom class — by stringifying them.

What is not tested in this file

  • execute() — the async generator that runs a graph. It depends on the registry, the app state, and node implementations. Testing it would require a full fixture setup.
  • ExecutionContext — the helper class that holds outputs during a run. It is exercised indirectly by execute(), but not tested in isolation.
  • _gather_inputs() — reads edge values from the execution context. Its logic is simple enough that a bug would be caught by an integration test at the route level.

Why 15 tests for two functions?

The topological sort is a small algorithm with a lot of edge cases. Every shape of graph — chain, fan, diamond, disconnected, cyclic — has a different failure mode. A bug that breaks the diamond case might pass the linear case, and vice versa. Covering all the shapes is the only way to be confident the algorithm is correct.

What is not tested in this file

  • llm.chat — needs an LLM client in the app state.
  • tool.list, tool.call — need an MCP client in the app state.
  • control.foreach with an op that itself calls an external service — the test uses input.number as the inner op precisely because it is pure.
  • custom_nodes — the example nodes are loaded by the custom-node loader but not tested by this suite. They are demonstrations, not core functionality.

Why the tests use the registry instead of importing node functions directly

Node functions like _input_text are module-private (leading underscore). Importing them directly would couple the tests to internal naming. Going through registry.get("input.text") is the public interface — the same one the engine uses — so the tests exercise the same code path the production system does.

What Is Not Tested

The suite is intentionally narrow. This page lists what is excluded and why, so that a reader does not mistake the coverage for a full integration test suite.

The exclusion table

Layer Why not
FastAPI routes Requires a live HTTP server; covered indirectly by _check_router() at startup
LLM client (backend/llm.py) Depends on an external OpenAI-compatible endpoint
MCP client (backend/mcp_client.py) Requires a live MCP subprocess
llama-cpp manager Requires the native library and a GGUF file
PHP executor Requires a php-cgi binary
Desktop client Requires a GUI environment
Agent loop (backend/agent.py) Drives the LLM and MCP clients — same dependencies
Storage (backend/storage.py) Currently uncovered; a legitimate next target because it has no external dependencies
Bootstrap (bootstrap/setup.py) Downloads binaries; testing it would require network access and a sandbox

Why the trade-off is deliberate

Testing integration code requires mocking infrastructure that quickly outweighs the value of the tests. Consider what a mocked test of /api/chat would need:

  • A fake LLMClient that returns canned streaming deltas.
  • A fake MCPClient that returns canned tool schemas and results.
  • A fake SessionStore that accepts and discards writes.
  • A fake app state dict with those three objects wired in.
  • Assembled per-test or via a fixture.

The test would then verify that the route calls the fake LLM and writes to the fake store — which is testing the mocks, not the route. If the real LLMClient or the real MCPClient has a bug, the mocked test would not catch it.

The alternative is real integration tests. Those would require a running Ollama instance, a built MCP server, and a controllable LLM — a full CI environment rather than a unit test suite. That is a legitimate future extension, not a current gap in coverage.

What covers these layers today

Layer Runtime validation
FastAPI routes _check_router() at startup asserts each router has the expected number of routes
LLM client LLMClient.warmup() pings the primary endpoint at startup and logs success or failure
MCP client MCPClient.connect() spawns the subprocess and initialises the session; a failure is logged clearly
llama-cpp LlamaServerManager.start() spawns the subprocess and waits for readiness; a failure is logged with the last 30 lines of subprocess output
PHP php_status() reports binary path, version, and CGI availability; the settings page surfaces it
Desktop client Manual testing — there is no CI story for a GUI

The startup diagnostics in backend/main.py are the current mechanism for catching integration failures. They are not a substitute for automated tests, but they are the right scope for a project this size.

The storage.py gap

Of the excluded layers, backend/storage.py is the most testable. It has no external dependencies — the SQLite file is created in a temporary directory, every method is async and pure with respect to the rest of the app, and the operations are simple CRUD.

A future test_storage.py could cover:

  • Session upsert and load
  • Session delete returning True/False
  • Graph run save with pruning
  • Graph run list, load, delete
  • Pagination and limit clamping

It would need one fixture — a temporary database path — and would add maybe 20 tests. It is the obvious next file.

What would stay excluded even after that

Even with test_storage.py, the following would remain integration-level:

  • Anything that talks to a network endpoint
  • Anything that spawns a subprocess (MCP, llama-server, PHP)
  • Anything that imports fastapi and exercises a route
  • Anything that requires a GPU or a specific CPU feature

That is the boundary. The suite will never cover those, and it does not need to — the boundary is drawn where automated testing stops being cheaper than manual verification.

Extending the Suite

Adding a new test file

Create tests/test_<area>.py. pytest discovers any file matching test_*.py in the tests/ directory. 

tests/
├── __init__.py
├── test_engine.py       ← existing
├── test_nodes.py        ← existing
└── test_storage.py      ← new file, auto-discovered

Adding a test function

A test function must:

  • Start with test_.
  • Take no arguments (unless using fixtures).
  • Use assertions to express the expected outcome.
def test_something():
    assert 1 + 1 == 2

Adding an async test

Decorate with @pytest.mark.asyncio and mark the function async def: 

import pytest

@pytest.mark.asyncio
async def test_async_operation():
    result = await some_async_function()
    assert result == expected

The suite uses explicit markers rather than auto-mode, so forgetting the decorator means the test is silently collected but never awaited. pytest-asyncio will warn about this — look for the PytestUnraisableExceptionWarning or a similar message in the output.

Using fixtures

The current suite has no fixtures, but pytest supports them cleanly. A fixture is a function decorated with @pytest.fixture that returns a value; a test that names a fixture as an argument receives that value. 

import pytest

@pytest.fixture
def temp_db(tmp_path):
    """A fresh SQLite path in a temp directory."""
    return str(tmp_path / "test.db")

def test_storage_init(temp_db):
    from backend.storage import SessionStore
    store = SessionStore(temp_db)
    # ...

tmp_path is a pytest built-in that gives each test a unique temporary directory. It is cleaned up automatically.

Parametrised tests

When the same logic needs to be verified against multiple inputs, use @pytest.mark.parametrize instead of copy-pasting the test: 

@pytest.mark.parametrize("inputs,expected", [
    ({}, ""),
    ({"value": "hi"}, "hi"),
    ({"value": 42}, 42),
])
def test_something(inputs, expected):
    assert process(inputs) == expected

pytest runs the test once per tuple and reports each as a separate PASSED/FAILED line.

Expected exceptions

with pytest.raises(ValueError, match="cycle"):
    _topo_sort(graph)

The match argument is a regex matched against the exception's string. It is a substring match by default, so match="cycle" succeeds if the message contains that word anywhere.

Testing the storage layer — a worked example

A new test_storage.py would follow the same pattern as the existing files. Sketch of the setup: 

from __future__ import annotations

import pytest

from backend.storage import SessionStore


@pytest.fixture
def store(tmp_path):
    """A SessionStore backed by a fresh temp database."""
    return SessionStore(str(tmp_path / "test.db"), max_graph_runs=10)


@pytest.mark.asyncio
async def test_save_and_load_session(store):
    await store.init()
    await store.save("s1", [{"role": "user", "content": "hi"}])
    loaded = await store.load("s1")
    assert loaded == [{"role": "user", "content": "hi"}]


@pytest.mark.asyncio
async def test_load_missing_session(store):
    await store.init()
    assert await store.load("does-not-exist") is None

The fixture tmp_path gives each test its own directory, so tests do not interfere with each other and the real sessions.db is never touched.

Naming conventions

Pattern Meaning
test_<function> Tests a specific function's happy path
test_<function>_<case> Tests a specific edge case of that function
test_<function>_raises Tests that a function raises for invalid input
test_<thing>_<behaviour> Tests a behaviour rather than a function name

The suite currently follows this loosely. test_topo_sort_diamond names the shape under test; test_control_branch_string_condition names the behaviour. Both are fine — the goal is a name that reads well in a failure report.

What to do when a test is too hard to write

If a test requires more setup than the thing it verifies, that is a signal about the code, not the test. Two options:

  1. Extract the pure logic. If the function under test calls three external services before doing something interesting, split out the interesting part as a pure function and test that.
  2. Accept the exclusion. Some code is integration code by nature and does not benefit from unit testing. Add the case to What is not tested and move on.
A test that takes an hour to write and never fails is a net loss. The current suite is fast, targeted, and small. Keeping it that way is more valuable than chasing coverage numbers.

"""
Tests for the graph execution engine.
https://3olution.com

Covers the pure-logic parts of backend/graph/engine.py:

    _topo_sort()   — Kahn's algorithm for topological sorting
    _safe()        — JSON-safety helper used when serialising outputs

The full execute() generator is not tested here because it depends
on the registry being populated with node types, the shared app
state being populated with LLM/MCP clients, and every node's
implementation being deterministic. Those dependencies are
integration-level concerns.

The topological sort is the critical algorithm — everything else
in the engine is a straightforward loop around it.
"""

from __future__ import annotations

import pytest

from backend.graph.engine import _safe, _topo_sort
from backend.graph.model import Edge, Graph, Node


# ══════════════════════════════════════════════════════════════════════
#  Helpers
# ══════════════════════════════════════════════════════════════════════

def _node(node_id: str, node_type: str = "input.text") -> Node:
    """Short constructor for a Node with sensible defaults."""
    return Node(id=node_id, type=node_type)


def _edge(
    edge_id: str,
    from_node: str,
    from_output: str,
    to_node: str,
    to_input: str,
) -> Edge:
    """Short constructor for an Edge."""
    return Edge(
        id=edge_id,
        from_node=from_node,
        from_output=from_output,
        to_node=to_node,
        to_input=to_input,
    )


# ══════════════════════════════════════════════════════════════════════
#  _topo_sort — happy path
# ══════════════════════════════════════════════════════════════════════

def test_topo_sort_linear():
    """
    A three-node chain sorts in strict order: a → b → c.

    This is the simplest possible graph shape and verifies the core
    invariant: every node appears after all of its dependencies.
    """
    g = Graph(
        nodes=[
            _node("a"),
            _node("b", "llm.chat"),
            _node("c", "output.text"),
        ],
        edges=[
            _edge("e1", "a", "text", "b", "messages"),
            _edge("e2", "b", "response", "c", "text"),
        ],
    )
    assert _topo_sort(g) == ["a", "b", "c"]


def test_topo_sort_fan_out():
    """
    A single root feeding two children places the root first and
    the two children in either order after it.
    """
    g = Graph(
        nodes=[
            _node("root"),
            _node("left", "output.text"),
            _node("right", "output.text"),
        ],
        edges=[
            _edge("e1", "root", "text", "left", "text"),
            _edge("e2", "root", "text", "right", "text"),
        ],
    )
    order = _topo_sort(g)

    assert order[0] == "root"
    assert set(order[1:]) == {"left", "right"}


def test_topo_sort_fan_in():
    """
    Two roots merging into one sink places both roots before the sink.
    """
    g = Graph(
        nodes=[
            _node("a"),
            _node("b"),
            _node("merge", "control.merge"),
        ],
        edges=[
            _edge("e1", "a", "text", "merge", "a"),
            _edge("e2", "b", "text", "merge", "b"),
        ],
    )
    order = _topo_sort(g)

    assert order[-1] == "merge"
    assert set(order[:-1]) == {"a", "b"}


def test_topo_sort_diamond():
    """
    A diamond graph (a → b, a → c, b → d, c → d) has exactly one
    valid topological order for the endpoints: a first, d last.
    """
    g = Graph(
        nodes=[
            _node("a"),
            _node("b"),
            _node("c"),
            _node("d"),
        ],
        edges=[
            _edge("e1", "a", "text", "b", "text"),
            _edge("e2", "a", "text", "c", "text"),
            _edge("e3", "b", "text", "d", "a"),
            _edge("e4", "c", "text", "d", "b"),
        ],
    )
    order = _topo_sort(g)

    assert order[0] == "a"
    assert order[-1] == "d"
    assert order.index("b") < order.index("d")
    assert order.index("c") < order.index("d")


def test_topo_sort_disconnected():
    """
    A graph with two disconnected components still sorts every node.

    Kahn's algorithm handles disconnected graphs naturally: every
    node with indegree 0 is enqueued as a starting point.
    """
    g = Graph(

            _node("b"),
            _node("x"),

            _edge("e1", "a", "text", "b", "text"),
            _edge("e2", "x", "text", "y", "text"),
        ],
    )
    order = _topo_sort(g)

    assert len(order) == 4
    assert order.index("a") < order.index("b")
    assert order.index("x") < order.index("y")
