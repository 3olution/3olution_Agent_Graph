PHP Notes App

A small, self-contained PHP notes application served by the Python backend through PHP's CGI SAPI. It is driver-agnostic — the same code runs against SQLite (default), MySQL, or PostgreSQL, chosen entirely by AGENT_PHP_DB_DRIVER. Every SQL statement is a prepared statement; every DDL statement is emitted by ensure_schema() in the correct dialect. This folder holds the app's PHP source, its SQLite database directory, and its static assets.

Overview docs

php_app/ — what this folder is
doc

Overview

The php_app/ folder is a complete PHP application that the Python backend serves at /php/. It is not a framework — it is four PHP files, one stylesheet, and a data directory. Together they implement a working notes app: list, add, and delete notes, backed by a relational database.

The app exists partly because PHP is good at this kind of small server-rendered CRUD application, and partly to demonstrate that the backend can host non-Python code through the same HTTP surface. The agent and the graph engine do not know or care that /php/ is PHP — the route just returns HTML.

Package layout

php_app/
├── index.php          main page — list, add, delete
├── db.php             connection factory + ensure_schema() + helpers
├── demo.php           JSON endpoint — reports driver + version
├── style.css          deprecated stub (see /php-static route)
│
├── data/              SQLite database directory
│   ├── .gitkeep       placeholder so git tracks the empty folder
│   └── app.db         created on first request (gitignored)
│
└── static/            assets served at /php-static/*
    └── style.css      the real stylesheet

What it does

RouteRenders
GET /php/The notes page — list of notes plus an add form
POST /php/ action=addInserts a note, redirects back to the list
POST /php/ action=deleteDeletes a note, redirects back to the list
GET /php/demo.phpJSON: driver, version, note count, table list
GET /php-static/style.cssThe stylesheet

What it does not do

  • No authentication — anyone who can reach the backend can read and write notes.
  • No pagination — every note is loaded on every page view.
  • No rich text — titles and bodies are plain strings.
  • No file uploads — attachments are out of scope.
  • No REST API — it is a server-rendered app, not a JSON backend (except demo.php).
Do not expose the backend to untrusted clients. The notes app runs with the backend process's privileges and there is no authentication in front of it. On a single-user machine that is fine. On a shared host, front it with a reverse proxy that enforces authentication.

Who owns the folder

Two modules own this folder, each responsible for a different part:

  • backend/php_server.py — finds the PHP CGI binary, builds the CGI environment, spawns the subprocess, parses the output.
  • backend/routes/php_routes.py — the FastAPI routes that receive HTTP requests, resolve paths safely, and forward to php_server.py.

The data/ folder is created automatically by backend/main.py's _ensure_php_dirs() during the FastAPI lifespan, so it is always present even on a fresh clone.

Version history worth knowing

Two earlier bugs are worth remembering because they shape the current code:

  1. The /php-static/ route did not exist. index.php linked a stylesheet at /php-static/style.css, but no route served that path. Every page loaded unstyled. The fix moved the CSS to php_app/static/ and added the route.
  2. The delete link was a GET. <a href="/php/?delete=42"> could be triggered by a link prefetcher or a bookmark. The fix is a POST form, with the old GET path kept for compatibility.

Architecture

The notes app is served by the Python backend acting as a CGI host. There is no Apache, nginx, or PHP-FPM in the picture — the backend builds the CGI environment itself, spawns php-cgi as a subprocess, and reads the response off the subprocess's stdout.

The full request flow

Browser
   │
   │  GET /php/
   ▼
FastAPI backend  (backend/routes/php_routes.py)
   │
   │  1. resolve path safely under php_app/
   │  2. build CGI environment (REQUEST_METHOD, QUERY_STRING, …)
   │  3. spawn php-cgi with the script as SCRIPT_FILENAME
   │  4. pass the request body on stdin
   │  5. capture stdout + stderr
   ▼
php-cgi subprocess
   │
   │  reads SCRIPT_FILENAME, executes the PHP file
   │  includes db.php via require_once
   │  db.php opens a PDO connection to:
   │      - SQLite at php_app/data/app.db  (default)
   │      - MySQL / PostgreSQL if configured
   ▼
app_db() → PDO connection
   │
   │  ensure_schema() emits driver-specific CREATE TABLE
   │  the page reads/inserts/deletes rows
   ▼
HTML response back up the chain

Why CGI?

  • No extra service. Running PHP-FPM or an Apache module would mean a second daemon to manage, a second port to bind, and a second configuration file to keep in sync. CGI is a subprocess call.
  • Process isolation. Each request is a fresh PHP process. A misbehaving script cannot leak state into the next request.
  • Cross-platform. php-cgi is available on Windows, Linux, and macOS. There is no equivalent portable FPM build.
The cost of process isolation. A fresh PHP process is spawned on every request. For a notes app this is negligible — the process starts in ~30 ms and the request completes in under 100 ms. For a high-traffic service the per-request process cost would matter, but that is not the use case here.

The CGI environment

The backend builds a full CGI/1.1 environment for the subprocess. PHP reads the request from environment variables, not from a socket:

VariableValue
REQUEST_METHODGET, POST, etc.
SCRIPT_FILENAMEAbsolute path to the .php file
SCRIPT_NAMEThe URL path PHP sees
QUERY_STRINGEverything after the ?
CONTENT_TYPEFrom the incoming request headers
CONTENT_LENGTHLength of the request body
SERVER_NAMEThe configured backend host
SERVER_PORTThe configured backend port
REDIRECT_STATUS1 — required by PHP for CGI mode
HTTP_X_FORWARDED_PREFIX/php — so links resolve correctly

In addition, every AGENT_PHP_* setting from .env is passed through as an environment variable, which is how db.php knows which driver and credentials to use.

Response parsing

php-cgi writes the response to stdout in standard CGI form — headers first, then a blank line, then the body: 

Content-Type: text/html; charset=utf-8
Status: 200 OK

<!DOCTYPE html>
<html>...

The backend splits at the first \n\n, parses each header line, extracts an optional Status: header, and returns a FastAPI Response with the resulting status code, headers, and body.

Path safety

Every user-supplied path is resolved under the PHP app directory. A path like ../../etc/passwd is rejected before the file is even opened: 

def _resolve_safe(rel_path: str) -> Path | None:
    base = PHP_APP_DIR.resolve()
    candidate = (base / rel_path).resolve()
    try:
        candidate.relative_to(base)
    except ValueError:
        logger.warning("Rejected path traversal attempt: {}", rel_path)
        return None
    return candidate

This is the standard defence against directory traversal. The same check is applied to static assets under php_app/static/.

Cross-Driver Support

The app runs against three databases through PDO. There is no ORM, no query builder, and no abstraction layer — just a small ensure_schema() function that picks the right DDL for the connected driver, and prepared statements everywhere else.

What actually differs

The original db.php claimed MySQL and PostgreSQL support but the index.php schema used SQLite-only AUTOINCREMENT syntax. That is now fixed: ensure_schema() in db.php picks the correct DDL per driver.

Feature SQLite MySQL PostgreSQL
Auto-increment PK INTEGER PRIMARY KEY AUTOINCREMENT INT AUTO_INCREMENT PRIMARY KEY SERIAL PRIMARY KEY
Version query SELECT sqlite_version() SELECT VERSION() SELECT version()
Table listing sqlite_master query SHOW TABLES pg_tables query
WAL mode PRAGMA journal_mode = WAL n/a n/a
Foreign keys PRAGMA foreign_keys = ON on by default (InnoDB) on by default

Prepared statements everywhere

Every SQL statement that takes user input goes through prepare() / execute(), never string concatenation. This is what makes the app safe against SQL injection without any escaping logic of its own. 

$stmt = $db->prepare(
    'INSERT INTO notes (title, body, created) VALUES (?, ?, ?)'
);
$stmt->execute([$title, $body, date('c')]);

The three drivers quote and bind the parameters differently under the hood, but the API is the same. No per-driver code is needed for ordinary inserts, updates, or selects.

Timestamps as strings

Timestamps are stored as ISO 8601 strings (2025-01-15T12:34:56+00:00), not as native DATETIME types. This is deliberate:

  • ISO 8601 sorts correctly as a string in every driver.
  • No timezone conversion is performed on read.
  • The format is portable and human-readable.

The trade-off is a small storage overhead and the loss of native date-arithmetic functions, neither of which matters for a notes app.

Driver-specific details

SQLite

The database file is created on first use. The connection enables foreign-key enforcement (off by default in SQLite) and WAL journaling. The created column is declared as TEXT because SQLite stores ISO strings natively.

MySQL

The connection uses charset=utf8mb4 and sets PDO::ATTR_EMULATE_PREPARES = false so that real server-side prepared statements are used. The table is created with ENGINE=InnoDB and COLLATE=utf8mb4_unicode_ci so that Unicode comparison behaves consistently.

PostgreSQL

The created column is VARCHAR(40) — large enough for any ISO 8601 string, small enough to index efficiently. A separate CREATE INDEX IF NOT EXISTS statement is issued because PostgreSQL does not support inline index declarations in CREATE TABLE.

One code base, three drivers. Switching databases is a .env change, not a code change. The ensure_schema() function and PDO do the rest.

The /php-static Route

This was one of the issues identified in the earlier review: index.php referenced /php-static/style.css but no such route existed in php_routes.py, so the CSS was a 404 on every platform and the notes app rendered completely unstyled.

The fix, in two parts

1. The route exists now

backend/routes/php_routes.py registers a route: 

@router.get("/php-static/{asset:path}", include_in_schema=False)
async def php_static(asset: str):
    path = _resolve_static_safe(asset)
    if path is None:
        raise HTTPException(status_code=404, detail=f"Not found: {asset}")
    return FileResponse(path)

The :path converter accepts nested paths, and _resolve_static_safe() applies the same path-traversal protection as the PHP execution route.

2. The CSS file lives where the route serves from

The stylesheet now lives at php_app/static/style.css — the directory the route serves from. index.php's <link> tag resolves to this file.

The directory is created automatically

backend/main.py's _ensure_php_dirs() creates php_app/static/ (and php_app/data/) on startup, so the folder is always present even on a fresh clone: 

def _ensure_php_dirs() -> None:
    if not settings.php_enabled:
        return
    for sub in ("data", "static"):
        d = PHP_APP_DIR / sub
        try:
            d.mkdir(parents=True, exist_ok=True)
        except Exception as exc:
            logger.warning("Could not create {}: {}", d, exc)

The old file is kept as a stub

The old php_app/style.css is kept as a stub with a comment pointing at the new location. This is defensive: any cached browser reference to /php/style.css gets a harmless stub instead of a 404. The stub also contains the minimal styling needed to render its own message, so a user who lands on it sees a readable explanation rather than unstyled HTML.

Why keep the stub? A 404 on a stylesheet is silent — the browser falls back to default styling and the page looks broken. A stub with a comment is loud: a developer who opens DevTools sees the redirect message and knows exactly where the file went.

How the URL is constructed

index.php uses a helper to build the stylesheet URL: 

<link rel="stylesheet"
      href="<?= h($base) ?>/php-static/style.css">

The $base variable comes from app_base(), which reads HTTP_X_FORWARDED_PREFIX from the CGI environment. This makes the app work whether it is mounted at /php/ or at the root of a subpath — a detail that matters when the backend is proxied.

Verifying the route

$ curl -I http://127.0.0.1:8000/php-static/style.css
HTTP/1.1 200 OK
content-type: text/css; charset=utf-8
content-length: 3421

A 404 here means the file is missing from php_app/static/. A 500 means the static directory does not exist — check the backend startup log for the _ensure_php_dirs warning.

POST-not-GET Delete

The delete action is a POST form, not a GET link. This is a deliberate design decision that closes a class of bugs that are easy to introduce and hard to notice.

The current form

<form method="post" action="/php/">
    <input type="hidden" name="action" value="delete" />
    <input type="hidden" name="id" value="42" />
    <button type="submit" ...>×</button>
</form>

The old form (and why it was wrong)

<a href="/php/?delete=42">×</a>

A GET-based delete can be triggered by:

  • A browser prefetcher. Some browsers speculatively fetch links on hover. If the link is /php/?delete=42, the note is deleted before the user has clicked anything.
  • A link scanner. Corporate email gateways, antivirus tools, and social-media previews all follow links to check for malware. A GET delete fires on every scan.
  • A bookmark. Bookmarking the delete URL and revisiting it later deletes the note again.
  • An embedded image. A malicious page can embed <img src="http://your-server/php/?delete=42"> and trigger the delete when the page loads.

A POST is not automatically triggered by any of those. The browser only sends a POST when a form is explicitly submitted.

Backward compatibility

The current implementation still accepts GET ?delete=ID for backward compatibility, but the primary path is a POST. The old path exists so that any cached page or bookmark that still uses the old URL does not break — the user sees the delete happen, and the next page load uses the POST form.

The GET path is deprecated. It is kept only to avoid breaking old bookmarks. New code should always use the POST form. Future versions may remove the GET path entirely.

Confirmation prompt

The delete button also has an onclick confirmation: 

<button type="submit"
        onclick="return confirm('Delete this note?')">×</button>

This is a UX guard rail, not a security control — a user who really wants to delete a note can accept the prompt. Its job is to prevent the accidental click from being destructive.

CSRF considerations

There is no CSRF token in the current implementation. The notes app is designed for single-user localhost use, where CSRF is not a meaningful threat — an attacker on another website cannot reach 127.0.0.1:8000 because that address is not routable from the public internet.

If the backend is ever exposed on a public address, a CSRF token should be added. The POST form is a step in that direction — it means adding a token is a one-line change rather than a rewrite of the delete path.

Redirect after POST

After a successful add or delete, the app issues a 302 redirect to /php/. This is the standard "redirect after POST" pattern, and it prevents the common bug where reloading the result page re-submits the form. 

header("Location: {$base}/php/");
exit;

Without the redirect, pressing F5 after adding a note would add a second copy. With the redirect, F5 simply reloads the notes list.

Permissions & WAL

Two small changes in db.php have outsized consequences: the mkdir mode and the SQLite journal mode.

Data directory permissions

The db.php mkdir call now uses 0755, not the original 0777: 

mkdir($dir, 0755, true);

What the bits mean:

OctalOwnerGroupOther
0755rwxr-xr-x
0777rwxrwxrwx

0777 would add write permission for group and other, letting any user on a shared host drop a malicious file into the data directory. The change is a no-op on Windows (permissions are ignored there) and a security improvement on Unix.

Never use 0777 on a directory the PHP process can write to. A world-writable data directory is a code-execution vector: an attacker who can write a file there can sometimes get the web server to execute it. 0755 is the correct default.

The database file permissions

The SQLite database file itself is created by PDO when the first connection is established. Its permissions depend on the process umask:

UmaskEffective file mode
022 (typical)0644 — owner rw, others r
002 (group-writable)0664 — owner rw, group rw
077 (private)0600 — owner rw only

For the default single-user scenario, 0644 is fine. On a multi-user host where other users should not read the notes, set the umask or use a restricted user for the PHP-CGI subprocess.

SQLite WAL mode

The SQLite connection now enables Write-Ahead Logging: 

$pdo->exec('PRAGMA journal_mode = WAL');

WAL mode changes SQLite's journaling behaviour in two ways:

  • Concurrent readers. Readers do not block writers and writers do not block readers. The default rollback journal mode serialises all access.
  • Cheaper commits. A commit appends to the WAL file rather than writing and syncing the entire database page set. This is significantly faster for write-heavy workloads.

The WAL sidecar files

WAL mode creates two additional files alongside the database:

FilePurpose
app.db-walThe write-ahead log — pending changes not yet checkpointed into the main file
app.db-shmThe shared-memory index — coordinates readers and the writer

The sidecar files are cleaned up automatically when the last connection closes. They are listed in .gitignore alongside *.db.

WAL is a persistent database property. It is set once and survives subsequent connections. You do not need to re-issue the pragma on every connect — but doing so is harmless.

Foreign key enforcement

SQLite has foreign keys disabled by default, which surprises most developers. The connection enables them explicitly: 

$pdo->exec('PRAGMA foreign_keys = ON');

The notes app does not currently use foreign keys — there is only one table — but the pragma is in place so that any future schema change that adds a foreign key gets the expected behaviour automatically.

Backup with WAL

A naive cp app.db backup.db is unsafe under WAL mode because it misses un-checkpointed writes in the WAL file. Use the SQLite CLI's .backup command instead: 

$ runtime/sqlite/sqlite3 php_app/data/app.db ".backup backup.db"

The .backup command takes a proper snapshot that includes any pending WAL content.

Driver Preflight

db.php checks PDO::getAvailableDrivers() before attempting a connection. This produces a clear, actionable error message instead of the generic "could not find driver" that PHP normally emits.

The check

$installed = PDO::getAvailableDrivers();
if (!in_array($driver, $installed, true)) {
    throw new RuntimeException(
        "PDO driver '$driver' is not installed. "
        . "Available drivers: " . (empty($installed) ? '(none)' : implode(', ', $installed))
        . ". " . $hint
    );
}

What the user sees

On a Debian machine with PHP installed but php-sqlite3 missing, the error message is: 

PDO driver 'sqlite' is not installed. Available drivers: mysql, pgsql.
On Debian/Ubuntu: sudo apt install php-sqlite3
On Fedora: sudo dnf install php-pdo
On macOS: brew reinstall php

Compare that with the default PHP error, which is just could not find driver with no further detail.

Platform-specific hints

DriverHint shown
sqlite Debian/Ubuntu: apt install php-sqlite3 · Fedora: dnf install php-pdo · macOS: brew reinstall php
mysql Debian/Ubuntu: apt install php-mysql · Fedora: dnf install php-mysqlnd
pgsql Debian/Ubuntu: apt install php-pgsql · Fedora: dnf install php-pgsql

The /api/php/drivers endpoint

The same information is exposed programmatically through backend/routes/php_routes.py: 

@router.get("/api/php/drivers")
async def php_pdo_drivers():
    php = find_php_cgi()
    if php is None:
        return {"available": False, "drivers": []}
    result = subprocess.run(
        [php, "-r", "echo implode(',', PDO::getAvailableDrivers());"],
        capture_output=True, text=True, timeout=5,
    )
    drivers = [d.strip() for d in result.stdout.strip().split(",") if d.strip()]
    return {"available": True, "drivers": sorted(drivers)}

A settings-page UI can call this endpoint to render a "PDO drivers available" panel without shelling out to PHP itself.

Calling it from the command line

$ curl http://127.0.0.1:8000/api/php/drivers
{"available":true,"drivers":["mysql","pgsql","sqlite"]}

If the list is empty, PHP was installed without any PDO drivers. This is common on minimal container images — the base php-cli package does not pull in any driver packages by default.

Fail early, fail clearly. A preflight check that produces a specific, actionable error is worth ten generic "something went wrong" messages. The check costs one function call per request and saves hours of debugging.

What if the driver is missing but the user does not need it?

The preflight only fires on the configured driver. If AGENT_PHP_DB_DRIVER=sqlite and the pdo_sqlite extension is missing, the app fails — but switching to mysql in .env would work if pdo_mysql is present. The preflight is per-driver, not per-application.

Common Configurations

Three worked examples covering the realistic deployment scenarios. Every one is a .env change — no PHP code modification is required.

1. Single-user SQLite (default)

AGENT_PHP_ENABLED=true
AGENT_PHP_DB_DRIVER=sqlite
AGENT_PHP_SQLITE_PATH=data/app.db

The database file is created at php_app/data/app.db on first request. Nothing else to configure. This is the recommended setup for a single-user machine.

ProsCons
Zero configuration · no server to run · single file to back up Single-writer only · no network access

2. Local MySQL

AGENT_PHP_ENABLED=true
AGENT_PHP_DB_DRIVER=mysql
AGENT_PHP_DB_HOST=127.0.0.1
AGENT_PHP_DB_PORT=3306
AGENT_PHP_DB_NAME=notes
AGENT_PHP_DB_USER=notes_user
AGENT_PHP_DB_PASSWORD=secret

The database and user must exist before the first request: 

CREATE DATABASE notes CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'notes_user'@'localhost' IDENTIFIED BY 'secret';
GRANT ALL PRIVILEGES ON notes.* TO 'notes_user'@'localhost';
FLUSH PRIVILEGES;

The notes table is created automatically on the first request. You do not need to run any DDL yourself.

ProsCons
Multi-writer · network-accessible · familiar tooling Requires a running MySQL server · separate backup process

3. PostgreSQL on another host

AGENT_PHP_ENABLED=true
AGENT_PHP_DB_DRIVER=pgsql
AGENT_PHP_DB_HOST=db.example.com
AGENT_PHP_DB_PORT=5432
AGENT_PHP_DB_NAME=notes
AGENT_PHP_DB_USER=notes_user
AGENT_PHP_DB_PASSWORD=secret

Requires:

  • The pdo_pgsql extension installed for PHP.
  • Network access from the backend host to the database server.
  • The database and user created server-side.
  • PostgreSQL's pg_hba.conf configured to allow the backend host to connect (or a firewall rule if the server is remote).
ProsCons
Best transaction semantics · excellent concurrency · rich SQL Most configuration of the three · network latency on every request

Disabling the app entirely

AGENT_PHP_ENABLED=false

When disabled, the /php/* routes are not registered. Requests to those paths return 404. The rest of the backend — chat, graph, models — is unaffected.

Switching between drivers

Changing AGENT_PHP_DB_DRIVER does not migrate any data. The notes table is created fresh in the new database on the first request. To carry data across, export from the old database and import into the new one manually.

No automatic migration. The app's schema is intentionally minimal — one table, four columns, no foreign keys. For a real application with a non-trivial schema, use a proper migration tool. For this app, the manual INSERT INTO new_db.notes SELECT * FROM old_db.notes is sufficient.

Testing & Cleanup

With the backend running, the notes app can be exercised end-to-end from a shell. Seven steps, all curl.

The test sequence

1. Check PHP is available

$ curl http://127.0.0.1:8000/api/php/status
{
  "available": true,
  "binary": "/path/to/runtime/php/php-cgi.exe",
  "is_cgi": true,
  "version": "PHP 8.4.15 (cgi-fcgi) ..."
}

If available is false, the backend could not find a PHP binary. See the runtime documentation for the bootstrap fix.

2. Check the driver is available

$ curl http://127.0.0.1:8000/api/php/drivers
{"available":true,"drivers":["sqlite"]}

The list must contain the driver configured in AGENT_PHP_DB_DRIVER. If it does not, install the matching PDO extension for PHP.

3. Load the notes page

$ curl http://127.0.0.1:8000/php/ | head -30
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    ...

The page should render with a styled header, an add-note form, and an empty notes list. If it renders unstyled, the /php-static/style.css route is broken — see The /php-static route.

4. Add a note

$ curl -X POST http://127.0.0.1:8000/php/ \
    -d 'action=add' \
    -d 'title=Test note' \
    -d 'body=Created via curl'

A successful add returns a 302 redirect to /php/. curl does not follow the redirect by default — the important thing is that the response is a 302, not a 500.

5. Verify the note was saved

$ curl http://127.0.0.1:8000/php/ | grep "Test note"
    <strong>Test note</strong>

The note appears in the rendered HTML.

6. Check the JSON demo endpoint

$ curl http://127.0.0.1:8000/php/demo.php
{
    "ok": true,
    "driver": "sqlite",
    "version": "3.46.0",
    "note_count": 1,
    "tables": ["notes"],
    "php": "8.4.15",
    "server": "3olution-Python-PHP",
    "time": "2025-01-15T12:34:56+00:00"
}

The version field confirms the driver is functioning. The tables list confirms the schema was created.

7. Inspect the SQLite database directly

$ runtime/sqlite/sqlite3 php_app/data/app.db "SELECT * FROM notes;"
1|Test note|Created via curl|2025-01-15T12:34:56+00:00

The portable SQLite CLI is the fastest way to verify what is actually on disk.

Cleanup and reset

To reset the notes app to a blank state:

SQLite:

$ rm php_app/data/app.db \
     php_app/data/app.db-wal \
     php_app/data/app.db-shm

The next request to /php/ recreates the database and the notes table automatically.

MySQL / PostgreSQL:

DROP TABLE notes;

Or drop and recreate the whole database. The table is recreated on the next request either way.

Full reset with curl

# List every note (just the IDs)
curl http://127.0.0.1:8000/php/ | grep -oP 'name="id" value="\K\d+'

# Delete each one

Verifying the WAL files

After the first write, two sidecar files should exist: 

$ ls -la php_app/data/
-rw-r--r--  app.db
-rw-r--r--  app.db-shm
-rw-r--r--  app.db-wal

On a clean read-only connection, SQLite may check-point and remove the sidecar files. Their presence is normal, and their absence is also normal — it depends on the last operation the database performed.

Test from a clean state. If something is behaving strangely, delete the entire php_app/data/ folder (not just the .db file) and let the app recreate it. This rules out a corrupted WAL sidecar as the cause.

Checking the backend log

The backend logs every PHP request at DEBUG level: 

$ curl "http://127.0.0.1:8000/api/logs/recent?lines=100&source=backend"

Or directly from disk: 

$ tail -f logs/backend-*.log | grep -i php

The log includes the PHP stderr output if the subprocess wrote anything. This is where you see PHP warnings, deprecation notices, and the stack trace of any uncaught exception.

Troubleshooting

Blank page or 500 error

Check the backend log first:

$ tail -50 logs/backend-*.log

A PHP syntax error or uncaught exception writes a stack trace to stderr, which the backend logs. The most common causes are a missing php.ini (so no extensions are loaded) or a missing PDO driver.

"could not find driver"

The PHP binary is running but the driver configured in AGENT_PHP_DB_DRIVER is not installed. Confirm with: 

$ runtime/php/php.exe -m | grep -i pdo

If the matching pdo_* extension is missing, add it to runtime/php/php.ini (or install the corresponding system package). The bootstrap's php.ini enables pdo_sqlite by default; the others must be uncommented.

Unstyled page (no CSS)

The /php-static/style.css route is not serving the file. Three things to check:

  1. Does php_app/static/style.css exist? If not, the CSS was lost during a copy.
  2. Does curl -I http://127.0.0.1:8000/php-static/style.css return 200? If it returns 404, the route is missing or the file is not where the route expects it.
  3. Does the backend startup log contain a warning about php_app/static/? If the directory could not be created, the route has nothing to serve.

"PDO driver 'sqlite' is not installed"

The preflight in db.php fired. The message includes the platform-specific install command. On the portable runtime, the fix is usually: 

$ python bootstrap/setup.py --force --skip-python --skip-sqlite --skip-deps --skip-vendor

This re-extracts the PHP ZIP and rewrites php.ini with the correct extension= lines.

Note does not appear after adding

Three possible causes:

  • The insert failed silently. Check that the POST returned 302 (not 500). A 500 means the insert threw.
  • The redirect went to the wrong place. Check the Location header on the 302 response. If app_base() returned an empty string, the redirect goes to /php/ — which is correct for a backend with no prefix.
  • The page is cached. Reload with Ctrl+Shift+R to bypass the browser cache.

Delete returns 404 or does nothing

Verify the form is submitting a POST with action=delete. If the form is submitting a GET (some browsers fall back to GET if the method attribute is misspelled), the action is lost and nothing happens.

The server also accepts GET ?delete=ID for backward compatibility, so a manual curl 'http://127.0.0.1:8000/php/?delete=1' should work as a test.

Database file is world-readable

The SQLite file is created with the process umask. If the umask is 022, the file ends up with mode 0644 — readable by any user on the system. To restrict it: 

$ umask 077
$ # then restart the backend

Or run the backend as a dedicated user with no other members in its group.

"file is not a database"

The file at php_app/data/app.db is not a valid SQLite database. This usually means an earlier operation wrote something else to that path — for example, a text error message was written because the directory did not exist and a different process created it as a regular file.

Delete the file and let the app recreate it: 

$ rm php_app/data/app.db*
$ curl http://127.0.0.1:8000/php/

"database is locked"

SQLite's default rollback journal serialises all access. WAL mode — which db.php enables — allows concurrent readers, so this error is rare. It can still happen if a long-running write transaction is in progress when a second writer tries to commit.

The notes app's writes are short (single INSERT or DELETE), so the lock window is tiny. A "database is locked" error under this app almost always means a stale process is holding the lock — for example, a runtime/sqlite/sqlite3 shell left open in another terminal.

Redirect loops

If app_base() returns a non-empty prefix but the backend is actually mounted at the root, the redirect target becomes /php/php/ and a loop can develop. Verify what the backend sends: 

$ curl -i -X POST http://127.0.0.1:8000/php/ \
    -d 'action=add' -d 'title=x' -d 'body=y' | grep -i location
Location: /php/

The Location header should not contain a doubled prefix. If it does, check that no upstream proxy is injecting X-Forwarded-Prefix unexpectedly.

Non-ASCII characters in notes are garbled

The app declares UTF-8 in both the HTML (<meta charset="UTF-8">) and the CGI response header. If characters are garbled, check that the database connection uses a UTF-8-compatible charset — MySQL needs utf8mb4, which db.php sets explicitly.

On SQLite, encoding is always UTF-8 and no configuration is needed.

Resetting

To wipe the notes app back to a blank state, delete the database and its WAL sidecars: 

$ rm php_app/data/app.db \
     php_app/data/app.db-wal \
     php_app/data/app.db-shm

The next request to /php/ recreates the database and the notes table automatically.

Deleting the database is not reversible. There is no undo. Back up app.db first if the notes matter.

Backup

A simple cp is not safe under WAL mode — it can miss un-checkpointed writes. Use the SQLite CLI's .backup command instead: 

$ runtime/sqlite/sqlite3 php_app/data/app.db \
    ".backup php_app/data/backup-$(date +%F).db"

The resulting file is a complete, self-contained snapshot that does not depend on the WAL sidecars.

Permissions

The directory is created with mode 0755 — owner can write, everyone else can read and traverse. The database file itself is created with the process umask, typically 0644.

To restrict access on a multi-user host:

$ chmod 700 php_app/data
$ chmod 600 php_app/data/app.db*

This makes the database readable only by its owner. The PHP-CGI subprocess runs as the backend user, so it continues to work.

How files are served

backend/routes/php_routes.py registers the route: 

@router.get("/php-static/{asset:path}", include_in_schema=False)
async def php_static(asset: str):
    path = _resolve_static_safe(asset)
    if path is None:
        raise HTTPException(status_code=404, detail=f"Not found: {asset}")
    return FileResponse(path)

The :path converter accepts nested paths (js/app.js, img/logo.svg), and _resolve_static_safe() applies the same path-traversal protection as the PHP execution route.

Why not just serve from web/?

The backend already serves a static directory at / (web/). Two reasons the PHP app has its own static root:

  1. Separation of concerns. web/ is the frontend for the chat and graph editor. php_app/static/ is the frontend for the PHP notes app. Mixing them would make both harder to reason about.
  2. Different lifecycle. The PHP app can be disabled (AGENT_PHP_ENABLED=false) without removing the main frontend. Keeping the assets in separate folders makes that clean.

Adding a new static asset

<link rel="stylesheet"

<script src="<?= h($base) ?>/php-static/js/app.js"></script>

No backend change is needed. The route serves any file under the directory.

<?php
/**
 * SQL helper for the 3olution PHP app.
 * https://3olution.com
 *
 * Returns a PDO connection configured from environment variables
 * that the Python backend passes through the CGI environment.
 *
 * ═══════════════════════════════════════════════════════════════════
 *   SUPPORTED DRIVERS
 * ═══════════════════════════════════════════════════════════════════
 *
 *   sqlite   Zero-config. The database file is created on first use.
 *   mysql    Requires pdo_mysql extension and a running MySQL server.
 *   pgsql    Requires pdo_pgsql extension and a running PostgreSQL.
 *
 * The driver is chosen by AGENT_PHP_DB_DRIVER. When it's 'sqlite', the
 * file lives at AGENT_PHP_SQLITE_PATH relative to php_app/. When it's
 * mysql or pgsql, the connection parameters come from AGENT_PHP_DB_*.
 *
 * ═══════════════════════════════════════════════════════════════════
 *   CROSS-DRIVER SCHEMA
 * ═══════════════════════════════════════════════════════════════════
 *
 * The `notes` table is defined per-driver in ensure_schema(). SQLite,
 * MySQL, and PostgreSQL each have their own dialect for auto-increment
 * primary keys:
 *
 *     SQLite:       INTEGER PRIMARY KEY AUTOINCREMENT
 *     MySQL:        INT AUTO_INCREMENT PRIMARY KEY
 *     PostgreSQL:   SERIAL PRIMARY KEY
 *
 * Trying to run one dialect's CREATE TABLE against a different driver
 * raises a syntax error. The ensure_schema() function switches on the
 * connected driver and emits the correct DDL.
 *
 * ═══════════════════════════════════════════════════════════════════
 *   TIMESTAMPS
 * ═══════════════════════════════════════════════════════════════════
 *
 * Timestamps are stored as ISO 8601 strings ('2025-01-15T12:34:56+00:00')
 * rather than native DATETIME types. This is deliberate:
 *
 *   - ISO 8601 sorts correctly as a string in every driver.
 *   - No timezone conversion is performed on read.
 *   - The format is portable and human-readable.
 *
 * The trade-off is a small storage overhead and the loss of native
 * date-arithmetic functions, neither of which matter for a notes app.
 */

declare(strict_types=1);


// ══════════════════════════════════════════════════════════════════════
//  Connection
// ══════════════════════════════════════════════════════════════════════

/**
 * Return a singleton PDO connection to the configured database.
 *
 * The connection is created on first call and cached in a static
 * variable for the lifetime of the request. Each PHP-CGI request is a
 * fresh process, so "the lifetime of the request" is effectively the
 * lifetime of this function's execution.
 *
 * The returned PDO has three important attributes set:
 *
 *   ERRMODE_EXCEPTION      Errors raise PDOException rather than
 *                          returning false. This makes error handling
 *                          uniform and forces callers to think about
 *                          failure.
 *
 *   DEFAULT_FETCH_MODE     Every fetch returns an associative array
 *                          (column name → value) instead of the default
 *                          numeric-indexed array.
 *
 *   EMULATE_PREPARES=false MySQL only — uses real server-side prepared
 *                          statements, which is both safer (correct
 *                          quoting even in edge cases) and faster for
 *                          repeated queries.
 *
 * @throws RuntimeException if the driver is unavailable or the
 *         connection fails.
 */
function app_db(): PDO
{
    static $pdo = null;
    if ($pdo !== null) {
        return $pdo;
    }

    $driver = strtolower(trim((string)(getenv('AGENT_PHP_DB_DRIVER') ?: 'sqlite')));

    // ── Preflight: check the driver is actually installed ────────────
    //
    // Some distributions ship PHP with no PDO drivers by default. The
    // user installs `php-cli` but not `php-sqlite3`, then wonders why
    // nothing works. This check produces a clear, actionable message
    // instead of "could not find driver".
    $installed = PDO::getAvailableDrivers();
    if (!in_array($driver, $installed, true)) {
        $install_hints = [
            'sqlite' => 'On Debian/Ubuntu: sudo apt install php-sqlite3
                         On Fedora: sudo dnf install php-pdo
                         On macOS: brew reinstall php',
            'mysql'  => 'On Debian/Ubuntu: sudo apt install php-mysql
                         On Fedora: sudo dnf install php-mysqlnd',
            'pgsql'  => 'On Debian/Ubuntu: sudo apt install php-pgsql
                         On Fedora: sudo dnf install php-pgsql',
        ];
        $hint = $install_hints[$driver]
            ?? "Install the pdo_$driver extension for PHP.";
        throw new RuntimeException(
            "PDO driver '$driver' is not installed. "
            . "Available drivers: " . (empty($installed) ? '(none)' : implode(', ', $installed))
            . ". " . $hint
        );
    }

    // ── Dispatch to the correct DSN builder ──────────────────────────
    switch ($driver) {

        // ── MySQL ────────────────────────────────────────────────────
        case 'mysql':
            $host = getenv('AGENT_PHP_DB_HOST')     ?: '127.0.0.1';
            $port = getenv('AGENT_PHP_DB_PORT')     ?: '3306';
            $name = getenv('AGENT_PHP_DB_NAME')     ?: 'app';
            $user = getenv('AGENT_PHP_DB_USER')     ?: 'app';
            $pass = getenv('AGENT_PHP_DB_PASSWORD') ?: '';

            $dsn = "mysql:host={$host};port={$port};dbname={$name};charset=utf8mb4";
            $pdo = new PDO($dsn, $user, $pass, [
                PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
                PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
                PDO::ATTR_EMULATE_PREPARES   => false,
            ]);
            break;

        // ── PostgreSQL ───────────────────────────────────────────────
        case 'pgsql':
        case 'postgres':
            $host = getenv('AGENT_PHP_DB_HOST')     ?: '127.0.0.1';
            $port = getenv('AGENT_PHP_DB_PORT')     ?: '5432';
            $name = getenv('AGENT_PHP_DB_NAME')     ?: 'app';
            $user = getenv('AGENT_PHP_DB_USER')     ?: 'app';
            $pass = getenv('AGENT_PHP_DB_PASSWORD') ?: '';

            $dsn = "pgsql:host={$host};port={$port};dbname={$name}";
            $pdo = new PDO($dsn, $user, $pass, [
                PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
                PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
            ]);
            break;

        // ── SQLite (default) ─────────────────────────────────────────
        case 'sqlite':
        default:
            $rel = (string)(getenv('AGENT_PHP_SQLITE_PATH') ?: 'data/app.db');

            // Absolute paths pass through. Relative paths resolve
            // against php_app/.
            $is_absolute =
                substr($rel, 0, 1) === '/'
                || (strlen($rel) > 1
                    && ctype_alpha($rel[0])
                    && $rel[1] === ':')
                || substr($rel, 0, 2) === '\\\\';

            if ($is_absolute) {
                $path = $rel;
            } else {
                $path = __DIR__ . DIRECTORY_SEPARATOR . ltrim($rel, '/\\');
            }

            $dir = dirname($path);
            if (!is_dir($dir)) {
                // 0755 is owner-writable, group/other-readable.
                // Do NOT use 0777 — that is world-writable and a
                // needless security exposure on shared hosts.
                mkdir($dir, 0755, true);
            }

            $pdo = new PDO("sqlite:{$path}", null, null, [
                PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
                PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
            ]);
            // Enable foreign key enforcement (off by default in SQLite).
            $pdo->exec('PRAGMA foreign_keys = ON');
            // Use WAL mode for better concurrent read performance.
            // WAL persists across connections because it is a database
            // property, not a per-connection setting.
            $pdo->exec('PRAGMA journal_mode = WAL');
            break;
    }

    return $pdo;
}

/**
 * Create the `notes` table if it does not exist.
 *
 * Emits driver-specific DDL because the three supported databases
 * disagree on how auto-increment primary keys are declared:
 *
 *     SQLite:     INTEGER PRIMARY KEY AUTOINCREMENT
 *     MySQL:      INT AUTO_INCREMENT PRIMARY KEY
 *     PostgreSQL: SERIAL PRIMARY KEY
 *
 * Safe to call on every request. CREATE TABLE IF NOT EXISTS is a no-op
 * when the table already exists.
 *
 * @param PDO $db The database connection.
 * @return void
 * @throws PDOException on DDL failure.
 */
function ensure_schema(PDO $db): void
{
    $driver = $db->getAttribute(PDO::ATTR_DRIVER_NAME);

    switch ($driver) {
        case 'mysql':
            $sql = "
                CREATE TABLE IF NOT EXISTS notes (
                    id      INT AUTO_INCREMENT PRIMARY KEY,
                    title   VARCHAR(255) NOT NULL,
                    body    TEXT NOT NULL,
                    created VARCHAR(40) NOT NULL,
                    INDEX idx_notes_created (created)
                ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
            ";
            break;

        case 'pgsql':
            $sql = "
                CREATE TABLE IF NOT EXISTS notes (
                    id      SERIAL PRIMARY KEY,
                    title   VARCHAR(255) NOT NULL,
                    body    TEXT NOT NULL,
                    created VARCHAR(40) NOT NULL
                );
                CREATE INDEX IF NOT EXISTS idx_notes_created ON notes (created)
            ";
            break;

        case 'sqlite':
        default:
            $sql = "
                CREATE TABLE IF NOT EXISTS notes (
                    id      INTEGER PRIMARY KEY AUTOINCREMENT,
                    title   TEXT NOT NULL,
                    body    TEXT NOT NULL,
                    created TEXT NOT NULL
                )
            ";
            break;
    }

    $db->exec($sql);
}

/**
 * HTML-escape a string for safe output.
 *
 * Convenience wrapper around htmlspecialchars() with the flags most
 * commonly needed: ENT_QUOTES (encode both double and single quotes)
 * and ENT_SUBSTITUTE (replace invalid UTF-8 sequences with U+FFFD
 * rather than returning an empty string).
 */
function h(?string $s): string
{
    return htmlspecialchars(
        (string)($s ?? ''),
        ENT_QUOTES | ENT_SUBSTITUTE,
        'UTF-8'
    );
}


/**
 * Return the URL prefix the app is mounted at.
 *
 * The Python backend injects X-Forwarded-Prefix: /php into the CGI
 * environment. PHP sees it as $_SERVER['HTTP_X_FORWARDED_PREFIX'].
 * Relative links and form actions prepend this prefix so they work
 * whether the app is mounted at /php/ or at the root.
 */
function app_base(): string
{
    $prefix = $_SERVER['HTTP_X_FORWARDED_PREFIX'] ?? '';
    if (!is_string($prefix)) {
        return '';
    }
    // Strip a trailing slash so concatenating "/path" always works.
    return rtrim($prefix, '/');
}

 * Endpoint:

 * Response shape:
 *     {

 *       "tables": ["notes"],
 *       "php": "8.4.15",
 *       "server": "3olution-Python-PHP",
 *       "time": "2025-01-15T12:34:56+00:00"
 *     }
 *
 * On error, returns HTTP 500 with:
 *     {"ok": false, "error": "..."}
 *
 * ═══════════════════════════════════════════════════════════════════
 *   CROSS-DRIVER NOTES
 * ═══════════════════════════════════════════════════════════════════
 *
 * The database version is fetched with a driver-specific query:
 *
 *     SQLite:     SELECT sqlite_version()
 *     MySQL:      SELECT VERSION()
 *     PostgreSQL: SELECT version()
 *
 * PostgreSQL has a SHOW server_version command whose result column is
 * named differently across releases. Using SELECT version() instead
 * returns a single, consistently-named `version` column on every
 * PostgreSQL build, so no special-casing is needed.
 */

declare(strict_types=1);

header('Content-Type: application/json; charset=utf-8');
header('Cache-Control: no-store');

require_once __DIR__ . '/db.php';

try {
    $db = app_db();
    ensure_schema($db);

    $driver = (string)$db->getAttribute(PDO::ATTR_DRIVER_NAME);

    // ── Database version ─────────────────────────────────────────────
    $version = 'unknown';
    switch ($driver) {
        case 'sqlite':
            $row = $db->query('SELECT sqlite_version() AS v')->fetch();
            $version = $row['v'] ?? 'unknown';
            break;

        case 'mysql':
            $row = $db->query('SELECT VERSION() AS v')->fetch();
            $version = $row['v'] ?? 'unknown';
            break;

        case 'pgsql':
            $row = $db->query('SELECT version() AS v')->fetch();
            // PostgreSQL's version() returns a long descriptive string
            // like "PostgreSQL 15.3 on x86_64-pc-linux-gnu, ..." —
            // extract just the version number portion.
            $full = $row['v'] ?? 'unknown';
            if (preg_match('/PostgreSQL\s+([0-9.]+)/', $full, $m)) {
                $version = $m[1];
            } else {
                $version = $full;
            }
            break;
    }

    // ── Note count ───────────────────────────────────────────────────
    $note_count = 0;
    try {
        $row = $db->query('SELECT COUNT(*) AS c FROM notes')->fetch();
        $note_count = (int)($row['c'] ?? 0);
    } catch (Throwable $e) {
        // Table does not exist yet — treat as zero notes.
        $note_count = 0;
    }

    // ── Table listing (driver-specific) ──────────────────────────────
    $tables = [];
    try {
        if ($driver === 'sqlite') {
            $stmt = $db->query(
                "SELECT name FROM sqlite_master
                 WHERE type = 'table' AND name NOT LIKE 'sqlite_%'
                 ORDER BY name"
            );
        } elseif ($driver === 'mysql') {
            $stmt = $db->query('SHOW TABLES');
        } elseif ($driver === 'pgsql') {
            $stmt = $db->query(
                "SELECT tablename FROM pg_tables
                 WHERE schemaname = 'public'
                 ORDER BY tablename"
            );
        } else {
            $stmt = false;
        }

        if ($stmt !== false) {
            foreach ($stmt->fetchAll(PDO::FETCH_NUM) as $r) {
                $tables[] = (string)$r[0];
            }
        }
    } catch (Throwable $e) {
        // Table listing is cosmetic — ignore failures.
        $tables = [];
    }

    // ── Response ─────────────────────────────────────────────────────
    echo json_encode(
        [
            'ok'         => true,
            'driver'     => $driver,
            'version'    => $version,
            'note_count' => $note_count,
            'tables'     => $tables,
            'php'        => PHP_VERSION,
            'server'     => $_SERVER['SERVER_SOFTWARE'] ?? 'unknown',
            'time'       => date('c'),
        ],
        JSON_PRETTY_PRINT | JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE
    );

} catch (Throwable $e) {
    http_response_code(500);
    echo json_encode(
        [
            'ok'    => false,
            'error' => $e->getMessage(),
        ],
        JSON_PRETTY_PRINT | JSON_UNESCAPED_SLASHES
    );
}
